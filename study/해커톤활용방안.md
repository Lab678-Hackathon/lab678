# KONNECT 해커톤 활용방안 및 계획

> 작성일: 2026-10-28  
> 대상: KONNECT 리포지토리를 2박 3일 해커톤 플랫폼으로 활용하는 팀

---

## 1. 결론 요약

**사용 가능하다. 단, 확장(Extension) 방식이 가장 현실적이다.**

KONNECT는 AI Agent + RAG + 인증 + 지도 + 배포가 모두 완비된 프로덕션급 서비스다.  
2박 3일 안에 새로운 서비스를 처음부터 만드는 것보다, **이 위에 새 기능 레이어를 추가**하면 데모 가능한 완성도를 훨씬 빠르게 낼 수 있다.

---

## 2. 플랫폼 적합성 분석

### 2.1 강점 — 이미 갖춰진 것

| 영역 | 내용 |
|---|---|
| AI Agent 파이프라인 | LangChain tool-calling, 멀티턴 대화, 오케스트레이터 (`agent/`) |
| RAG | Supabase pgvector + OpenAI Embeddings — 지식베이스 적재·검색 전 과정 |
| 인증 | Supabase Auth (Google OAuth + 익명 Sign-in + identity linking) |
| 데이터베이스 | Supabase Postgres + RLS, 마이그레이션 스크립트 |
| 배포 인프라 | Render(백엔드) + Vercel(프론트) — 설정 파일 완비 |
| 외부 API 클라이언트 | TourAPI, TMap, Google Places, KMA, AirKorea — httpx + tenacity 패턴 |
| 프론트엔드 | 10개 페이지, 10개 이상 컴포넌트, 지도, 바텀시트, 상태관리 |
| 번역 모듈 | `agent/translate.py` + `components/translate-toggle.js` 기존 구현 존재 |
| 평가 프레임워크 | `eval/` — golden set + metrics, pytest 151개 이상 |
| 데이터 신뢰 패턴 | normalize → judge → rank → explain 파이프라인 |

### 2.2 약점 / 위험 요소

| 리스크 | 설명 |
|---|---|
| 도메인 결합도 높음 | `domain/` 로직이 서울 문화경험에 특화 — 새 도메인은 신규 작성 필요 |
| 학습 곡선 | 백엔드 모듈 90개 이상 — 온보딩에 반나절 최소 필요 |
| Seoul 특화 API | TourAPI EngService2는 한국 문화관광 전용 |
| 신뢰 불변식 | CLAUDE.md §6 원칙 — 팀원이 숙지하지 않으면 위반하기 쉬움 |

## 3. 접근 방식 선택

### Option A: KONNECT 확장 (권장)

기존 도메인(서울 문화경험) 위에 새 기능 레이어를 추가.

- 인프라·인증·배포 즉시 사용
- 온보딩 빠름 (기존 코드 건드리지 않고 새 모듈만 추가)
- 2박 3일 내 데모 가능한 완성도 달성 현실적
- **2박 3일 해커톤에 강력 권장**

### Option B: 인프라 템플릿으로 사용

FastAPI + Supabase + LangChain + Vanilla JS 패턴을 추출해 완전히 다른 서비스 구축.

- 자유도 높지만 기존 코드 제거·개조에 시간 소요
- 2박 3일에는 빠듯함 — 팀 인원이 5인 이상이면 고려 가능

## 4. 추천 확장 트랙 (Option A)

### Track 1: 맛집 + 문화 패키지 루트 `난이도 중` `임팩트 높음`

문화경험 추천 후 주변 식당을 자연스럽게 연계한 통합 루트 제공.

**확장 포인트:**
- `sources/` — 네이버 로컬 검색 API 또는 Kakao Local API 클라이언트 신규 추가
- `domain/food_filter.py` — 가격대·식이제한(채식/할랄/글루텐프리) 판정 로직
- `models/recommend.py` — `food_option` 필드 추가
- `agent/orchestrator.py` — 문화 후보 확정 후 식당 후보 병렬 조회 연결
- 프론트 — 결과 카드에 식당 섹션 추가

**데모 시나리오:** "박물관 관람 후 근처 한식 맛집(채식 가능)"을 한 번에 추천

---

### Track 2: 그룹 여행 플래너 `난이도 중`

여러 명의 관심사·예산·이동 선호를 병합해 공통 루트 추천.

**확장 포인트:**
- `models/group.py` — GroupSession, MemberPreference 스키마
- `db/migrations/0003_group_sessions.sql` — 그룹·멤버 테이블
- `domain/preferences_merge.py` — 다수 선호 교집합/가중합 로직 확장
- `api/group.py` — 그룹 생성·참가·선호 제출 엔드포인트
- 프론트 — 멤버 초대 링크 생성 + 선호 입력 시트 신규 추가

**데모 시나리오:** 4명이 각자 선호 입력 → AI가 모두가 만족할 문화 루트 생성

---

### Track 3: 번역 + 현장 가이드 강화 `난이도 낮음` `가장 빠른 완성`

이미 존재하는 `translate.py` + `translate-toggle.js`를 확장해 현장 AI 가이드로 발전.

**확장 포인트:**
- `api/interpret.py` — `POST /api/interpret` 신규 (이미지/음성 → 번역 + 맥락 설명)
- OpenAI Whisper — 음성 입력 → 텍스트 변환
- GPT-4o Vision — 안내판 사진 → 번역 + 문화 설명
- 프론트 — 카메라/마이크 입력 컴포넌트, 결과 오버레이

**데모 시나리오:** 한국어 안내판 사진 찍기 → 즉시 영어 번역 + 문화적 배경 설명

---

### Track 4: 날씨 연동 동선 실시간 재구성 `난이도 중`

이미 있는 `domain/environment.py` + `sources/kma.py`를 심화해 날씨 변화 시 루트 자동 재구성.

**확장 포인트:**
- `sources/kma.py` — 실황(현재) → 단기예보(3~6시간 후) 추가 연동
- `domain/route.py` — 예보 악화 감지 시 실내 경험 우선 재정렬 로직
- `agent/route_orchestrator.py` — 날씨 변화 알림 + 대안 루트 제안
- 프론트 — 날씨 변화 배너 + "실내 전환" CTA

**데모 시나리오:** 오후에 비 예보 → 야외 일정을 실내 대체로 자동 재구성

## 5. 2박 3일 개발 일정

### Day 1 — 이해 + 설계 (8~10시간)

```
오전 (3h)  코드베이스 온보딩
           - CLAUDE.md §2(스택), §4(아키텍처), §6(신뢰 불변식) 필독
           - backend 실행: cd backend && uvicorn app.main:app --reload
           - frontend 실행: cd frontend && python -m http.server 5500
           - 기존 pytest 전체 통과 확인: python -m pytest

오후 (3h)  Track 선정 + 설계
           - 팀 논의로 Track 1~4 중 선택
           - 새 엔드포인트 API 계약 설계 (Pydantic 모델 초안)
           - 신규 외부 API 키 발급 (필요 시)
           - 새 브랜치 생성: git checkout -b hackathon/track-N

저녁 (3h)  기반 작업
           - DB 스키마 추가 (Supabase SQL 에디터)
           - models/ 에 새 Pydantic 모델 파일 생성
           - 더미 pytest 1개 작성 후 Green 확인
```

### Day 2 — 핵심 구현 (12시간)

```
오전 (4h)  백엔드 핵심 로직
           - sources/ 에 새 API 클라이언트 추가 (httpx + tenacity 패턴 복사)
           - domain/ 에 판정 로직 추가 + 단위 테스트
           - pytest Green 유지하며 진행

오후 (4h)  Agent 연결 + API 엔드포인트
           - agent/tools/schemas.py 에 새 Tool 추가
           - chat_agent.py 또는 orchestrator.py 확장
           - api/ 에 새 라우터 추가 → main.py include_router
           - 로컬 curl/브라우저로 동작 확인

저녁 (4h)  프론트엔드
           - pages/ 에 새 페이지 또는 기존 페이지 확장
           - components/ 에 새 UI 컴포넌트
           - js/api.js 에 새 엔드포인트 래퍼 추가
           - 모바일 브라우저 확인 (390px 기준)
```

### Day 3 — 통합 + 데모 (6~8시간)

```
오전 (3h)  통합 테스트 + 버그 수정
           - 전체 pytest 통과 확인
           - 실 브라우저 end-to-end 데모 시나리오 3회 통과
           - 엣지케이스 처리 (0건, API 실패 등)

오후 (2h)  배포 + 데모 준비
           - Render 백엔드 재배포 (git push → 자동)
           - Vercel 프론트 재배포
           - 데모 시나리오 3개 정리 + 발표 자료 준비

발표       5분 라이브 데모 + Q&A
```

## 6. 팀 역할 분담 (3인 확정)

> 팀원 3명 기준. 백엔드 2인 / 프론트+PM 1인 구성이 KONNECT 확장에 가장 효율적입니다.  
> 예상 주제: 공공성 + AI + 멀티컨텍스트

| 역할 | 주요 담당 영역 | Day 1 | Day 2 | Day 3 |
|---|---|---|---|---|
| **AI / Backend A** | agent/, domain/, sources/ | 새 공공 API 조사 + 클라이언트 작성 | LangChain 파이프라인 연결, 멀티컨텍스트 심화 | 통합 디버깅, trace 시각화 |
| **Backend B** | api/, db/, models/, 배포 | DB 스키마 + Pydantic 모델 확정 | API 엔드포인트 + Render 배포 갱신 | 버그 수정, 배포 안정화 |
| **Frontend + PM** | pages/, components/, 발표 | 화면 흐름 설계 + Track 최종 선정 | UI 구현 + 공공 데이터 출처 배지 | 데모 시나리오 3개 + 발표 준비 |

### 3인 분업 시 주의사항
- **API 계약(Pydantic 모델)을 Day 1 저녁까지 확정**해야 A와 B가 Day 2에 충돌 없이 병렬 작업 가능합니다.
- Backend B가 `api/` 라우터를 먼저 스텁으로 올려두면 Frontend가 Day 2 오전부터 바로 연결 가능합니다.
- Frontend + PM이 QA 역할도 겸하므로 Day 2 저녁에 통합 테스트 시간을 반드시 확보하세요.

## 8. 신규 모듈 추가 패턴 (빠른 참고)

새 기능을 추가할 때 아래 패턴을 그대로 따른다.

```
# 1. 새 외부 소스 추가
backend/app/sources/new_source.py
  - httpx.AsyncClient + tenacity retry
  - 타임아웃 내장 (connect=3s, read=10s)
  - 실패 시 빈 리스트 반환 (전체 실패 방지)

# 2. 새 도메인 판정
backend/app/domain/new_domain.py
  - 순수 함수 (외부 I/O 없음)
  - 미확인 값 → unknown 반환 (긍정 추정 금지)
  - pytest 단위 테스트 필수

# 3. 새 API 엔드포인트
backend/app/api/new_endpoint.py
  - APIRouter 생성
  - Pydantic 모델로 입출력 검증
  - Envelope(data=...) 로 감싸서 반환
  → main.py: app.include_router(new_endpoint.router)

# 4. 새 프론트 페이지
frontend/js/pages/new_page.js
  - export function showNewPage() {...}
  → app.js: import + showView('new-page') 라우팅
```

## 9. 트랙별 추천 우선순위

| 순위 | Track | 이유 |
|---|---|---|
| 1순위 | Track 3 (번역 가이드) | 가장 빠른 완성, 외국인 사용자에 직관적 |
| 2순위 | Track 1 (맛집 연계) | 사용자 임팩트 최고, 기존 route 파이프라인 재사용 |
| 3순위 | Track 2 (그룹 플래너) | 차별화 높음, DB 설계 공수 추가 필요 |
| 4순위 | Track 4 (날씨 재구성) | 기술 완성도 높음, 데모 임팩트는 상황 의존 |
