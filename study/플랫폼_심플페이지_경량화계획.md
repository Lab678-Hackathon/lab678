# KONNECT 플랫폼 심플 페이지·경량 코드화 계획

> 작성일: 2026-10-28  
> 목적: KONNECT를 다른 주제와 대회에 쉽게 재사용할 수 있도록 메뉴·페이지·코드 구조를 단순화하고, LLM이 빠르게 파악할 수 있는 경량 구조를 만든다.

## 1. 목표와 방향

KONNECT의 기존 기능을 없애는 것이 목표가 아니다. 현재의 추천·챗봇·RAG·루트·로그인 기능을 유지하면서, 사용자가 보는 진입점과 개발자가 읽는 코드 경계를 단순하게 만든다.

### 목표

- 첫 화면에서 사용자가 이해할 수 있는 메뉴를 5개 이하로 제한
- 실제 핵심 페이지를 4개로 정리
- `app.js`에서 도메인 로직·API 호출·상태 변경을 제거
- 주제 변경 시 콘텐츠 파일과 설정 파일만 우선 교체
- 각 기능을 1개 진입 파일과 1개 API 모듈로 추적 가능하게 구성
- LLM이 10분 안에 전체 흐름과 변경 지점을 파악할 수 있게 문서화
- 기존 API 계약·신뢰 불변식·테스트를 보존

### 프론트엔드 기술 결정

이번 해커톤에서는 팀의 React 경험이 없고 48시간 안에 안정적인 시연을 해야 하므로 **React를 도입하지 않는다**. 기존 Vanilla HTML/CSS/JavaScript와 ES Modules 구조를 유지하고, 파사드·라우팅·공통 컴포넌트로 복잡도를 줄인다.

- 새 프레임워크 학습·마이그레이션에 시간을 사용하지 않는다.
- JSX, React 상태관리, 별도 컴포넌트 런타임을 추가하지 않는다.
- 현재 동작하는 화면과 API 계약을 우선 보존한다.
- 남는 개발 시간은 Naito 연동, 당일 공개 주제 API, fallback, 발표 동선 검증에 사용한다.

### 비목표

- React/Vue 등 프론트엔드 프레임워크 도입 또는 마이그레이션
- 팀 합의와 검증 없이 Vite 등 새 빌드 도구 추가
- 백엔드 전체 재작성
- 기능을 무리하게 하나의 거대 파일로 합치기
- 기존의 미확인·근거·fallback 표시 제거
- API 키나 외부 서비스 설정을 코드에 하드코딩

## 2. 제안하는 사용자 메뉴

### 최종 메뉴

```text
Home
  ├─ Discover      지금 가능한 경험 추천
  ├─ Plan          대화형 루트·FAQ·후속 조건 수정
  ├─ Saved         선택한 경험·저장 루트
  └─ Account       로그인·선호·설정
```

### 메뉴별 책임

| 메뉴 | 핵심 역할 | 연결 기능 |
|---|---|---|
| **Home** | 서비스 소개·최근 선택·빠른 진입 | welcome, current choice |
| **Discover** | 조건 입력과 추천 결과 | A 추천, 지도, 선택 |
| **Plan** | 자연어 질문과 루트 계획 | 챗봇, RAG, B 루트 |
| **Saved** | 저장 결과 재접근 | 선택 상세, 저장 루트 |
| **Account** | 사용자 설정 | 로그인, 선호, 로그아웃 |

기존 `welcome`, `input`, `loading`, `results`, `choice`, `chat`, `route`, `mypage`, `onboarding`, `error`는 사용자에게 별도 메뉴로 노출하지 않고 위 메뉴 안의 상태 또는 하위 화면으로 취급한다.

## 3. 제안하는 심플 페이지 구조

### 3.1 4개 핵심 페이지

```text
pages/
├─ home.js        Home
├─ discover.js    Discover: 입력 → 로딩 → 결과 → 상세
├─ plan.js        Plan: FAQ·챗봇·루트
└─ account.js     Account: 로그인·온보딩·선호
```

### 3.2 상태는 페이지 내부 상태로 제한

페이지 전체를 갈아끼우는 현재 구조는 유지하되, 각 페이지가 다음 상태를 자체적으로 관리한다.

```text
Discover: idle → editing → loading → result → detail → error
Plan: idle → chatting → route_loading → route_result → error
Account: signed_out → sign_in → onboarding → preferences
Home: welcome → ready
```

페이지 간 공유가 필요한 값만 `state.js`에 둔다.

- 현재 로그인 사용자
- 현재 선택
- 마지막 추천 요청·결과
- 저장 루트 참조
- 현재 위치

폼 입력, 로딩 여부, 오류 문구, 챗봇 입력값은 전역 상태로 올리지 않는다.

## 4. 권장 디렉터리

### 4.1 단기 변경안 — 기존 파일을 보존하면서 진입점 단순화

기존 기능을 깨지 않기 위해 먼저 facade 파일을 추가한다.

```text
frontend/js/
├─ app.js                 # 부트스트랩·메뉴·페이지 전환만
├─ routes.js              # 메뉴 이름 → 페이지 함수 매핑
├─ content.js             # 서비스명·카피·메뉴·주제 콘텐츠
├─ api.js                 # HTTP 요청 공통 처리
├─ state.js               # 최소 공유 상태
├─ auth.js                # 인증 전용
├─ map.js                 # 지도 전용
├─ pages/
│  ├─ home.js
│  ├─ discover.js         # 기존 input/results/choice facade
│  ├─ plan.js             # 기존 chat/route facade
│  ├─ account.js          # 기존 onboarding/mypage facade
│  └─ error.js
└─ components/
   ├─ menu.js
   ├─ status-badge.js
   ├─ fact-list.js
   ├─ result-card.js
   ├─ route-card.js
   └─ sheet.js
```

기존 페이지와 컴포넌트는 한 번에 삭제하지 않는다. 새 facade가 안정화된 뒤 사용처가 없는 파일만 단계적으로 정리한다.

### 4.2 콘텐츠와 코드 분리

새 주제에 맞춰 자주 바꾸는 값은 `content.js` 또는 JSON으로 이동한다.

```js
export const CONTENT = {
  brand: {
    name: "KONNECT",
    tagline: "Seoul culture, made doable",
  },
  menu: {
    home: "Home",
    discover: "Discover",
    plan: "Plan",
    saved: "Saved",
    account: "Account",
  },
  copy: {
    aiNotice: "AI-assisted results · unconfirmed details marked",
    unavailable: "Some information needs confirmation.",
  },
};
```

콘텐츠 파일에는 API 호출, DOM 조작, 판정 로직을 넣지 않는다. 코드 파일에는 주제별 문구를 직접 흩어 쓰지 않는다.

## 5. LLM이 쉽게 읽는 코드 규칙

### 5.1 파일 책임 규칙

각 파일은 한 문장으로 설명할 수 있어야 한다.

| 파일 | 한 문장 책임 |
|---|---|
| `app.js` | 앱을 시작하고 현재 메뉴를 표시한다 |
| `routes.js` | 메뉴와 페이지 함수를 연결한다 |
| `api.js` | 백엔드 HTTP 요청을 보낸다 |
| `state.js` | 페이지 간 공유 상태만 저장한다 |
| `discover.js` | 추천 입력과 결과 흐름을 표시한다 |
| `plan.js` | 대화·FAQ·루트 흐름을 표시한다 |
| `account.js` | 로그인·선호 흐름을 표시한다 |
| `content.js` | 사용자에게 보이는 콘텐츠를 제공한다 |

### 5.2 함수 길이와 의존성

- 화면 렌더 함수는 80줄 이하를 목표로 한다.
- 이벤트 핸들러는 API 호출과 화면 렌더를 직접 섞지 않는다.
- 한 모듈의 import는 8개 이하를 목표로 한다.
- 순환 import를 금지한다.
- `app.js → routes.js → pages → api/state` 단방향 흐름을 유지한다.
- 페이지에서 `backend/app` 내부 개념이나 세부 모델을 직접 추측하지 않는다.

### 5.3 이름 규칙

- 메뉴는 `home`, `discover`, `plan`, `saved`, `account`로 고정한다.
- API 함수는 `getX`, `postX`, `putX`, `deleteX`로 시작한다.
- 화면 함수는 `renderXView` 또는 `showX` 중 하나만 선택해 통일한다.
- 상태값은 `idle`, `loading`, `success`, `empty`, `error`처럼 공통 상태명을 사용한다.
- 콘텐츠 키는 `CONTENT.brand`, `CONTENT.menu`, `CONTENT.copy`처럼 영역을 표시한다.

## 6. Naito API 준비

경량화 대상에서 Naito 연동을 완전히 제외할 필요는 없다. 다만 Naito를 추천 후보의 사실 판정이나 외부 데이터 조회 엔진으로 넣지 않고, **Plan 메뉴의 대화형 안내용 provider**로 제한한다. 이렇게 하면 대회에서 제공되는 토큰을 받았을 때 빠르게 연결하면서도 추천의 신뢰 판정과 기존 OpenAI/RAG 흐름을 흔들지 않는다.

### 6.1 준비할 범위

```text
Plan page
  → POST /api/plan/chat
  → plan service
  → LLM provider adapter
       ├─ naito provider
       └─ openai provider
```

- 백엔드에 `agent/providers/` 또는 `services/llm/` 중 하나의 작은 provider 경계를 둔다.
- `naito.py`는 인증 헤더·endpoint·model 전달과 응답 정규화만 담당한다.
- Naito의 실제 endpoint, 인증 방식, 모델명, 요청 형식은 주최 측 문서와 토큰 수령 후 확인한다. 확인 전에는 OpenAI 호환 API라고 단정하지 않는다.
- 프론트엔드는 Naito 토큰을 직접 사용하지 않고 기존 Plan API만 호출한다.
- 최초 구현은 스트리밍보다 일반 JSON 응답으로 시작해 데모 안정성을 우선한다.

### 6.2 환경설정과 전환

`.env`에는 값이 아니라 키 이름만 준비한다.

```dotenv
LLM_PROVIDER=openai
NAITO_BASE_URL=
NAITO_API_KEY=
NAITO_MODEL=
```

- `LLM_PROVIDER=naito`일 때만 Naito 설정을 읽는다.
- 빈 endpoint·토큰·모델은 성공 응답으로 대체하지 말고 명확한 설정 오류로 반환한다.
- 운영·배포 환경의 실제 토큰은 `.env` 또는 Secret에만 넣고 커밋하지 않는다.
- provider 전환은 서버 재시작 또는 배포 설정 변경으로 명시적으로 수행한다. 요청마다 임의로 번갈아 호출하지 않는다.
- Naito 장애 시 자동으로 사실을 만들어내지 않는다. Plan 채팅은 오류 안내 또는 명시적으로 설정된 OpenAI provider로만 fallback한다.

### 6.3 Naito의 역할 제한

Naito 채팅은 FAQ·여행 설명·다음 행동 제안처럼 대화형 안내에 사용한다. 다음 값은 Naito 응답에서 직접 받지 않는다.

- 가격, 운영시간, 예약 가능 여부
- 후보의 이용 가능 판정과 hard 제외 여부
- 좌표, 거리, 이동시간
- 공식 데이터의 사실 필드

이 값들은 기존 `sources/`와 `domain/`이 소유하고, Plan 화면에는 확인·미확인 상태를 그대로 표시한다. Naito가 사실을 생성하거나 추천 결과를 덮어쓰지 못하도록 provider 출력은 `message`와 선택적 `citations` 정도로 제한한다.

### 6.4 준비 완료 기준

- [ ] Naito endpoint·인증·모델 계약을 주최 측 문서로 확인했다.
- [ ] `LLM_PROVIDER`가 `openai`와 `naito` 중 하나를 명시적으로 선택한다.
- [ ] Naito 토큰이 프론트 코드·로그·에러 화면에 노출되지 않는다.
- [ ] Naito 미설정·timeout·4xx/5xx가 사용자에게 오류 상태로 표시된다.
- [ ] Naito 채팅 실패가 Discover 추천과 사실 판정을 중단시키지 않는다.
- [ ] `naito`와 `openai`가 같은 내부 Plan 응답 형식으로 변환된다.
- [ ] Naito 응답으로 가격·운영·예약·좌표가 생성되지 않는다.
- [ ] 실제 토큰 없이 adapter 단위 테스트와 mock 응답 테스트가 실행된다.

## 7. 백엔드 경량화 계획

프론트 메뉴를 단순화해도 백엔드 판정 로직은 정확성을 위해 유지한다. 백엔드는 파일 수를 무조건 줄이지 않고, LLM이 읽을 진입점을 만든다.

### 7.1 기능별 facade

```text
backend/app/
├─ main.py
├─ config.py
├─ api/
│  ├─ discover.py    # 추천 API 진입점
│  ├─ plan.py        # 챗봇·루트·FAQ 진입점
│  ├─ account.py     # 세션·선호·인증 진입점
│  └─ health.py
├─ contracts/
│  ├─ discover.py
│  ├─ plan.py
│  └─ common.py
├─ services/
│  ├─ discover.py
│  ├─ plan.py
│  └─ account.py
├─ domain/           # 결정론 판정 유지
├─ sources/          # 외부 API 유지
└─ agent/            # LLM 파이프라인 유지
```

기존 `api/recommend.py`, `api/route.py`, `api/chat.py`, `api/ask.py`를 즉시 삭제하지 않는다. `services/`가 기존 함수를 감싸는 facade가 된 후 새 라우터에서 사용한다.

### 7.2 백엔드 단순화 원칙

- Router는 입력 검증·인증·서비스 호출·Envelope 반환만 담당한다.
- `services/`는 흐름 조합만 담당한다.
- `domain/`은 외부 I/O와 LLM 호출을 하지 않는 순수 판정만 담당한다.
- `sources/`는 HTTP 호출·timeout·retry만 담당한다.
- `agent/`는 구조화·라우팅·설명만 담당한다.
- 사실 필드는 LLM 응답에서 직접 가져오지 않는다.

## 7. 단계별 실행 계획

### Phase 1 — 메뉴와 콘텐츠 정의

- `CONTENT` 구조를 먼저 정의한다.
- 5개 메뉴와 각 메뉴의 성공 상태를 확정한다.
- 기존 화면과 새 메뉴의 매핑표를 만든다.
- 코드 이동 없이 `routes.js`와 facade부터 추가한다.

완료 기준:

- 홈에서 5개 메뉴가 보인다.
- 각 메뉴가 기존 기능으로 연결된다.
- 기존 URL·API 계약은 변경되지 않는다.

### Phase 2 — Discover/Plan/Account facade

- `discover.js`가 input → results → choice를 연결한다.
- `plan.js`가 chat → FAQ/route를 연결한다.
- `account.js`가 login → onboarding → mypage를 연결한다.
- 기존 페이지 파일은 내부 구현으로 남겨 둔다.
- Plan API 뒤에 provider adapter를 두고, 실제 Naito 계약 확인 전에는 mock으로 검증한다.

완료 기준:

- 기존 A/B/FAQ/로그인 시나리오가 동일하게 동작한다.
- 페이지 전환 규칙이 `routes.js` 한 곳에서 보인다.
- `app.js`에 도메인별 이벤트 코드가 남지 않는다.

### Phase 3 — 코드 경계 정리

- 공유 상태를 5개 항목으로 줄인다.
- 중복 API 호출·오류 처리·로딩 처리를 `api.js`와 공통 helper로 이동한다.
- 콘텐츠 문자열을 `content.js`로 이동한다.
- Naito/OpenAI 선택과 공통 응답 정규화를 Plan service 안에 둔다.
- 사용처 없는 import와 기존 facade 중복 코드를 정리한다.

완료 기준:

- 새 주제 적용 시 우선 수정할 파일이 `content.js`, RAG 문서, 환경설정으로 좁혀진다.
- 순환 import가 없다.
- 기존 테스트와 브라우저 smoke test가 통과한다.

### Phase 4 — LLM용 인덱스와 검증

`study/`에 다음 문서를 추가하거나 기존 문서를 갱신한다.

```text
frontend/README.md       # 메뉴·페이지·상태·수정 지점
backend/README.md        # API·서비스·domain·sources 경계
docs/content-map.md      # 콘텐츠 파일과 사용자 노출 위치
docs/feature-map.md      # 기능 → 진입점 → 테스트
```

각 문서는 긴 설명 대신 다음 형식을 사용한다.

```text
목적:
진입점:
입력:
출력:
호출 파일:
수정할 때 함께 볼 파일:
검증 명령:
```

## 9. LLM 작업용 최소 진입 문서

LLM이 기능을 수정할 때 다음 순서만 읽으면 되도록 한다.

1. `frontend/README.md` 또는 `backend/README.md`
2. 해당 메뉴의 page facade
3. `api.js` 또는 backend `services/`
4. provider adapter가 있으면 `services/llm/` 또는 `agent/providers/`
5. 관련 `domain/` 또는 `sources/`
6. 해당 테스트

LLM에게 작업을 요청할 때는 다음 형태를 사용한다.

```text
목표: Discover 결과 카드에 새 상태 배지를 추가한다.
읽을 파일: frontend/README.md, frontend/js/pages/discover.js,
           frontend/js/components/status-badge.js,
           frontend/js/content.js
수정 범위: 위 파일과 관련 테스트만
보존 조건: API 계약, 미확인 표시, 기존 상태 3종
검증: pytest 또는 브라우저 smoke test
```

## 10. 가벼운 운영·성능 기준

- 첫 화면은 인증·추천 API가 늦어도 메뉴와 기본 Home을 먼저 표시한다.
- 기능별 API는 필요한 시점에만 호출한다.
- Plan·Account를 열지 않았으면 해당 기능의 데이터를 조회하지 않는다.
- 실패한 선택 기능 때문에 전체 페이지를 실패시키지 않는다.
- 이미 있는 외부 API 캐시 금지 정책을 임의로 바꾸지 않는다.
- 프론트 번들러를 도입하지 않고 ES Modules를 유지한다.
- 콘텐츠 교체만으로 배포할 수 있도록 환경변수와 문구를 코드에서 분리한다.
- Naito 채팅은 Plan 진입 시에만 provider를 초기화하고, Home·Discover의 첫 화면 로딩을 막지 않는다.
- provider timeout은 짧게 제한하고, 실패 시 성공처럼 보이는 빈 답변을 반환하지 않는다.

## 11. 위험과 대응

| 위험 | 대응 |
|---|---|
| facade가 기존 로직을 중복 구현 | facade는 연결만 하고 판정·API 호출을 복제하지 않음 |
| 메뉴 단순화로 기능 접근성이 떨어짐 | Saved·Account에서 기존 선택·선호 기능으로 연결 |
| LLM이 문서만 보고 잘못 수정 | README에 보존 조건·테스트·파일 경계를 명시 |
| 콘텐츠 교체 중 사실 판정이 바뀜 | 콘텐츠와 `domain/` 판정 코드를 분리 |
| 기존 기능 회귀 | Phase마다 A/B/FAQ/Auth smoke test 실행 |
| 단순화를 이유로 신뢰 표시 제거 | AI 고지·Fact·Unconfirmed·fallback을 필수 UI로 유지 |
| Naito API 계약이 예상과 다름 | endpoint·인증·모델을 사전 확정하고 adapter 내부에서만 흡수 |
| Naito 장애가 전체 데모를 중단 | Plan 채팅만 오류 처리하고 Discover 추천은 독립 유지 |
| 토큰이 프론트나 로그에 노출 | 서버 전용 Secret과 민감정보 마스킹 사용 |

## 12. 완료 기준

- [ ] Home/Discover/Plan/Saved/Account 5개 메뉴가 동작한다.
- [ ] 프론트엔드는 Vanilla HTML/CSS/JavaScript와 ES Modules를 유지한다.
- [ ] React 또는 JSX 의존성이 추가되지 않는다.
- [ ] 핵심 페이지가 Home/Discover/Plan/Account 4개 facade로 정리된다.
- [ ] `app.js`는 부트스트랩과 라우팅만 담당한다.
- [ ] 주제 콘텐츠는 `content.js`와 RAG 문서에서 교체할 수 있다.
- [ ] 기존 A 추천·B 루트·FAQ·로그인 기능이 유지된다.
- [ ] Plan 채팅은 Naito/OpenAI provider를 설정으로 선택할 수 있다.
- [ ] Naito API가 없어도 mock provider로 전체 UI를 검증할 수 있다.
- [ ] API 계약과 신뢰 불변식이 유지된다.
- [ ] 기존 페이지는 facade 안정화 전까지 삭제하지 않는다.
- [ ] `frontend/README.md`, `backend/README.md`, feature map이 있다.
- [ ] LLM 작업 요청에 읽을 파일·수정 범위·보존 조건·검증 방법을 지정할 수 있다.
- [ ] 전체 테스트와 핵심 브라우저 smoke test가 통과한다.

## 13. 최종 제안

KONNECT를 가볍게 만드는 가장 안전한 방법은 기능을 삭제하거나 백엔드를 전부 다시 만드는 것이 아니다.

1. **사용자 화면은 5개 메뉴로 단순화한다.**
2. **페이지 진입점은 4개 facade로 줄인다.**
3. **React를 도입하지 않고 Vanilla JS를 유지한다.**
4. **`app.js`는 라우팅만 담당하게 한다.**
5. **콘텐츠는 `content.js`와 RAG 문서로 이동한다.**
6. **Naito는 Plan 채팅 전용의 얇은 provider로 준비한다.**
7. **기존 기능과 신뢰 판정 코드는 그대로 재사용한다.**
8. **LLM은 README → facade → API/service → provider → domain/source → test 순서로 읽는다.**

이 방식이면 현재 KONNECT의 기능과 검증 자산을 잃지 않으면서도, 새 대회 주제에 맞는 콘텐츠를 빠르게 교체하고 LLM이 수정 범위를 쉽게 파악할 수 있다.
