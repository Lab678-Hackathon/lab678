## 3. 브랜치 · PR · Merge 운영 — 10/29 추가 합의

**[합의] 기본 흐름**

`최신 develop에서 개인 브랜치 생성 → 개발·최소 테스트 → Commit / Push → develop 대상 PR → Discord 공유 → 본인 Merge 가능 → develop에서 통합 → develop → main PR → 손희영님 최종 승인 → 배포`

| 변경 유형 | PR | 병합·확인 기준 |
|---|---|---|
| **개인 담당 기능 → `develop`** | **필수** | 본인 기능의 최소 정상 동작을 확인한 후 **셀프 Merge 가능** |
| **공통 설정·공통 기능 또는 타 팀원 담당 영역 수정** | **필수** | 변경 전에 **관련 팀원에게 공유·확인** 후 반영 |
| **`develop` → `main`** | **필수** | 주요 기능·빌드·기존 기능 영향 확인 후 **손희영님 최종 승인** |
| **긴급 버그 수정** | **가급적 PR** | Discord 공유 후 빠르게 처리. `main` 최종 승인 원칙의 예외 여부는 따로 결정된 바 없음 |

- **`develop` [합의]:** 공동 통합·디버깅 브랜치. **팀원 자율 Merge 허용**. 다만 기본 브랜치로 전환했는지, 실제 GitHub 설정이 적용됐는지는 별도 확인한다.
- **`main` [합의]:** 시연·자동 배포의 기준 브랜치로 운용한다. **손희영님이 최종 승인**한다. 실제 배포 연결 및 다른 팀원의 직접 Push·Merge 제한 여부는 별도 검증한다.
- **개인 브랜치 [합의]:** 새로운 기능의 브랜치는 **최신 `develop`을 기준으로 생성**한다. 이름은 `feature/<설명>`, `fix/<설명>`과 같이 이해하기 쉽게 사용한다(이름 형식은 권장).
- **PR [합의]:** 담당 기능도 반드시 PR을 거치며, 공식 **Approve는 필수 아님**. 팀원 간 상호 리뷰도 의무가 아니다. **PR을 올리면 Discord에 한 줄과 링크**를 남긴다.
- **셀프 Merge 조건 [합의]:** 코드 생성이나 커밋만으로 완료 처리하지 않는다. 본인 기능이 실제로 정상 동작하는지 확인하고, 변경 파일·영향 범위·테스트 결과·남은 문제를 확인한다.
- **공통·타 담당 영역 [합의]:** API 계약, 공통 컴포넌트, 환경·배포 설정, DB 스키마, 다른 담당자 화면·기능에 영향을 주는 작업은 변경 **전에** 관련 팀원에게 확인받는다. 단순 개인 담당 기능은 불필요한 대기 없이 진행한다.
- **손희영님 본인 PR [기존 합의]:** 본인 PR은 직접 Merge할 수 있으며, 기능·API 변경은 사전에 공유한다.

**기본 용어:** Commit = 변경 기록 저장 · Push = GitHub에 업로드 · PR = 합쳐 달라는 요청 · Merge = 실제로 합침 · Approve = GitHub 공식 승인(이번 팀은 필수 조건 아님).

> **설정 주의:** 팀의 '희영님 `main` 최종 승인' 합의와 GitHub의 실제 권한 제한은 별개다. `main` 보호 규칙이 실제로 의도대로 작동하는지 확인해야 한다. `develop`을 강하게 보호하거나 별도 Approve를 의무화한다는 합의는 없다.

## 4. 코드 동기화 및 Discord 알림

### 정기 동기화 — [합의]

- **하루 2~3회 정도를 권장**한다. 구체적인 시각은 정하지 않고 그날 개발 흐름에 맞춰 유연하게 운영한다. *(김동조님 10:55 제안, 손희영님 11:28 동의)*
- **작업 종료 전에는 서로의 최신 Merge 상황을 확인하고 가능하면 동기화**한다. 특정 시각의 일괄 동기화나 전원 작업 중단을 강제하지 않는다.
- 정해진 동기화 시점 외에도 **필요한 PR Merge·긴급 수정은 진행 가능**하다. 각자 본인 기능의 최소 정상 동작 확인과 관련 팀원 사전 공유 원칙은 유지한다.
- **동기화 시간과 PR Merge 권한은 다른 문제**다. 개인 기능의 `develop` 셀프 Merge는 계속 허용한다.

### 안전한 수동 동기화 — 팀원 행동 기준

- **[권장]** 작업 시작 전, 동기화 권장 시점, 다른 팀원의 Merge 소식을 확인한 뒤 최신 `develop` 변경사항을 자신의 작업 브랜치에 적절히 반영한다.
- **중요:** `git pull origin develop`은 **현재 체크아웃한 브랜치에** `develop` 내용을 가져와 병합할 수 있다. 아무 브랜치에서나 무작정 실행하지 않는다. 먼저 `git status`로 미저장·미커밋 변경을 확인하고, 자신의 작업 브랜치와 합치는 방법을 확인한다.
- **참고 예시:** `git switch develop` → `git pull --ff-only origin develop`로 로컬 `develop`을 갱신한 다음, 자신의 작업 브랜치로 돌아와 필요한 방식으로 최신 변경사항을 반영한다. 충돌이 나면 담당자와 상의한다. *(Git 명령은 상황에 따라 달라지므로 무조건 실행하는 의무 절차가 아님.)*

### GitHub Actions + Discord Webhook — [선택 제안, 미적용]

- **김동조님 제안(10/29 10:49):** `develop`·`main` PR Merge 시 Discord에 동기화 알림을 자동 전달하는 방안이다. **손희영님은 김동조님이 맡는 방법을 제안했으나, 담당 수락·설치 일정은 아직 미확정**이다. 해커톤 기획·구현 시간을 우선하며, 설정에 시간이 오래 걸리면 도입하지 않아도 된다.
- **필요 작업:** 알림을 받을 Discord 채널의 Webhook 생성 → 저장소의 **Settings → Secrets and variables → Actions**에 `DISCORD_WEBHOOK` 등록 → YAML 문법·실행 이벤트·메시지 검증 → 워크플로 등록 → 실제 병합 이벤트 테스트.
- **검증 주의:** 공유된 YAML은 Discord 메시지에서 들여쓰기와 코드 블록이 깨진 부분이 있어 **그대로 사용하지 않는다.** 또한 `on: push`는 PR Merge가 아닌 일반 Push에도 실행될 수 있으므로, **PR Merge만 알릴지 모든 변경 Push를 알릴지 먼저 정하고 트리거를 맞춰야 한다.**
- **보안:** Webhook URL을 MD·YAML·Discord 공개 메시지에 직접 쓰지 않고 GitHub Actions Secret으로 관리한다. 알림에 민감정보·긴 로그를 포함하지 않는다.
- **운영:** 이 자동 알림은 **새 저장소를 만들면 별도 이전·재설정**해야 한다. 실제로 자동화가 구성되고 테스트되기 전까지는 기존 Discord PR 공유 규칙을 유지한다.

## 5. AI 코딩 도구 공통 규칙 — [합의], 간결하게 운영

**작업 시작 전**
1. `TEAM_WORKFLOW.md`, 확정된 PRD·화면 명세·관련 Figma·API 명세를 확인한다. AI가 자동으로 읽었다고 추정하지 않는다.
2. 작업 브랜치·담당 기능·수정 범위를 확인한다. 겹칠 우려가 있는 공통 영역은 사전에 공유한다.
3. **다른 팀원 담당 파일·공통 설정·공유 API 계약에 영향**이 있으면 **수정 전에 Discord로 관련 팀원에게 공유·확인**한다. *(10/29 합의)*

**AI에 허용할 변경 범위**
- 요청한 기능과 필요한 파일만 수정한다. 무관한 리팩터링, 대량 삭제, 공통 인터페이스·의존성 변경은 사전 협의한다.
- AI에게 권한·역할이 확인되지 않은 `main` 직접 Push·최종 Merge·실서비스 배포를 임의 실행시키지 않는다. 실제 비밀값을 코드·로그·PR에 포함하지 않는다.

**작업 완료·PR 보고**
- **수정 파일 / 구현 내용 / 실제 실행한 테스트와 결과 / 남은 오류·영향 / PR 링크**를 간단히 남긴다.
- 테스트하지 않은 항목에 **PASS**를 쓰지 않는다. 개인 담당 기능은 최소 정상 동작 테스트 후 `develop`에 Merge한다.

**AI별 지침 연결 [방향 합의 · 적용 예정]**
- **공통 규칙의 기준 문서는 `TEAM_WORKFLOW.md` 하나로 둔다.** AI별 지침 파일에 규칙을 중복 작성하지 않고 공통 문서를 짧게 참조하도록 한다. *(손희영님 11:28 동의)*
- `AGENTS.md`(Codex), `CLAUDE.md`(Claude Code), `GEMINI.md`(Gemini/Antigravity)에서 공통 문서 참조를 안내하고, 각 도구가 실제로 읽는지 확인한다. **문서 작성과 AI 도구별 실제 적용·검증은 별개다.**
- 해커톤 동안은 **작업 범위·사전 공유·기능 테스트·비밀값 보호·PR 안내**처럼 꼭 필요한 규칙 위주로 유지한다.
