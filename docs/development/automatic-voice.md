# 자동 음성 대화·종료 설정

2026-10-31 사용자 요청: 버튼을 계속 누르지 않고 몇 차례 대화, 설정 메뉴에서 최대횟수, 몇초 무응답이면 자동종료. 개인 backend 모듈과 팀 통합 복사본 적용. 팀 원본 브랜치/공용plan은 변경하지 않았다.

## 사용 방법

Chrome에서 http://127.0.0.1:5175/?#/home 를 열고 새로고침한다. **‘자동 음성 대화 시작’**을 한 번 누르면 AI가 먼저 질문하고, 낭독이 끝나면 답변을 듣는다. 필요하면 ‘음성 대화 설정’에서 최대횟수와 무응답 시간을 정한다. 설정값은 현재 브라우저 세션에 저장되며 새로고침 후 마이크가 자동 시작되지는 않는다.

기존8765에 ‘한 번 말하기’만 보이면 다른 점검 화면이다. 로컬8765를 새로고침하면 상단 ‘마이크 · 자동 대화 화면 열기’로 최신5175홈에 이동할 수 있다. 이 바로가기는 같은PC에서만 보이고 공개배포에는 표시하지 않는다. `node utils/scripts/check_voice_entry.cjs`로 기존화면→최신홈→마이크표시/초기꺼짐을 확인했다.

### 마이크 버튼 켜기·끄기 (10/31 추가)

마이크 아이콘이 있는 같은 버튼을 다시 눌러 자동 대화를 끈다. 꺼짐은 흰색 버튼/사선 마이크/‘자동 대화 꺼짐’, 켜짐은 녹색 버튼/마이크/‘자동 대화 켜짐’이다. 듣기·AI 처리·답변 읽기 단계도 표시한다. 자동 대화가 켜져 있어도 TTS/AI 처리 중 마이크로 녹음하지 않으며 다음 듣기에서만 녹음한다.

버튼은 끈 뒤에도 다시 켤 수 있다. 켜진 상태에서는 처리·읽기 중에도 잠그지 않아 즉시 중지할 수 있고, 마이크/낭독/요청을 취소한다. 수동 텍스트 AI 요청 도중 마이크를 누르면 이전 요청을 취소하고 음성 대화를 시작한다. `aria-pressed`·접근성 이름·상태 설명을 함께 갱신한다. 페이지 로드만으로 시작하지 않는다.

최신 실행 패키지는 `.local/chat-handoff-6accf0e-063bdde13b/` (프론트6accf0e, 8파일)이다. 로컬에서는 팀 API와 동일하게 같은 주소의 프록시를 사용한다. 배포 주소가 meta에 있어도 로컬 대화가 그 주소로 새지 않도록 검사했다. 아래 이전 패키지는 작업 이력이다.

### 듣는 중 파동과 기기 호환 보완

최신은 `.local/chat-handoff-6accf0e-026a06b9ea/` 8파일, 로컬5175다. 음성 엔진 연결 대기는 노란 안내만 표시한다. `audiostart`/발화 시작 후 실제 듣기에서 마이크 주위에 두 원이 퍼지고, audio 종료·읽기·AI 처리·중지에서는 파동을 정지한다. 시스템 움직임 줄이기에서는 정적 원/상태 글자를 쓴다. 파동은 음량/음성 신호의 그래프가 아니다.

미지원 안내는 특정브라우저 강제 대신 텍스트/키보드받아쓰기로 대화를 이어가도록 수정했다. 접두어 API·미지원 텍스트 복귀도 모의 검사한다. 실제 MacBook/iOS/Android는 아직 검증하지 않았으며 [기기별 확인 범위](voice-browser-compatibility.md)를 따른다. 공개 홈페이지는 기존6accf0e이므로 파동·자동대화 패치의 팀 통합/재배포가 필요하다.

- 최대 대화: 기본5회, 1~10회. 사용자 최종 전사와 AI 응답을 합쳐1회. 재시작하면 횟수를 새로 센다.
- 무응답: 기본15초, 5~60초. 듣는 단계에서만 측정한다. AI 처리·답변 낭독 동안에는 무응답 시간을 세지 않는다.
- 순서: 첫 질문 읽기 → 듣기 → 최종 전사1회 전송 → AI 해석·조건 갱신 → 답변 읽기 → 다음 듣기. 첫 안내는 대화 횟수에 넣지 않는다. 읽기 완료 이벤트를 기다리므로 듣기/읽기를 겹치지 않는다.
- 브라우저가 no-speech로 조기 종료하면 동일 무응답 타이머 안에서만 재시작한다. 네트워크·권한 오류는 재시도하지 않고 종료한다.
- 발화를 시작하면 무응답 시계를 멈추고 발화 끝부터 다시 센다. 인식되지 않는 긴 발화는 첫 speechstart 이후60초 상한으로 종료한다. 답변 낭독 역시60초 상한이다.

## 종료와 확인

횟수 도달·무응답·중지 버튼/발화·직접 입력 수정·수동 화면 이동·탭 숨김·인식/API/TTS 오류에서 종료한다. 음성 명령으로 이동할 때는 같은 대화를 이어간다. 종료하면 타이머·마이크·낭독·진행 중 AI 요청을 취소하고 늦은 결과로 재개하지 않는다. 기존 입력/대화·변경 확인은 유지한다.

조건이 준비되면 최대횟수 전이라도 멈추고 S02a 최종 확인을 기다린다. 출발지 좌표 선택/확정 조건 변경 확인에서도 멈춘다. 음성 대화를 다시 시작해 ‘변경 모두 반영’ 또는 ‘기존 조건 유지’로 명시적 결정을 전달할 수 있다. 조건 준비만으로 추천 API를 호출하지 않는다.

## 공통 화면 조작 — 사용자 추가 요구

PRD/화면명세는 S02 대화와 결과→조건 복귀를 규정한다. 10/31 사용자가 추가한 화면별 음성 조작은 이 문서에 따로 기록하며 공용 기획은 변경하지 않는다. 홈·조건·추천·상세·내 정보에 **같은 패널 하나**를 옮겨 쓴다. 내 정보 화면은 기존 준비 화면이며 저장/로그인을 완성하지 않았다.

- ‘음악을 듣고 싶어요’: S02로 이동하고 기존 AI 조건 해석 API에서 후속 질문.
- ‘두 번째 장소 자세히 보여줘’: 현재 추천 순서의 실제 후보 ID로 S04 이동.
- ‘이 장소 읽어줘’/‘이 장소 선택’: 현재 상세 후보의 사실 필드 낭독/선택. 미확인은 그대로 안내.
- ‘추천 목록 보여줘’, ‘조건 바꿔’, ‘홈으로 가줘’, ‘뒤로’: 허용된 화면으로 이동하며 음성 대화 유지.
- ‘대화 중지’: 낭독 후 세션 종료. 즉시 중지는 화면 중지 버튼.
- S05 코스·길찾기 화면은 팀 UI에 미연결이므로 준비 중 안내. 모든 HTTP 엔드포인트를 음성으로 직접 실행하는 구조는 아니다.

단순 조작은 제한된 문구를 코드로 해석한다. 임의 URL/후보/노선을 LLM이 만들지 않으며 복합 화면 명령의 범용 해석은 아직 지원하지 않는다.

음성 대화 중에는 AI 답변을 자동으로 읽는다. 별도 ‘텍스트 대화 답변도 읽기’ 체크는 키보드로 보낸 대화의 낭독 옵션이다. 실제음성은 브라우저 SpeechRecognition/speechSynthesis이며 Naito 음성API를 호출하지 않는다.

## 구현과 인계

- backend/voice_session.js: 제한된 음성 세션·인식·낭독·취소 이벤트 정리.
- backend/team_chat.js: 최대횟수/무응답 설정·시작/중지·API신호 연결, 이전조건/응답보호 유지.
- backend/team_voice_actions.js: 화면 맥락·첫 질문·제한된 이동/후보 조작 명령·사실 필드 낭독.
- 최신 패키지8파일: `.local/chat-handoff-164cd40-01e552cba6/team-chat-handoff.zip`. 기존7파일에 `frontend/js/dj-voice-actions.js` 추가. 5175의 실제파일 통합본과5174 동적복사본에서 사용한다.
- 기존 개인 점검 화면8765는 단발성 음성 분류 화면이다. 자동 대화 확인 주소는5175다.

## 검증과 한계

`node utils/scripts/check_voice_session.cjs`는 Chrome의 모의 음성인식/TTS/AI로 자동반복·최대횟수·침묵·읽기중 무응답 제외·늦은응답차단·네트워크/API실패·조건준비·화면이동·설정복원을 검사한다. `--live`는 마지막1회만 실제 Naito를 쓰며 마이크/스피커는 여전히 모의다. 실제 Chrome 마이크/스피커의 자동 왕복은 사용자 실기기 확인 전이다.

검증 결과는 qa-voice-session/ 아래에 보관한다. API실패를 모의데이터로 대체하거나 동작하지 않은 실제 마이크를 PASS로 표시하지 않는다.

추가 `check_voice_navigation.cjs`는 홈 시작→AI 첫 질문→2턴→S02 자동 이동, 추천→두 번째 상세→읽기→선택→목록→조건 5턴, 없는 후보/미연결 경로, 수동 선택/이동/중지, 변경 동의와 새로고침 보존을 검사한다. `--live`는 홈의 음악 요청 1회만 실제 Naito이며 음성 장치는 모의다. 실패 원인은 페이지 종료/세션 시작 시 변경 동의가 지워지는 것으로 확인해 해당 취소에서 pending을 보존했다.

## 배포 상태 정정

사용자가 희영님은 Vercel 인증을 마쳤고 Render 승인은 이제 진행한다고 알려줬다. 이는 사용자 보고이며 콘솔 실검증은 별도다. 역할은 Vercel=팀 프론트, Render=백엔드/API. 에이전트의 Vercel 직접 배포는 아직 수행하지 않았다.
