사용자 정정: 설정 화면이 불편하며, 음성 인식과 자연어 분석으로 요구에 최대한 맞는 결과를 제시해야 한다. 단순히 입력칸을 자동으로 채우는 것만으로는 부족하다. **최신 PRD도 선택·결정 부담을 줄이는 대화와 조건 해석을 핵심으로 정의한다.** 공식 행사 주제 문구를 새로 확인한 것은 아니다.

## 검토 방법과 결론

기존 분석의 README·함수 역색인·특이점 문서를 먼저 읽고, 해당 함수의 실제 코드와 현재 PRD/코드를 대조했다. 이전 서비스의 실서버·키·추천 품질을 실행 검증하지 않았다. 아래는 코드에서 확인한 기능이며 실제 모든 요구 충족 보장은 아니다.

현재 구현은 **기본 입력 자동화** 중심이다. 이전 구현은 **자연어 선호 → 검색 후보 구성 → 제외/예산 판단 → 정렬 → 대화로 재추천**까지 연결한다. 경량화 과정에서 중요한 추천 기능까지 축소됐다. 기존 검색을 기본으로 두고 AI를 선택적 입력 도움으로만 보자는 직전 제안은 사용자 방향과 PRD의 핵심 경험을 충분히 반영하지 못했다.

## 핵심 코드 근거

원본 커밋의 아래 파일/함수를 읽었다. 경로는 기존 소스의 위치이며 새로 이식했다는 뜻이 아니다.

- `backend/app/agent/note_parser.py: parse_note`: 자연어 요구를 ParsedConditions로 추출. 무료/저렴함·제외·이미 방문·걷기 등을 구분. 실패 시 빈 조건으로 돌아가는 정책은 새 서비스에 그대로 채택하면 안 된다.
- `backend/app/models/recommend.py: ParsedConditions`: interests, avoid_interests, exclude_concepts, exclude_places, open_preferences, keywords, budget_krw, free_only, indoor_outdoor, indoor_outdoor_strict, prefer_shorter_walks, unsupported 등.
- `backend/app/agent/chat_agent.py: dispatch_tool/run_chat`: 추천/코스/질문 도구 선택, 위치·시간 맥락 부족 시 질문, 이전 조건을 이어받아 같은 도구를 다시 실행하도록 프롬프트 구성.
- `backend/app/agent/agent_loop.py: run_chat_loop/_present`: 최대6단계 도구 실행, 코드 결과에서 카드 렌더, 추천0건일 때 근거 없는 장소 설명을 막는 분기. 루프가 있는 것과 품질 검증 완료는 다르다.
- `backend/app/agent/orchestrator.py: base_radius/recommend_a/_rerank_and_judge`: 걷기 선호로 초기 검색 반경, 저장 선호보다 이번 요구 우선, 키워드 후보 추가, 관심사/의미 유사도/실내외/거리로 선발, 공식 텍스트 분류와 제외.
- `backend/app/agent/semantic_rank.py: build_intent_text/semantic_similarities`: 긍정 요구만 의미 비교에 사용. 싫다는 표현을 좋아하는 신호로 섞지 않도록 제외 요구는 별도 처리.
- `backend/app/domain/ranking.py: display_sort_key`: 실제 구현은 상태등급 → 만족조건 수 → 관심사/실내외/분위기/날씨, 같은 키 안에서 거리순 유지. 파일 앞부분의 과거 주석보다 함수 구현을 기준으로 판단했다.
- `backend/app/domain/budget.py: judge_budget`: 무료·유료·미확인과 예산 판정.
- `backend/app/domain/exclusion.py: select_with_exclusion`: 전부 제외되면 후보를 되살리고 안내하는 기존 정책 확인.
- `frontend/js/pages/chat.js`: 대화 내 결과 카드/코스, 맥락 전달, 실제 사용 시간창을 칩과 동기화. 현재 위치·지금~4시간 초기값도 있어 완전히 무설정/무가정은 아니다.

현재 비교 대상: `backend/naito_chat.py`, `chat_conditions.py`, `team_chat.js`, `outing.py`, `course.py` 및 최신 PRD의 서비스 정의·F04~F06·Hard/Soft 규칙.

## 그대로 가져오지 않을 부분

1. **제외 조건 자동 완화:** 이전 select_with_exclusion은 후보가 모두 없어지면 배제를 풀 수 있다. 새 PRD의 명시적 필수 제한은 유지한다. 조건을 풀어야 한다면 먼저 선택 가능한 대안과 변경점을 설명하고 동의받는다.
2. **걷기 반경=보행 제한 충족:** 반경은 실제 보행거리/시간·계단·접근성 보장이 아니다. 기존1/2/3km 값을 새 서비스 기본 정책으로 임의 확정하지 않는다.
3. **모호한 비용을 임의 확정:** 이전 코드는 “저렴하게”를 체험당3만원으로 취급한다. 이번 서비스에서는 기획 합의 없이 같은 숫자를 채택하지 않는다.
4. **확정값 자동 덮어쓰기:** 이전 발화 우선 처리와 달리 새 PRD의 확인값 충돌 동의는 유지한다. 다만 모든 기본/초안 값을 확인값으로 간주해 계속 동의를 요구하는 현재 연결 모듈은 개선 대상이다.
5. **복잡한 도구 루프/인증/DB/임베딩 전체 복제:** 사용자 가치에 필요한 조건 구조와 판정·재추천부터 선택적으로 재사용한다. 한 번의 해석 후 코드 추천, 필요할 때만 결과 설명을 호출하는 경량 방식도 가능하다.

## 다음 구현 방향 — 제안, 아직 미실행

사용자가 “청량리에서 오늘 오후 두 시부터 다섯 시까지, 국악이나 전시 보고 싶고 많이 걷기는 싫어요. 만 원 안쪽이면 좋겠어요”라고 말하면:

1. 국악/전시·시간·출발지·예산·걷기 선호를 한 번에 구조화한다.
2. 좌표 선택 등 반드시 필요한 정보와 중요한 모호함만 확인한다. “적게 걷기”가 절대 제한인지 모호하면 짧게 질문한다.
3. 공식 후보를 충분히 조회하고 실제 비용·운영/참여 시간·이동 근거로 판정한다. 미확인은 충족으로 바꾸지 않는다.
4. 2~3개 후보/대안과 적합 이유·미확인·차이를 제시한다. 이 숫자는 설명용 제안이며 공통 화면 계약 확정은 아니다.
5. “두 번째는 멀어요”라고 하면 기존 맥락과 장소 ID를 유지해 다시 계산하고, 필수 조건을 바꿔야 할 때만 동의를 받는다.

결론: 음성 버튼 추가보다 **자연어 요구가 후보를 바꾸도록 연결하는 것**이 우선이다. 상세 작업 계획은 개인 plan_dj에 기록하며 공용 기획/팀 화면은 이번 비교 작업에서 변경하지 않는다.
