## 우선 보완해야 할 구체 차이

1. **출발 위치:** `init`에서 예시 청량리 좌표를 채우고, 위치 권한 거부 시 기존 출발지를 유지한다. 이름 수정 시 좌표를 지우는 보호는 있다. 그러나 장소명 검색/확정이 없어 명세의 수동 장소 선택을 충족하지 못한다. 예시를 실제 확정 위치로 오인하지 않도록 확인 상태를 구분해야 한다.
2. **AI 대화:** `applyNote`는 분류 키워드와 두 곳 코스 의도 처리다. 출발지·시각 추출, 모호함 질문, Hard/Soft 해석, 대화 Draft/Confirmed는 미구현. STT/TTS 성공과 별개다.
3. **시간:** `validate`는 같은 날/종료>시작을 검증한다. 과거 시각 금지와 30/60분 최소시간은 현재 강제하지 않는다. 어느 경계를 제품 기준으로 채택할지는 미정으로 보존한다.
4. **재생성 실패 복원:** `search`는 조회 전 카드와 선택을 지우고, 실패 시 `previousCourse` 문자열만 덧붙인다. 이전 카드·지도 선택·제외 목록 전체 복원과 다르다. 기존 작업 목록의 '이전 일정 보존'은 이 제한 범위로 읽어야 한다.
5. **결측 정보:** 좌표 결측 후보는 카드로 남기고 핀은 만들지 않는다. 반면 `recommend`는 공식 URL/식별 정보 오류를 만나면 요청 전체 오류로 처리한다. 명세의 해당 요소만 미확인/비노출과 차이가 있어 식별자 정책과 함께 보완한다.
6. **오래된 응답:** 위치·경로·대안은 버전/취소 처리가 있으나 기본 추천 `search`에는 동일한 요청 버전 검사가 없다. 입력 비활성화만으로 모든 화면 전환 시나리오를 충족했다고 단정하지 않고 구간 테스트에 포함한다.
7. **저장·체험:** 예전 test1/test2 설계는 참고안이다. 이번 명세는 외부 계정·실제 사용자 ID 없는 버튼 기반 데모 상태를 명시한다. 이를 비교 기록하며 기존 설계를 최종 요구로 채택하지 않는다. 선택≠저장≠예약, 현재 브라우저 한정·전체 초기화·최신 정보 재확인을 포함해야 한다.
8. **데이터 계약:** 명세 예시는 `request_kind=route`, 개인 구현은 `course`다. 현재 `category`는 6종이고 명세 관심사 범위보다 좁다. 응답 주소·행사기간·추천 이유 등도 차이가 있다. 개념 계약을 그대로 확정 API로 보지 않고 UI 연결 전에 매핑을 제시한다.
9. **이동:** 도보/대중교통 내부 안내는 이미 추가했으나 코스 계산은 도보만 사용한다. 총 도보 누락·미래시각·접근성 미확인은 유지한다. 명시 보행 상한을 충족한 것처럼 표시하지 않는다.
