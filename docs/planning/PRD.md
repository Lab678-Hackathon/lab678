## 1. 제품 정의와 사용자 문제

### 1.1 서비스 한 줄 정의 [제품 기본선]

**서비스명은 ‘오늘 나들이’**다. 홈의 `나들이 찾기`는 서비스명이 아닌 핵심 행동 버튼(CTA)이며, 화면 구조와 기존 사용자 동작은 유지한다.

**문화나들이를 하고 싶지만 장소·시간·이동·참여 조건을 비교해 선택하기 부담스러운 시니어가, 한국어 AI 음성·텍스트 대화로 자신의 조건을 확인하고 실제 문화정보 기반 추천을 지도·카드 또는 나들이 코스로 받아 방문을 결정하도록 돕는 서비스.**

### 1.2 왜 만드는가 — 기획 출발점 [팀 검토 대기]

사회적 교류와 외출 기회가 줄어드는 시니어에게 **새로운 문화·여가활동을 경험할 계기**를 제공하고자 한다. 외출하고 싶은 마음이 있더라도 어디에 가야 하는지, 자신의 시간·이동 여건에서 실제 방문을 고려할 수 있는지 살피는 과정이 장벽이 될 수 있다는 문제의식에서 출발한다.

**문제의 핵심은 ‘문화나들이를 선택하고 결정하는 과정의 부담’입니다.**

사회적 고립·외로움 완화는 **기획 동기이자 검증할 장기적 가능성**이지, 이 MVP가 입증한 직접 성과가 아니다. 서비스가 직접 지원하는 과정은 **조건 파악 → 근거 확인 → 선택·수정**이다.

### 1.3 타깃 정의 [팀 검토 대기 — 희영님 구두 찬성 포함]

- **핵심 사용자 제안:** 문화·여가활동을 해보고 싶지만 장소 탐색과 시간·거리·걷기·참여 조건을 살펴 나들이를 선택하고 결정하는 데 부담을 느끼는 시니어.
- **대표 사례·우선 검증 집단:** **1인 시니어 가구**. 손희영님의 **구두 찬성**이 있었으나 이 문서의 전체 타깃 문구는 팀의 최종 문서 검토가 남아 있다.
- **이용 범위:** 1인 거주가 가입·추천의 필수 조건이 아니다. 부부·친구 등 동행 시니어도 사용할 수 있다. 별도의 동행자 예약·그룹 프로필 기능까지 확정된 뜻은 아니다.
- **초기 검증 생활권:** 서울. 이를 서울 외 접근을 기술적으로 금지하는 정책으로 해석하지 않는다. 실제 데이터 조회 범위는 확인해야 한다.
- **가정 금지:** 모든 시니어가 스마트폰 사용·보행에 어려움을 겪는다고 전제하지 않는다. ‘70세 이상 독거노인 전용’ 같은 제한적 카피는 별도 근거·합의 없이 사용하지 않는다.
- **미검증:** 실제 당사자가 나들이 선택 과정에서 겪는 불편의 크기, 대표 연령·디지털 이용 수준·걷기 제약, 서비스 사용으로 선택 부담이 얼마나 줄어드는지.

### 1.4 사용자 목표와 차별화 지점

1. 새로운 활동을 알아보고 본인에게 맞는 후보를 좁힌다.
2. 복잡한 화면 입력 대신 **말하거나 직접 입력**해 날짜·출발지·관심사·시간·이동 부담을 설명한다.
3. AI는 **모호하거나 빠진 중요한 조건만** 확인한다. 운영·예약·가격·이동 등 사실은 검증 가능한 데이터·규칙에 근거한다.
4. 추천 결과에서 **이유와 확인 필요 정보**를 보고 실제 방문을 결정한다.
5. 결과가 맞지 않으면 조건을 바꾸거나 같은 조건으로 다른 장소를 찾는다.

이 제품의 차별화 초점은 단순 장소 나열이나 AI의 말솜씨가 아니라 **대화로 조건을 정확히 파악하고, 선택에 필요한 근거·미확인을 구분하며, 사용자의 결정을 이어주는 경험**이다. 기존 검색이나 일반 AI와 비교한 우월성은 사용자 검증 전까지 주장하지 않는다.

### 1.5 목표와 범위

| 구분 | 범위 |
|---|---|
| 핵심 결과 | 개별 문화장소의 지도+카드 추천, 사용자 요청 시 2~3곳을 잇는 코스 1개 |
| 핵심 입력 | 직접 입력 + 한국어 턴 기반 음성·텍스트 AI 대화, 동일 조건 필드 동기화 |
| 결정·재탐색 | 상세·선택, 조건 수정, 같은 조건의 추가 후보 찾기, 코스 제외 후 재생성 |
| 저장·재접근 | 실제 OAuth 없는 **체험용 로그인**과 동일 브라우저의 장소·코스·선호 저장·초기화 |
| 포함 범주 | 문화 체험·전시·공연·축제/행사·역사문화 장소 |
| 범위 밖 | 복지 지원 신청·자격 판정, 자체 예약·결제, 실시간 좌석 보장, 자체 턴바이턴 내비게이션, 실제 소셜 OAuth·서버 회원 DB·기기 간 동기화, 상시 듣는 전이중 음성 |
| 추후 검토 | 복지/생활지원 연계, 포토·스탬프, 장기적 사회적 연결 성과, 별도 동행자 기능 |

## 2. 단일 진입 구조와 대표 사용자 시나리오

### 2.1 정보 구조 [제품 확정]

```text
S01 홈 [나들이 찾기: 단일 핵심 진입]
  ↓
S02 통합 입력(위치·날짜·시작/종료시각 + ‘더 원하는 게 있으세요?’ 음성/텍스트)
  └─ S02a: 같은 화면의 인라인 AI 조건 확인 [기획 확정]
      ├─ 개별 장소 요청 → S03 지도 위 / 카드 아래
      │   ├─ 카드·마커 연동 / 같은 조건의 다른 후보 찾기
      │   └─ S04 상세 → 임시 선택 / 명시적 저장
      └─ 다중 장소 요청 → S05 코스 1개(2~3곳)·순서·시간·지도
          └─ 제외 예정 표시 → 코스 다시 만들기 / 저장
S03·S05 [조건 바꾸기] → S02의 기존 입력·대화 복귀
S04·S05 저장 시 비회원 → S06 체험 로그인 → 요청한 저장 자동 1회 완료
S01 → S07 내 정보(비회원도 진입 가능) → 저장 장소·코스 / 선호·초기화
```

**별도 코스 시작 메뉴와 결과 화면 전용 AI 채팅창은 두지 않는다.** 출발지·날짜·시각·대화 맥락을 보존한 채 원래 입력 화면에서 조건을 변경한다.

### 2.2 대표 시나리오 A — 문화장소 추천

1. 사용자가 홈에서 `나들이 찾기`를 누르고 **“오늘 오후에 가까운 전시를 보고 싶어요. 오래 걷기는 힘들어요”**라고 말한다.
2. 서비스는 위치·출발/종료 시각 등 아직 필요한 조건을 확인하며, ‘짧게 걷기’가 단순 선호(Soft)인지 필수 제한(Hard)인지 모호하고 중요하면 질문한다.
3. 조건 충돌이 없으면 초안에 반영하고, 기존에 확정한 값과 충돌하면 변경 전·후를 안내하고 승인받는다.
4. **S02 내부 조건 확인 영역**에서 날짜·시간·이동 선호 등을 최종 확인한 뒤 추천한다.
5. 실제 조회 근거에 따라 개별 장소를 소수 추천하고 **상단 지도·하단 카드**와 추천 이유·확인 필요 사항을 보여준다.
6. 카드/지도에서 장소를 비교해 상세를 보고 선택하거나 저장한다.
7. `조건 바꾸기`로 대화 화면에 돌아가 변경한 조건으로 다시 추천받거나, `다른 곳 찾기`로 같은 조건의 새로운 후보를 탐색한다.

### 2.3 대표 시나리오 B — 여러 장소 나들이 코스

1. 같은 `나들이 찾기` 화면에서 “전시 두 군데를 이어서 가고 싶어요”라고 요청한다.
2. 날짜·출발 위치·시작/종료 경계를 확인한 후 **2~3곳을 순서 있게 잇는 코스 1개**를 제시한다.
3. 각 장소의 운영 가능성·도착 예정·관람/체류시간·구간 이동과 미확인 사항을 보여준다.
4. 장소를 빼려면 먼저 `제외 예정`으로 표시하며, 사용자가 `코스 다시 만들기`를 명시적으로 누를 때 재구성한다.
5. 저장은 선택/확인 후 체험용 로그인을 이용한다. 시간·데이터 검증 실패 시 이전 유효 결과를 보존한다.

### 2.4 음성 대화의 합의된 경험

- 마이크 누르기 → 발화 인식 완료 → **별도 보내기 버튼 없이 AI가 자동 처리**하는 턴 기반 방식. 전사 텍스트를 보여주고 바로잡기·다시 말하기를 제공한다.
- AI 답변은 화면에 텍스트로 표시하고, 가능한 환경에서는 TTS로 읽으며 읽기 중지·텍스트 대체를 제공한다.
- 음성에서 파악한 출발지·날짜·시각은 **같은 입력 필드**에 연결한다. 직접 수정된 최신값은 이전 AI 해석보다 우선한다.
- 기존 확인값과 새 발화가 충돌하면 **자동 덮어쓰지 않고 확인**한다.
- 중복 응답·정정 도중 경합에 대한 세부 구현은 기술·UX 확인이 필요하다. 상시 마이크 청취·말 끊기 가능한 전이중 통신은 MVP 필수가 아니다.

## 3. 기능 요구사항 — F01~F20 (v0.5 보존 + 세부 확정 반영)

| ID | 사용자 기능 | 필수 결과와 정책 | 구분 |

| F02 | 출발 위치 | 현재 위치 권한 또는 직접 장소 검색·확인. **좌표 임의 대체 금지** | 기준 요구 |
| F03 | 날짜·시간 | 출발 날짜·시작·종료 입력. **최소 가용시간 60분**, 오류는 필드 바로 아래 표시 | 기획 확정 D13/D15 |
| F04 | 한국어 양방향 AI 대화 | 음성 STT/텍스트 → AI 조건 확인·질문 → 텍스트/TTS 응답. 인식 종료 시 자동 처리 | 제품 확정 + D10 |
| F05 | 입력 필드↔대화 동기화 | 대화값을 필드에 반영, 기존 확정값 충돌 시 변경 승인, 직접 수정 최신값 우선 | 제품 확정 + D09 |
| F06 | 조건 해석 | 관심사·예산·실내외·걷기·제외·일정. Soft 선호/Hard 필수 제한 구분 | 제품 확정 Q2 |
| F07 | 개별 문화장소 추천 | 근거 있는 소수 후보·이유·추가 확인 항목 표시, 없는 결과 억지 보충 금지 | 기준 요구 |
| F08 | 지도+카드 | 지도 위/하단 가로 카드, 마커↔카드 포커스 연동, 지도 단독 오류여도 카드 유지 | 제품 확정 + D12 |
| F09 | 장소 상세·공식 행동 | 운영·가격·예약·대상·이동·출처·공식 링크·외부 길찾기, 미확인 표시 | 기준 요구 + D16 |
| F10 | 장소 선택·저장 | `이 장소 선택`과 `내가 고른 장소에 저장` 구분. 저장 성공 시 상세 유지·저장됨 표시 | 기획 확정 D01/D17 |
| F11 | 코스 의도 판별 | 같은 대화에서 `place/route` 분기, 별도 홈 코스 메뉴 없음 | 제품 확정 Q3 |
| F12 | 코스 조건 확인 | 날짜·출발 위치·시작·종료 4값 확인 후 실행 | 기준 요구 |

### 3.1 문화 콘텐츠 및 선호 범위 [기준 요구]

- 추천 유형: 직접 참여 체험, 공연, 전시, 문화·역사 장소 방문, 축제·행사.
- 기본 관심사 6종: 전통문화 / 역사·궁궐 / 문화 체험 / 미술·전시 / 공연 / 축제·이벤트. 복수선택 또는 Skip 허용, 자유 선호 기록은 구현 범위 확인.
- 일반 쇼핑·맛집 검색·스포츠·레저·복지 지원 신청은 이번 제품의 핵심이 아니다.
- 참여 연령·예약 필요·사전 신청·보호자 동반 등은 실제 참여 가능성을 판단하는 중요 데이터다.

### 3.2 조건 및 시간 정책 [제품·기획 확정]

- 최소 가용시간 **60분**(D15). UI·API 검증값을 이 기준으로 일치시킨다. 기존 서버 코드의 30분 처리는 이 제품 요구와 충돌하므로 회귀 테스트 대상이다.
- 필수 시간 정보는 출발 날짜·시작 시각·종료 시각이며, 오류는 **문제 필드 바로 아래 인라인 안내**(D13). 종료 날짜·자정 경계·과거 시각 검증의 구체 규칙은 기술·UX 합의 필요.
- **Hard(필수):** 사용자가 분명히 정한 절대 제한, 행사 종료·참여 대상 불일치. Hard에 어긋나는 후보를 정상 `조건 충족`으로 표시하지 않는다.
- **Soft(선호):** 짧은 도보 선호, 관심·예산 선호 등. Soft를 AI가 임의로 Hard로 격상하지 않는다.
- “걷는 게 힘들다”처럼 모호하지만 선택에 중요한 경우 AI가 보완 질문한다. 건강 상태를 진단하거나 불필요한 건강정보를 요구하지 않는다.
- 이동·운영·가격·예약이 미확인이면 **추정으로 이용 가능을 보장하지 않는다**. 사실을 숨기지 않고 확인 필요로 분류한다.

### 3.3 추천 상태·신뢰 [기준 요구]

- 후보 상태: **조건 충족 / 추가 확인 필요 / 조건 완화 대안**. 근거 없이 `조건 충족`을 주장하거나 제외 후보를 정상 결과에 끼우지 않는다.
- 추천 이유는 확인된 근거에서만 **0~2개** 표시한다. AI가 영업시간·무료·예약가능·도보시간·무장애 여부 등을 만들어내지 않는다.
- 실제 후보가 0건이면 정상적인 **0건 상태**를 표시한다. **첫 추천 0건은 S03에 남아 조건 변경을 안내**하며 자동으로 S02로 이동시키지 않는다(D14).
- 같은 조건 `다른 곳 찾기`는 중복되지 않는 후보 탐색. 추가 후보가 없으면 **기존 카드 유지 + 더 없음 안내**(D07/D08).
- **지도만 실패하면 카드 유지 + 지도 영역 재시도**(D12). 전체 조회 실패·입력 오류·유효 후보 0건과 섞지 않는다.
- 장소 카드의 운영·가격·예약·이동 미확인은 해당 항목 **바로 옆**에 표시하고, 상세 S04에는 **확인 필요 항목 요약**을 제공한다(D16).

### 3.4 결과 카드/상세에 필요한 정보 [기준 요구]

| 데이터 | 표시·판정 원칙 |
|---|---|
| 장소명·유형·주소·좌표 | 실제 소스 값. 위치 좌표가 없으면 핀 임의 생성 금지 |
| 사진·아이콘 | 사용 가능한 경우만. 누락된 중요 운영정보를 사진으로 가리지 않음 |
| 행사기간·운영일/시간·예상 방문시각 | 서로 구분하고 기준 날짜와 대조. 실제 운영 보장 아님 |
| 가격·예약·참여대상 | 미확인을 무료·예약 불필요로 표기하지 않음 |
| 도보 거리·시간·코스 구간 | 검증 가능한 경로 기반 값만 도보시간으로 주장. 직선 거리 구분 |

| 코스 결과 | 방문 순서·도착·예상 체류·구간 이동·시간 부족 표시·미확인 항목 |

### 3.5 저장·체험용 로그인 정책 [Q1/Q6 + D01/D03~D06/D17~D20]

1. **비회원 이용:** 추천·대화·재추천·코스 구성은 로그인 없이 이용 가능. S01의 `내 정보`를 눌러도 로그인 강제 없이 S07에 진입할 수 있다(D05).
2. **체험용 로그인:** 저장·개인화 진입 시 안내. 버튼 클릭으로 **외부 Google·Kakao 인증 없이** 데모 로그인 상태 전환. 인증토큰·회원 DB·실제 계정/기기 동기화 구현 범위 아님.
3. **저장 행동 연속성:** 비로그인 사용자가 S04/S05의 `저장`을 누르면 로그인 완료 후 **원래 저장 행동을 자동으로 단 한 번 완료**한다(D18). 인증을 취소하면 저장하지 않고 입력·결과·임시 선택을 유지한다.
4. **온보딩 순서:** 첫 체험 로그인에서 선호·관심사 설정 때문에 **요청한 저장을 지연하지 않는다**. 저장 성공 뒤 `관심사를 설정하면 더 알맞은 나들이를 추천받을 수 있어요` 안내와 `설정하기/나중에` 선택을 제공(D19/D20).
5. **장소 선택/저장 구분:** S04 `이 장소 선택` ≠ `내가 고른 장소에 저장`. 저장 완료해도 상세 S04에 머물며 `저장됨`과 `내 정보에서 보기`를 제공(D01/D17).
6. **홈 저장 미리보기:** 실제 저장 항목이 있을 때만 표시(D06). 저장 항목이 없으면 빈 미리보기 카드 자동 노출 금지.
7. **내 정보:** 탭이 아닌 **세로 섹션형**(D04), 비로그인 방문 허용. 저장 목록·관심사/선호·데모 상태는 각자의 조건에 따라 표시한다.
8. **체험 종료:** 사용자 확인을 받은 뒤 **데모 로그인 상태와 브라우저 저장 데이터 전체를 초기화**한다(D03). 단순 '로그아웃만 하고 저장 유지'를 종료 동작으로 주장하지 않는다.
9. **보존 한계·개인정보:** 동일 브라우저 저장소(`localStorage` 등, 구현 결정)에서만 새로고침/재방문 복원. 기기 간 동기화 없음. 위치·음성 원본·전사·대화 저장 여부와 삭제 범위, 개인정보·민감정보 저장 최소화는 기술 검증 필요.
10. **보안:** 데모 로그인 플래그는 인증 수단이 아니다. 보호된 서버 사용자 데이터에 실제 인증된 것처럼 접근하지 않는다.

## 5. 실제 데이터·AI·이동 기술 경계

### 5.1 AI와 데이터의 책임 분리 [제품 기본선]

- **AI:** 말/글의 의도·조건 파악, 필요한 조건 질문, 결과의 근거 있는 설명·문화/이용 Q&A.
- **데이터·규칙:** 장소/행사 목록·기간·운영·가격·예약·대상·좌표·이동시간·코스 적합성의 사실 판정.
- 미확인/누락 데이터는 **확인 필요**로 표시한다. 데이터가 없다는 이유로 AI가 장소 좌표·운영시간·가격·예약 여부·도보시간을 채워 넣지 않는다.
- 추천 출발지는 사용자가 선택한 실제 좌표를 사용하며, 위치 권한 거부 시 직접 입력을 허용한다. 임의 기본 좌표로 사용자를 대체하지 않는다.

### 5.2 연동 후보 및 상태 [기술 검증 필요]

| 역할 | 후보 | 현재 문서 수준 |
|---|---|---|
| 문화행사·장소 | 서울문화포털/서울시 문화행사 데이터, TourAPI | 실제 API 응답/결측/시연 데이터 확인 필요 |
| 공식 예약/강좌 | 서울시 공공서비스예약 등 | 추가 후보, 전면 통합 확정 아님 |
| 공연 보완 | KOPIS 등 | 데이터 공백시 선택 후보 |
| 도보·이동 | TMAP 보행자 경로 등 | 경로 데이터·요청권한/시연 환경·접근성 근거 검증 필요 |
| 지도 표시·외부 길찾기 | 검증된 지도 SDK/외부 링크 | 현재 기술 구현에 맞춰 확정, 인증/지도 표시 오류 상태 분리 |

| FAQ/정보 검색 | 확인 가능한 문서·공식 자료 기반 | 근거 없으면 확인 필요/공식 문의 경로 안내 |
| STT·TTS | 시연 브라우저에서 검증한 방식 | 실제 음성 인식·읽기·권한/오류/중단/자동 전송 경합 확인 필요 |
| 저장 | 브라우저 스토리지 | 동작·데이터 범위·초기화 QA 필요, 서버 회원 저장 X |

**교통 범위:** 대중교통 총 소요시간·환승·도보거리의 인앱 표시는 실제 데이터와 공수가 확인되면 검토한다. 실시간 하차 알림·턴바이턴 경로안내·자체 내비게이션은 필수 범위에서 제외한다. 미구현 시 외부 길찾기 링크는 가능하되, 링크만으로 대중교통 상세를 구현했다고 표시하지 않는다.

### 5.3 논리적 인터페이스 (실제 API 스키마 아님)

- **입력 예시:** `start_location`, `start_at`, `end_at`, `interests`, `budget_limit`, `mobility_preference`, `hard_constraints`, `excluded_places`, `existing_plans`, `request_kind(place|route)`, `confirmed_fields`, `conversation_context`.
- **AI 조건 결과:** `assistant_text`, `missing_fields`, `updated_condition_draft`, `need_clarification`, `ready_to_search`.
- **장소/코스 결과:** `candidates[]` 또는 `route(stops[])`, `status`, `facts`, `reasons`, `checks_required`, `official_url`, `source_checked_at`.
- **체험 상태:** `is_demo_signed_in`, `saved_picks`, `saved_routes`, `preferences`, `onboarding_done`, `pending_save_action`(명칭 제안). 실제 저장 스키마·중복 저장 방지 키는 기술팀 결정.
- **오류 분리:** 입력 검증 오류 / 음성 권한·인식 오류 / API·네트워크 오류 / 유효 조건 정상 0건 / 지도만 실패 / TTS 실패 / 코스 시간 부족 등.

API 연동 담당자는 실제 구현에서 **요청·응답 자료형, 필수/선택, 결측 처리, 최신값 적용, 실패 상태**를 팀 UI와 공유해야 한다. 기존 예시 JSON을 확정 계약으로 간주하지 않는다.

### 5.4 개발·개인정보·배포 보호

- 사용자 입력·추천 결과·저장한 선택 상태를 구분하며, 오래된 비동기 API 응답이 최신 조건을 덮어쓰지 않게 한다.
- API Secret/환경값은 공개 코드·클라이언트 코드·로그에 노출하지 않는다.
- 비회원 대화·위치·음성 전사/원본의 보관 범위 및 데모 데이터 삭제 정책은 개인정보 최소화 관점에서 기술 확인한다.
- Mock/Fixture와 실제 데이터를 화면·테스트·발표에서 구분한다.
- **기존 프로젝트 코드·디자인·에셋 사용은 행사 규정과 운영진 공식 답변을 확인**하고 진행한다. 이 PRD가 재사용 적법성/허용 여부를 승인하지 않는다.
