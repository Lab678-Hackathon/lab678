### 1.1 해결하려는 문제

사용자가 나들이 장소를 직접 검색하고 운영시간·예약·위치·이동 부담을 일일이 비교하는 과정은 외출을 미루는 원인이 될 수 있다. 특히 확인이 필요한 정보를 단순히 “직접 확인하세요”라고 넘기면 추천이 실제 방문 결정으로 이어지기 어렵다. **이 MVP는 외로움·사회적 고립 감소 효과를 입증하지 않으며**, 방문 결정에 필요한 정보 탐색과 선택 부담을 줄이는 데 집중한다.

### 1.2 가치와 차별화 가설

- **친구 같은 시작:** 홈에서 캐릭터가 먼저 나들이를 제안한다. OS 푸시 알림이 아니라 서비스 접속 후 인사다. [H01]
- **대화형 탐색:** 말하거나 글로 편하게 이야기하면 AI가 조건을 해석하고 빠진 내용만 묻는다. [H02~H04]
- **정보 확인 부담 감소:** 실제 이름·위치가 확인되고 방문에 필수적인 운영·예약 조건을 확인할 수 있는 장소를 기본 추천으로 보여준다. [H11 보완]
- **결정과 이동의 연결:** 상세 정보와 실제 경로 계산에 근거한 보행 안내까지 이어진다. [H06/H12]

차별성이 실제 사용자에게 유효한지, 부담을 얼마나 낮추는지는 [미검증]이다.

## 2. MVP 범위와 정책

### 2.1 이번 추가 합의로 우선 구현할 핵심 흐름 [기획 확정]

```text
S01 홈: 캐릭터가 나들이 제안 / [말로 대화 시작하기] / 텍스트 입력
  ↓
S02 대화: 활동·기분 파악 → 부족한 출발지·날짜·시간만 확인
  ├─ 필요할 때 출발지·날짜·시간 선택 UI 노출
  ├─ 현재 위치는 사용자가 [현재 위치 사용]을 누를 때만 권한 요청
  └─ 조건이 충분하면 별도의 전체 요약·승인 화면 없이 즉시 추천
        ↓
S03 = S02 대화 안의 인라인 추천 결과 상태 (최대 3개 세로 카드)
  ├─ 카드 [상세 보기] → S04 장소 상세
  │    ├─ [지도 보기] → S08 내부 지도·보행 경로 (S08은 신규 화면 ID 제안)
  │    └─ [내 나들이에 저장] → 필요할 때 S06 체험 모드 → 저장
  └─ 사용자가 말/글로 조건 변경 → 기존 조건 중 변경된 것만 갱신 → 같은 대화에서 재추천
S01/상세 → S07 내 정보·내 나들이 (현재 브라우저 저장만)
```

**S02a 기존 인라인 ‘최종 조건 확인’ 단계는 매번 필수로 거치지 않는다.** 필수값이 불명확하거나 기존 확정값과 충돌하는 경우에만 확인을 요청한다. [H04/H09]
**S03은 기존 별도 ‘지도 위·가로 카드 아래’ 결과 페이지로 쓰지 않고 S02 내 결과 상태로 재정의한다.** 지도는 상세 이후 S08로 제공한다. [H05~H07/H12]

### 2.2 포함 [기획 확정]

1. 홈 캐릭터 선제 인사 및 **한국어 음성·텍스트** 자유 대화.
2. 대화에서 선호 활동/기분, 출발지, 방문 날짜·시간 추출; 중복 질문 금지; 모호한 경우만 보완 질문.
3. 충분한 조건 확보 후 **추가 확인 버튼 없이 자동 추천**.
4. 동일 대화에서 **방문 가능 근거가 있는 장소 최대 3개**를 세로 카드로 표시하고 상세로 이동.
5. 기존 조건 보존 + 자연어로 바꾼 조건만 적용하여 재추천. 동일 조건에서 “다른 곳” 요청도 자연어로 처리.
6. 상세에서 큰 **지도 보기** 및 보조 **내 나들이에 저장**; 지도에서는 TMAP 기반 보행 경로와 예측 소요시간 **검증 성공 시에만** 표시.
7. 원클릭 체험 모드, 브라우저 내 장소·간단한 선호 조건 저장/복원. 전체 대화 내역의 영구 저장은 제외.
8. AI 답변 텍스트+음성 병행, 음성 끄기. 한 번 음성 대화를 시작하고 자동 턴 전환을 우선 시도; 실패 시 명확한 수동 마이크 버튼 방식. 텍스트는 상시 이용 가능.
9. 문화 나들이와 관계없는 요청은 짧게 대응하고 나들이 주제로 자연스럽게 유도.
10. 위치 권한 거절/미지원·음성 오류·API 실패·정상 0건·지도 실패를 구분하고 대체 경로 제공.

### 2.4 제외 또는 후속 검토

- [확정 제외] 실제 OAuth·소셜 회원가입·서버 계정 DB·기기 간 동기화·전체 대화 기록 영구 저장·직접 예약·결제·OS 선제 푸시 알림.
- [기존 제외 유지] 실시간 좌석 확보 보장, 복지 신청, 자체 턴바이턴 내비게이션, 실시간 하차 알림, 범용 챗봇.
- [기술 검증 조건] 연속 음성 대화, TMAP 내부 보행 경로는 **구현 우선 목표이나 동작 성공이 검증되지 않은 상태**. fallback을 임의로 최종 정책으로 확정하지 않음.
- [미확인] 다중 코스의 MVP 구현 우선순위. **기존 약속 기능이므로 사용자·팀 승인 없이 삭제하거나 ‘제외 확정’으로 변경하지 않음.**

## 4. 데이터 신뢰·추천 규칙

### 4.1 사실 근거와 판정 책임

**AI는 사용자 말을 해석하고 설명하되, 사실을 만들어서 빈 데이터를 채우지 않는다.** 실제 장소·위치·운영·기간·예약·참여자격·경로·예상시간은 API/공식 출처/검증 로직으로 확인한다.

| 검사 항목 | 기본 추천 처리 |
|---|---|
| 장소명·ID·위치 좌표 | 실제 출처에서 확인돼야 추천. 출발지/목적지 임의 대체 금지 |
| 행사 기간 / 방문일 운영 여부 | 방문 예정 날짜·시간과 부합한다는 근거가 없으면 기본 추천에서 제외 |
| 예약 필수 여부 및 필요 조건 | 확인할 수 없는 필수 방문 조건이 있으면 기본 추천에서 제외 |
| 가격·유료 여부 | 확인 값만 표시. 금액이 방문의 필수 제약인 경우 불확실하면 제외; 일반적으로 미확인은 무료로 해석하지 않음 |
| 입장권·잔여 좌석 | 실시간 데이터가 없다면 **예약 완료·입장 보장 불가**. 실제 확인 범위를 사용자에게 설명 |
| 도보 소요시간 | TMAP 등 경로 계산이 성공한 경우에만 수치 표시. 직선 거리 수치를 보행시간으로 대체 금지 |
| 공식 페이지 | 출처가 확인된 링크만 제공. 확인 방법만 떠넘기는 안내를 기본 답변으로 삼지 않음 |

**용어 주의:** ‘방문 가능성이 확인된 장소’는 확인 가능한 일정·운영·예약 규칙이 조건에 부합한다는 뜻이다. 현장 사정, 실시간 매진, 임시 휴관까지 보장하는 표현은 사용하지 않는다.

### 4.2 추천·재추천

- 조건이 준비되면 **최대 3개** 반환. 후보 1~2개만 검증되면 그 수만 표시, 부족분을 허구로 채우지 않음.
- 거리 가까움은 기본 정렬 선호일 뿐 필수 질문이나 모든 시니어의 보행능력 가정이 아니다.
- **첫 0건:** 같은 대화 안에서 조건을 변경하도록 제안, 결과 페이지로 튕기지 않음.
- **재추천 0건:** 이전 유효 결과는 보존하고 더 찾지 못했다는 사실을 설명.
- **API 오류:** 0건과 구별; 재시도 제공. 실제 API 실패를 가짜 성공으로 대체하지 않음.
- 수정한 조건을 최신 요청 식별자로 관리해 늦은 응답이 기존 UI를 덮지 않도록 함 [구현 제안].

### 4.4 논리적 데이터 계약 [제안 — 실제 API 확정 아님]

```text
conversation_turn(text, speech_transcript?, conditions_draft, confirmed_fields)
  → assistant_text, conditions_patch, missing_fields[], ready_to_search, clarification?
recommend(confirmed_start_location{label,lat,lng,source}, visit_date,
          start_time, end_time?, interests[], mood?, mobility_preference?, exclusions[])
  → candidates[0..3]{id,name,lat,lng,address,source,checked_at,
                      visit_eligibility,operating_info,reservation_info,

  → route_geometry?,duration_minutes?,status,error?
```

`end_time?` 선택 여부는 기존 60분 가용시간 규칙과 합의해 확정한다. 필드 이름·타입·엔드포인트·Mock/실 API 표시는 개발팀 계약이 기준이다.
