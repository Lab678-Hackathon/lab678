# Lab 678 | 김동조 개발 병렬 착수 패키지 v0.1

**기준:** 독립형 PRD v0.5 · 2026-10-30. 기술 설계·API 최종 승인 전의 **착수 제안**이며, 구현 방법·엔드포인트는 개발 담당자가 제안·팀 확인.

## 지금 별개로 시작 가능한 작업
1. 서버/프론트/외부 API 개발 환경·Secret 관리·Health/에러 확인(기존 TEAM_WORKFLOW.md의 실제 스택·브랜치 규칙 확인 후).
2. **TourAPI/서울문화포털 등의 실데이터 1건 조회**: 제목·주소·좌표·운영·예약/가격·공식 URL·조회 시점 필드의 실제 값/결측을 확인. 실제 응답 샘플 1건과 누락 데이터 1건을 Product에 전달.
3. **STT/TTS 한국어 최소 스파이크**: 실제 시연 브라우저에서 마이크 권한, 음성→전사 텍스트, 텍스트→음성 읽기, 실패→텍스트 입력 복귀 검증. 상시청취·전이중은 범위 아님. 방법은 기술 선택.
4. **조건 구조화→추천 결과의 세로 슬라이스**: 화면과 독립적으로 유효 요청 1건을 받아 장소 소수 후보를 반환. 시간/운영/가격/예약/참여·이동의 확인/미확인 구별. 정해지지 않은 근거는 생성 금지.
5. 후속 병렬로 **코스 2~3곳 1개 구성·수정·재계산**과 **데모 로그인/브라우저 저장**을 별 모듈로 진행. 기능 삭제 결정 아님.

## 최소 논리 계약 — Product/UX와 필드 확인 후 고정

```json
{
  "request_kind": "place",
  "start_location": {"label":"청량리역", "lat":null, "lng":null},
  "start_at": "2026-10-31T14:00:00+09:00",
  "end_at": "2026-10-31T17:00:00+09:00",
  "note": "전시를 보고 싶고 가까운 곳이 좋아요",
  "conditions": {"interests":["exhibition"], "mobility_preference":"shorter_walks", "hard_constraints":[], "excluded_places":[]},
  "confirmed_fields": ["start_location", "start_at", "end_at"]
}
```

*위 좌표 `null`은 임의 좌표로 대체해서 추천하라는 뜻이 아니다. 실제 요청에 사용하려면 유효한 출발지 좌표를 사용자 입력/지오코딩으로 확보하고 확인해야 한다. 시간·날짜는 테스트용 예시이며 실제 시연/요청 시점에 맞춰 검증한다.*

```json
{
  "status":"ready",
  "assistant_text":"조건에 맞는 장소를 확인했어요.",
  "missing_fields":[],
  "request_kind":"place",
  "candidates":[{
    "id":"source-id", "title":"예시 문화장소", "address":null,
    "lat":null, "lng":null, "status":"check", "reasons":[],
    "opening_info":null, "price_info":null, "reservation_info":null,
    "mobility_info":null, "checks_required":["운영시간 확인 필요"],
    "official_url":null, "source_checked_at":null
  }]
}
```

*결과 JSON은 **형태 예시(Mock)**이고 실제 데이터가 아니다. 데모·테스트에 사용할 땐 명시적으로 Mock 표시. 실제 타입/엔드포인트/응답 envelope는 담당자 제안 후 합의.*

## 절대 혼동하지 않을 정책
- 홈 진입은 하나(S02 대화 의도로 `place|route` 분기). 결과 화면에 새 채팅 컴포넌트를 넣지 않음. **조건 바꾸기→S02 조건/대화 맥락 복구**.
- Soft `짧게 걷기` 선호를 Hard 제한으로 변환하지 않음. 사용자가 명시한 시간/거리 Hard는 실제 경로 근거 있을 때만 적합 판정. 확인 불가이면 `check`와 사유.
- 소수 후보(강제 채우기 X), 운영·예약·무료 추정 X, 지도 핀 임의 좌표 X. 가격/참여 조건/방문 가능이 확인 안 되면 `check` 처리.
- 코스 요청은 하나의 진입에서 2~3곳 순서 있는 1개 코스. 시간·운영·이동 불가능은 정상 결과로 통과시키지 않음. 수정 실패하면 이전 유효 선택 보존.
- **실제 OAuth/계정 DB 미구현**. 로그인 클릭은 데모 상태 전환일 뿐 인증 토큰/보호 API 접근 권한이 아님. 선택/코스/선호는 로컬 저장·복원·초기화; 로그아웃 동작은 UX와 합의.
- 음성 인식 실패·통신 오류·정상 0건·입력 오류 구별. `TTS` 읽기 결과와 화면 텍스트 일치.

## 기술 확인 목록(팀에 한 번에 전달할 쟁점)
1. 실제 API 연결·데이터 품질/키와 지도 SDK 허용 여부, 요청·응답 필드명과 좌표 필수 여부.
2. 한국어 STT/TTS 구현 경로·지원 브라우저·마이크 권한 실패 대비.
3. S02 화면 입력↔AI 대화 필드 동기화/상태 보존 방식.
4. 추천 최소 시간 **UI 최근 60분 vs 기존 서버 30분** 불일치 해결(대표 3시간 시나리오로 선착수 가능).
5. 시니어 이동 부담 Hard 판정에 사용할 실제 이동 경로·보행 편의 데이터의 범위.
6. 코스 날짜/방문 순서/시간 충돌 및 2~3곳 상한 회귀 테스트.
7. 브라우저 데모 로그인 상태·저장/초기화·후보 선택과 저장 상태 분리.
8. **해커톤 기존 프로젝트 코드 재사용은 운영진 확인 전 직접 이식 보류.** 기술 검증·독립 신규 구현은 착수 가능.

## 첫 인계물
- 실제 문화정보 **성공 샘플 1건 + 실패/결측 1건**, 출처 및 확인시각.
- API 최소 계약 문서/타입 예시와 화면 데이터 바인딩 키.
- STT/TTS 실제 작동 여부, 미지원·권한거부 시 fallback 결과.
- 독립 정상 요청 1건→실제 추천 응답 검증(또는 Mock만 가능했으면 그 사실 표시).
