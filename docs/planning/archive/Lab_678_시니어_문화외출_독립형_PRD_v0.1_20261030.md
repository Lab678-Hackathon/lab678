## 1. 제품 정의

### 1.1 해결할 문제 [확정]

**고령 1인 가구가 일상생활에서 도움이 필요하다는 사실은 알지만, 자신의 불편이 어떤 지원서비스로 연결되는지 몰라 실제 도움을 받지 못하는 문제**를 해결한다. 식사·장보기·외출·디지털 기기 이용처럼 생활 불편은 다양하다. 검색 결과나 일반 LLM 답변을 받은 뒤에도 제공 지역, 이용 대상, 신청 과정, 실제 문의처를 스스로 비교·확인해야 하는 부담이 남을 수 있다.

### 1.2 제공 가치 [확정]

사용자가 **평소 사용하는 말**로 불편을 설명하면 시스템이 최소한의 추가 질문으로 상황을 파악하고, **공식 자료에 근거해 검수한 지원서비스 DB**에서 후보를 찾는다. 결과에는 **추천 이유, 자격·접수 확인사항, 실제 문의처와 신청 방법**을 제시한다.

> 사용자가 도달해야 할 상태: **“혼자 해결해야 할 줄 알았는데 이런 도움을 받을 수도 있구나. 여기로 연락해 확인하면 되겠구나.”**

**제품의 경계:** 서비스 적합성은 안내하지만 이용 자격·접수 가능·실제 수혜를 보장하지 않는다. 고령 1인 가구라도 모두 돌봄이 필요하다고 전제하지 않는다.

### 1.3 핵심 사용자와 이용 맥락

- **[확정] 1차 페르소나:** 혼자 거주하는 시니어(고령 1인 가구). 나이·생활 기능·자립 수준은 다양하다.
- **[확정] 대표 문제:** 지원서비스의 존재를 모르거나, 찾고 비교하고 문의하는 과정에서 막힌다.
- **[가정·제안] 보조 사용 맥락:** 가족 등이 함께 정보를 확인할 수 있는 일반 웹 이용. 별도 대리 신청·계정 기능은 미합의.
- **[미확인] 사용자 근거:** 관련 조사·실제 사례, 시니어 또는 가족 인터뷰 결과는 별도 확보 필요.

### 1.4 기존 검색·일반 LLM 대비 차별성

| 일반적인 정보 탐색의 과제 | Lab 678의 설계 대응 | 검증 방법 |
|---|---|---|
| 생활 불편을 제도명으로 직접 번역해야 함 | LLM으로 자연어를 지원 수요 태그로 구조화 | 같은 불편 문장의 해석·추가 질문 점검 |
| 검색 결과와 자격조건을 사용자가 대조해야 함 | 검수된 DB + 직접 구현한 조건 필터 | 맞지 않는 지역·명시된 자격조건 배제 테스트 |
| 추천 근거가 불명확할 수 있음 | 출처·태그·규칙과 연결된 추천 이유 | 결과 설명의 근거 추적 |
| 결과가 상황 변화에 반응하지 않을 수 있음 | 적합도 계산과 피드백 기반 재계산 | 이동 가능/불가능 등 조건별 순위 변화 |
| 실제 신청 행동으로 이어지기 어려움 | 연락처·신청 경로·확인 필요 조건 제공 | 사용자가 다음 행동을 말할 수 있는지 확인 |

**[미확인] 차별성의 실증:** 일반 LLM보다 정확하거나 유용하다는 성능 우위는 아직 입증되지 않았다. 가능하면 동일 시나리오 비교 테스트로 평가한다.

## 2. 범위와 성공 조건

### 2.1 서비스 전체 방향 [확정]

식사 지원, 외출·이동, 생활 도움, 디지털 기기 이용 등 **시니어 생활지원 전반으로 확장 가능한 구조**를 지향한다. 병원 방문이나 특정 진료에 한정하지 않는다. 다만 실제 제공 가능한 지원 종류는 검증된 DB 범위에 따른다.

### 2.2 해커톤 MVP [확정: A안]

**대표 생활 상황 한 가지**에서 `불편 입력 → 조건 확인 → 검수된 서비스 추천 → 근거·문의 안내 → 피드백 재추천`이 실제로 작동하도록 구현한다. 다른 생활지원 영역은 확장 가능한 **공통 데이터 구조·태그·엔진**으로 수용한다. 아직 작동하지 않는 영역을 사용 가능한 기능처럼 표시하지 않는다.

**[미확인] 대표 상황:** ‘혼자 사는 75세 시니어가 장보기·식사 준비에 어려움을 겪음’은 **검증 후보 시나리오**이지 확정된 구현 대상이 아니다. 실제 사용자 문제 근거와 검수 가능한 데이터 2~3건을 모두 확인해 선정한다.

### 2.3 MVP 기능 우선순위

| ID | 핵심 기능 | 기준 상태 | 우선순위 |
|---|---|---|---|
| F-01 | 자연어로 생활 불편 입력 | [확정] | P0 |
| F-02 | 거주 자치구·간단한 연령 정보 확인, 필요한 경우만 추가 질문 | [확정] | P0 |
| F-03 | LLM을 통한 사용자 상황 구조화(정보 추측 금지) | [확정] | P0 |
| F-04 | 검수된 지원서비스 DB 조회 및 공식 근거 유지 | [확정] | P0 |
| F-05 | 자체 조건 필터, 적합도 점수, 추천 우선순위 | [확정] 원칙 / [가정·제안] 상세식 | P0 |
| F-06 | 추천 이유·확인 필요 조건·연락처·신청 방법 안내 | [확정] | P0 |
| F-07 | 피드백을 조건·후보에 반영해 실제 재추천 | [확정] | P0 |
| F-08 | 결과 없음·정보 부족·오류·검증 중 데이터 처리 | [확정] 원칙 / [가정·제안] 세부 UI | P0 |
| F-09 | **최대 3건** 결과 카드 표시 | [가정·제안] 카드 수, 변경 가능 | P0 제안 |
| F-10 | 다른 분야 서비스 데이터 수용을 위한 태그 구조 | [확정] | P0(설계) |

**의도적으로 수행하지 않는 일 [확정된 제품 경계]:** AI가 이용 자격을 확정하거나 실제 승인·접수를 보장하는 일, 원천자료에 없는 지원서비스·혜택·연락처를 생성하는 일.

**후속 검토 제안 [가정·제안, 제외 확정 아님]:** 회원가입·이력 보관·알림, 실제 신청 대행, 모든 생활 분야의 실데이터 연결. 이 항목들의 P1/제외 처리는 팀 합의가 필요하며 기존 확정 기능을 승인 없이 삭제하지 않는다.

### 2.4 대표 시나리오 확정의 4개 필수 게이트 [확정]

1. **사용자 문제 근거:** 관련 조사·실제 시니어/가족 사례가 있다. 소수 사례를 전체 사용자 가치가 검증됐다고 과장하지 않는다.
2. **검수 가능한 실제 지원서비스:** 공식 서비스 **최소 2~3개**의 제공 지역·지원 내용·대상 조건·문의처·신청 방법을 확인한다.
3. **조건별 추천 차이:** 예컨대 동일한 식사 불편이라도 이동 가능한 사람과 거동이 어려운 사람의 결과가 **실제 태그·필터·점수 계산**에 의해 달라진다.
4. **문의 행동 가능성:** 결과에서 사용자가 추천 이유·확인사항·문의처를 알고 다음 행동을 결정할 수 있다.

4개 게이트가 충족되지 않았다면 대표 상황과 실제 지원정보의 완성은 `[미확인]`으로 유지한다. 데이터 확보 실패 시 대표 상황 변경 여부는 팀에서 승인한다.

## 3. 데이터 정책과 스키마

### 3.1 현황과 데이터 역할

- **[팀원 보고]** 김동조님이 서울시 공공 복지서비스 **396건 수집**, 그중 **노년 대상 후보 116건 1차 분류**를 보고했고 분석을 진행 중이다.
- **[미확인]** 원본 파일·필드·최신성·중복·개별 서비스 적합성은 이 문서 작성 시점에 검증하지 않았다. **116건은 검수 완료 또는 추천 가능 116건을 뜻하지 않는다.**
- **[확정]** 지원서비스 **상세정보**를 핵심 추천 DB로 사용하고, **시설 목록**은 문의처·연결정보를 보완하는 별도 자료로 둔다. 시설 항목만으로 지원 대상·혜택을 만들어내지 않는다.

### 3.2 태그 및 검수 정책 [확정]

| 구분 | 정의 | 사용 예시 |
|---|---|---|
| 확인된 태그 | 공식 자료에 명시된 사실 | 해당 자치구, 명시된 연령, 공식 제공 방식 |
| 근거 기반 파생 태그 | 원문에서 명확히 도출 가능한 의미 | “가정으로 도시락 배달” → 식사 지원·배달형 |
| 미확인 조건 | 원문에 없거나 확정하기 어려운 조건 | 소득·수급 여부·세부 심사·현재 접수 가능 여부 |

LLM이 태그 **후보**를 뽑을 수는 있으나 핵심 태그는 **원문 근거 확인·검수 후** 추천 DB에 반영한다. 원문 근거가 불분명하거나 상충하면 검수 완료 전 추천에서 제외한다. 서비스별 공식 출처와 확인일을 기록한다.

### 3.3 공통 레코드 구조 [가정·제안: 개발용 필드 초안]

| 필드 | 타입 | 요구·제약 |
|---|---|---|
| `service_id` | string | 내부 고유 ID |
| `name` | string | 원문으로 확인된 지원서비스명 |
| `need_tags` | string[] | 식사·이동·디지털 등 (확장 가능) |
| `delivery_mode_tags` | string[] | 배달·방문·시설방문·전화/비대면 등 |
| `region_codes` | string[] | 제공 지역. 원문 불명확하면 임의 보정 금지 |
| `eligibility_rules` | object[] | 조건 종류·연산자·값·근거·미확인 여부 |
| `provider_name` | string | 운영·안내기관 |
| `contact` | object | 전화번호 등 확인된 문의 정보 |
| `application_method` | string/null | 신청·문의 절차 또는 미확인 |
| `intake_status` | enum | `confirmed_open` / `confirmed_closed` / `unknown` (제안) |
| `official_source_url` | string | 공식 출처 링크 또는 안정적인 공식 근거 식별자 |
| `source_checked_at` | string | 확인 일자 (ISO 날짜 제안) |
| `tags_evidence` | object[] | 각 태그의 원문 근거·출처 위치·명시/파생 구분 |
| `review_status` | enum | `pending` / `reviewed` / `conflict` / `rejected` |
| `facility_refs` | string[] | 보완 시설 데이터의 참조 ID (선택) |

**추천 DB 편입 기준 [확정 원칙, 세부 필수필드 가정]:** 실제 서비스명·제공 지역·서비스 내용·공식 출처·실행 가능한 문의 방법이 확인되고 검수를 통과한 레코드만 실제 추천에 노출한다. 신청 세부 자격이나 현재 접수 상태가 불명확하면 명시적으로 안내한다. 누락된 신청정보가 있다면 허위 정보를 채우지 않고 문의를 통한 확인을 안내하되, 4개 게이트의 충족 여부를 별도 판단한다.

### 3.4 데이터 모드 분리 [가정·제안]

- `verified`: 검수 완료된 실제 서비스만 노출.
- `test`: 엔진 개발용 예시/Mock 데이터. **화면·로그·시연에서 테스트 자료임을 명시**하며 실제 서비스로 혼동하지 않도록 한다.
- 검수된 실제 레코드가 없으면 '실제 추천 성공'이라고 표시하지 않는다.

## 4. 입력 정책과 사용자 흐름

### 4.1 최소 입력 [확정]

- 최초 파악: **생활 불편 자연어**, **거주 자치구**, **간단한 연령 정보**.
- 조건부 질문: **독거 여부**, **이동 가능 여부** 등 실제 후보·순위가 바뀌는 조건만 필요한 순간에 질문.
- 초기 필수 입력 아님: **소득·수급자/차상위 여부·장기요양등급** 등 민감하거나 본인이 모를 수 있는 조건. 필요할 때 선택적으로 묻거나 `신청 전 확인 필요` 안내.
- 모르는 정보는 `unknown`으로 보존한다. 지역이 빠져 신뢰할 만한 추천이 불가능하면 **먼저 질문**한다. 사용자의 거주 지역을 임의로 추정하지 않는다.

**[가정·제안] 연령 UI:** 대략적인 연령대 입력으로 시작하되 서비스의 명시적 나이 경계에서 판정이 필요하면 정확한 나이를 선택적으로 확인한다.

### 4.2 핵심 플로우 [확정 기능, 화면 단계는 제안]

1. 사용자가 생활 불편을 평소 말로 입력한다.
2. 시스템이 LLM으로 지원 수요와 이미 말한 생활조건을 **추출**한다.
3. 거주 자치구·필요한 연령 정보가 없으면 간단히 확인한다. 이동 가능 여부 등은 실제 후보가 달라지는 경우에만 추가 확인한다.
4. 검수 DB에서 명백한 불일치 후보를 제외하고 적합도와 자격 확인 수준을 계산한다.
5. 추천 결과에 **이유·자격 확인 필요·접수 확인 필요·문의처·신청 방법·출처**를 표시한다.
6. 사용자가 부적합 이유 또는 '다른 추천'을 선택하면 **조건 수정/후보 제외 후 실제 필터·점수를 다시 계산**한다.
7. 사용자는 해당 기관에 직접 문의해 이용 가능 여부를 확인한다.

**[가정·제안] 카드 수:** 결과는 최대 3개, 검수 후보가 1~2개면 그만큼만 표시. 후보를 채우려고 서비스를 생성하지 않는다.

## 5. 추천 엔진 정책

### 5.1 역할 구분 [확정]

- **LLM:** 자연어 → 구조화된 의도·조건 추출; 검증된 근거를 이해하기 쉬운 문장으로 바꾸는 보조 역할.
- **직접 구현 로직:** 데이터 태그 기반 후보 조회, 하드 조건 필터, 적합도 계산, 우선순위, 피드백 재추천.
- **최종 이용 자격:** 기관 확인사항. AI 또는 추천 점수로 확정하지 않는다.

### 5.2 후보 판정 순서 [확정 원칙]

1. `review_status != reviewed` 또는 출처 불명확·정보 충돌 → **추천 제외**.
2. 사용자가 확인한 지역·나이·대상 조건과 공식 규칙이 **명확히 불일치** → **추천 제외**.
3. 조건을 확인하지 못했지만 명백한 불일치는 없고 지원 내용·방식이 맞음 → **확인 필요 후보**.
4. 공식 명시 대상 조건을 사용자 정보로 확인한 후보 → **우선 추천 후보**.
5. **현재 접수 상태만 미확인** → 제외하지 않고 `접수 가능 여부 확인 필요` 표시. 신청 가능하다고 표현하지 않는다.

**[확정] 질문 05의 우선순위:** 생활 적합도가 조금 낮더라도 **명시된 대상 조건을 충족하는 서비스 B**를, 적합도는 매우 높지만 중요한 자격조건이 미확인인 서비스 A보다 먼저 보여준다. 둘 다 실제 수혜나 현재 접수가 보장되지는 않는다.

### 5.3 정렬 알고리즘 [가정·제안: 최초 구현용]

**사전 그룹**을 점수보다 우선한다.

- `G1`: 공식 명시 대상 조건 중 필요한 비교를 완료했고 **알려진 불일치·미확인 핵심 자격조건이 없는** 후보.
- `G2`: 명백한 불일치는 없지만 **확인되지 않은 자격조건이 있는** 후보.
- `OUT`: 검수 불가, 출처 충돌, 알려진 필수조건 불일치.

`G1 → G2` 순으로 보여주고, **그룹 안에서만 적합도 점수로 정렬**한다. 공개 자료에 대상 조건 자체가 부족한 경우는 G2로 두고 확인 필요를 표시한다. 이 그룹은 신청 자격 승인 등급이 아니다.

**점수 예시(미승인):**

| 항목 | 예시 배점 | 산출 근거 |
|---|---:|---|
| 주요 생활 불편 ↔ 지원 분야 | 50 | `need_tags` 매칭 |
| 이동조건 ↔ 지원 제공방식 | 25 | `delivery_mode_tags` 매칭 |
| 알려진 생활조건과의 부합 | 15 | 검증된 대상·상황 태그 |
| 문의·신청 안내의 실행 가능성 | 10 | 실제 연락·신청 정보 확보 수준 |
| **합계** | **100** | 테스트를 위한 임시 수치 |

정량 항목이 미확인일 때 근거 없는 가점을 주지 않는다. 점수 동률이면 `service_id` 등 고정 키로 재현성 있게 정렬한다. **적합도 점수는 수급 가능성의 확률이 아니며, 화면에 숫자를 노출할지는 UX 단계에서 결정**한다.

**[미확인]** 실제 태그 분포와 검수 샘플에 따라 가중치·그룹 경계 조정 필요. 위 계산식을 확정 정책으로 간주하지 않는다.

### 5.4 재추천 [확정 기능 / 가정·제안: 피드백 값]

- 예: `방문하기 어려워요` → 이동조건 갱신 → 후보 재검색·재계산.
- 예: `내 상황과 맞지 않아요` → 이유를 선택/확인 → 충돌 조건 수정 또는 해당 후보 제외.
- 예: `다른 추천 보기` → 이미 보여준 `service_id`를 제외하고 남은 후보 계산.
- 새 후보가 없으면 **추가 추천 없음**을 보여주고 이전 결과·문의 방법 또는 조건 수정 경로를 남기는 방식 제안.
- 단순히 LLM이 설명 문장만 바꾼 경우는 재추천 성공으로 인정하지 않는다.

### 5.5 예외 정책 [확정 원칙 / 세부 표시 제안]

| 조건 | 처리 |
|---|---|
| 자치구 등 필수 조건 부족 | 필요한 정보만 다시 질문, 기본 지역 임의 지정 금지 |
| 불편 내용 해석 불가·LLM 실패 | 사용자에게 쉬운 확인 질문 또는 수동 선택 경로 제공 제안 |
| 명백히 불일치 | 후보 제외, 부적격 이유를 로그로 추적 |
| 미확인 자격·접수 여부 | 후보 유지 가능, 항목별 '확인 필요' 표시 |
| 검수 미완료·출처 충돌 | 실제 추천 목록에서 제외 |
| 검수된 후보가 없음 | 결과 없음과 공식 문의 경로 확인 안내(실제 확인된 경로만) |
| 서버/DB 오류 | 오류 안내 및 재시도, 가짜 결과 생성 금지 |
| 재추천 후보 소진 | 결과 없음·조건 수정 안내, 기존 추천을 신규 결과로 재포장하지 않음 |

## 6. API·인터페이스 계약 초안 [가정·제안]

**기술 스택·폴더·Git/PR 규칙은 이 문서에서 확정하지 않는다.** TEAM_WORKFLOW.md와 김동조님의 기술 검토를 우선한다. 아래 필드명·경로는 프론트/엔진 병렬 착수를 위한 계약 **제안**이다.

### 6.1 추천 요청 `POST /api/recommend`

```json
{
  "message": "혼자 지내는데 장을 보러 나가기가 어렵고 밥을 챙기기 힘들어요",
  "profile": {
    "district": "사용자가 선택한 자치구 코드",
    "age_years": null,
    "age_group": "70s",
    "lives_alone": null,
    "mobility": "unknown"
  },
  "excluded_service_ids": []
}
```

- `message: string` 입력한 불편; 필수.
- `profile.district: string|null` 실제 사용자 확인값; 추천에 지역이 필수라면 확인 후 실행.
- `age_years: number|null` / `age_group: string|null` 연령 확인 정도에 따라 입력.
- `lives_alone: boolean|null`, `mobility: mobile|limited|unknown` 조건부로 입력.
- `excluded_service_ids: string[]` 피드백으로 제외한 후보.

### 6.2 추천 응답 (필드 예시)

```json
{
  "status": "success",
  "data_mode": "verified",
  "interpreted": {"primary_need": "meal", "mobility": "unknown"},
  "missing_fields": [],
  "recommendations": [
    {
      "service_id": "검수된 내부 ID",
      "name": "검수된 실제 서비스명",
      "eligibility_group": "G2",
      "suitability_score": 75,
      "reason": "원문과 매칭 태그에 근거한 설명",
      "checks_required": ["세부 자격 확인 필요", "현재 접수 여부 확인 필요"],
      "contact": {"provider": "검수한 기관명", "phone": "검수한 번호"},
      "application_method": "검수한 신청·문의 절차",
      "official_source_url": "검수한 공식 URL",
      "source_checked_at": "YYYY-MM-DD"
    }
  ]
}
```

**주의:** 위 JSON의 값은 구조 예시로, **실제 서비스 정보·검증 결과가 아니다**. 응답의 `status`는 `success`, `need_input`, `no_match`, `error` 등을 제안하며, `data_mode=test`이면 프론트에도 테스트 상태를 전달한다.

### 6.3 재추천 요청 [가정·제안]

`POST /api/recommend/feedback` 또는 기존 추천 API 재호출 중 개발팀이 하나를 결정한다. 전달 조건: `message`, 수정된 `profile`, `excluded_service_ids`, `feedback={service_id, reason}`. 응답은 동일한 추천 카드 스키마를 사용한다. 서버 저장 세션·로그인은 MVP 필수로 합의된 바 없다.

### 6.4 보안·개인정보 처리 [가정·제안: 최소 안전 기준]

- 질문에 불필요한 이름·주민등록번호·상세 주소·의료기록을 요구하지 않는다.
- 입력 문장과 민감 조건을 외부 로그나 공개 저장소에 그대로 남기지 않는 방향으로 구현한다.
- LLM으로 전달하는 개인 정보는 구조화에 필요한 최소한으로 제한하고, 사용 서비스의 데이터 처리 조건을 기술 담당자가 확인한다.
- API 키는 브라우저 응답이나 Git 저장소에 노출하지 않는다.

## 7. UX·화면 설계 착수안 [가정·제안]

**공동 설계 전 임시 ID**이므로 팀에서 확정된 화면 ID가 있다면 그대로 교체한다.

| ID | 화면/상태 | 필수 구성 | 주요 행동·이동 |
|---|---|---|---|
| `SCR-01` | 생활 불편 말하기 | 큰 입력창, 생활 사례 문구, 자치구·간단 연령 입력 | `도움 찾기` → 구조화/필수정보 점검 |
| `SCR-02` | 추가 확인 | 한 번에 필요한 조건 하나, `잘 모르겠어요` 허용(조건에 따라) | 확인 → 추천 실행 또는 다음 필요조건 |
| `SCR-03` | 추천 결과 | 추천 카드, 이유, 확인 필요 상태, 문의·신청·출처, 피드백 | 전화·공식 안내 확인, 재추천 |
| `SCR-03` 상태 | 로딩·결과 없음·오류·재추천 | 상태 안내와 복구 행동 | 다시 시도·조건 수정·돌아가기 |

- **[확정 UX 원칙]** 생활 용어로 묻고 필요한 질문만 이어간다. 개인 상황 전체를 먼저 입력하도록 강요하지 않는다.
- **[가정·제안]** 큰 글자·명확한 버튼·한 화면 한 행동·쉬운 단어를 사용한다. 구체적인 숫자·색·배치는 손희영님의 UI 설계에서 정한다.
- **[확정]** 지원 내용과 **이용 자격 확인 필요** 및 **접수 여부 확인 필요**를 혼동하지 않게 표시한다.
- **[가정·제안]** 전화 연결은 전화번호가 공식 자료에서 검수된 경우에만 `tel:` 링크로 노출. 공식 URL이 없으면 임의 링크 생성 금지.
- 로딩/빈 결과/오류는 우선 별도 화면이 아닌 기존 화면 상태로 처리하는 안을 제안한다.

## 8. 수용 기준·테스트

### 8.1 기능 테스트 (P0)

| ID | 테스트 | 통과 조건 |
|---|---|---|
| QA-01 | 일반 생활 불편 입력 | 구조화된 주요 불편과 원문에서 확인 가능한 조건이 생성됨 |
| QA-02 | 지역·연령 누락 | 필요한 정보만 요청; 임의 자치구·정확한 나이 추정 없음 |
| QA-03 | 이동 가능/불가능 비교 | 동일한 불편이라도 실제 태그·점수·순위가 의미 있게 달라짐 |
| QA-04 | 공식 지역/대상 조건 불일치 | 알려진 부적격 후보가 제외됨 |
| QA-05 | 자격 미확인 A vs 확인 B | 점수가 더 높은 A라도 명시 대상 조건을 충족하는 B가 우선됨 |
| QA-06 | 현재 접수 여부 미확인 | 후보 유지 가능 + `접수 가능 여부 확인 필요` 표시 |
| QA-07 | 출처 없음·태그 충돌 | 해당 서비스가 실제 추천에서 제외됨 |
| QA-08 | 카드 정보 | 근거 있는 이유, 확인조건, 유효 문의처, 신청 경로, 출처 표시 |
| QA-09 | 피드백 후 재추천 | 후보 집합/순위가 실제로 재계산됨. 문장만 재생성하지 않음 |
| QA-10 | 추천 0건/1~2건 | 허위 3건 채우기 없음, 다음 행동 안내 |
| QA-11 | LLM·네트워크 실패 | 오류 구분, 사용자 재시도 또는 수동 확인 가능 |
| QA-12 | 데이터 모드 | Mock·미검수 결과를 실제 검증 데이터처럼 표시하지 않음 |

### 8.2 사용자 가치 테스트 [확정: 평가 방향 / 미확인: 실제 수행]

- 실제 시니어 또는 가족의 대표 불편 사례·관련 조사 근거를 기록한다.
- 테스트 참가자가 **“왜 이 서비스를 추천했는가 / 무엇을 확인해야 하는가 / 어디로 문의할 수 있는가”**에 답할 수 있는지 확인한다.
- 가능하면 같은 상황을 일반 검색·일반 LLM과 비교하되, 성능 우위가 입증되지 않은 경우 주장하지 않는다.
- 테스트 수행 여부·표본·결과는 완료 후 기록한다. **현재 사용자 검증 완료 아님.**

### 8.3 완료 정의(DoD)

**MVP 기능 완료:** 대표 시나리오에서 사용자 입력 → 실제 자체 필터·점수 처리 → 근거 포함 결과 → 조건 변화/피드백에 따른 재계산이 정상 시연된다.

**실데이터 검증 완료:** 2~3개 이상의 실제 공식 서비스 레코드가 주요 필드 및 출처 기준으로 검수되었고, 대표 시나리오 4개 게이트를 충족한다.

**시연 완료:** 사용자가 결과로부터 문의할 곳과 확인할 질문을 파악하며, 모르는 자격이나 접수 상태를 확정으로 오인하지 않는다. 오류·빈 결과 경로도 확인된다.

**구별:** Mock 엔진 통과 ≠ 실데이터 검증 완료 ≠ 실제 사용자 가치 검증 완료.

## 9. 구현 우선순위와 팀 인수인계

### 9.1 남은 시간의 핵심 순서

1. **데이터 선행 검증:** 후보 116건 중 대표 상황과 관련된 2~3개 이상을 공식 근거로 검수할 수 있는지 확인한다. 가능할 때만 대표 상황 확정.
2. **병렬 착수:** 동일한 최소 스키마를 기준으로 UX 화면 흐름과 추천 엔진을 별도 제작한다.
3. **첫 수직 시나리오:** 하나의 입력에서 조건 필터 → 순위 → 결과 카드까지 실제 연결한다.
4. **재추천과 예외:** 이동 가능성 등 조건 변화를 반영하고 실패/빈 결과를 테스트한다.
5. **출처·사용자 가치 검수:** 실데이터 근거와 문의 행동 가능성을 확인한다.

### 9.2 담당자별 시작 정보

| 담당 | 바로 진행할 일 | 첫 산출물 / 착수 조건 |
|---|---|---|
| **정민규** (Product·기획) | 핵심 시나리오·User Flow·P0 화면 목록·질문 정책·QA 인수조건 정리 | **팀 합의 후** 화면명세서. 미확정 화면 ID는 임시 표기 |
| **손희영** (팀장·UX/UI) | 입력·추가 확인·결과 카드·재추천·오류 상태 UI | 화면 목적·필드·전이의 최소 합의 후 Figma 기본 UI 착수 |
| **김동조** (기술·데이터/개발) | 데이터 원문/필드 검수, 정규화, 태그·필터·점수·재추천, API 계약 검토 | 검수 레코드 2~3건 및 I/O 스키마 초안; 독립 기술 검증은 바로 진행 가능 |

이 표는 **기존 역할**을 기준으로 한 인수인계이며 상세 파일 분담·협업 규칙·스택을 새로 확정하지 않는다. 공동 설계 지침과 TEAM_WORKFLOW.md를 따르되 해당 문서 내용은 확인 전 추측하지 않는다.

## 10. 결정 기록 및 남은 이슈

### 10.1 인터뷰 확정 사항

1. **고령 1인 가구**를 핵심 페르소나로 한다.
2. 지원제도를 모르거나 이용 과정에서 막히는 **일상생활 불편**을 해결한다.
3. **상황에 맞는 도움·추천 이유·확인 조건·문의처**를 알게 하는 경험이 핵심 가치다.
4. 전체 제품은 생활지원 전반으로 확장하고 MVP는 **대표 상황 1개 깊이 구현(A안)**으로 한다.
5. 대표 상황은 **사용자 문제 근거 + 공식 서비스 2~3건 검수 + 상황별 추천 차이 + 문의 행동 가능성**을 모두 충족해야 한다.
6. 공식 사실·명확한 파생 사실만 태그로 사용하고 **검수한 정보만 실제 추천**한다.
7. **지원서비스 상세정보**와 **시설 연결정보**는 용도를 분리한다.
8. **LLM은 해석·쉬운 설명**, 자체 코드는 조건 필터·점수·재추천을 담당한다.
9. **명시된 조건에 부합하는 서비스 B를 자격 미확인 A보다 우선**한다. 단 최종 이용 자격은 보장하지 않는다.
10. **접수 여부 미확인 서비스는 표시를 달아 추천 가능**하다.
11. 최초에는 **생활 불편·자치구·간단한 연령**, 필요할 때만 독거·이동 조건을 확인하며 민감 정보는 강제하지 않는다.
12. 명백한 부적격은 제외, 불명확한 자격은 **확인 필요**, 검수 실패·정보 충돌은 추천 제외한다.

### 10.4 주요 리스크와 대응

- **개별 서비스 검증 부족:** 원천 116건을 추천 가능 건수로 포장하지 않는다. 검수되는 서비스와 핵심 사용자 문제가 동시에 성립하는 대표 상황으로 팀이 확정한다.
- **태깅 오류·자격 오인:** 태그별 원문 근거·검수 상태를 남기고 불명확한 자격은 별도 표시한다.
- **LLM 실패 또는 환각:** 원문 외 서비스·자격·연락처를 생성하지 않으며 구조화 출력 실패를 처리한다.
- **개발 시간 부족:** 확정된 핵심 시나리오를 먼저 수직 통합한다. 기능 축소나 범위 변경이 필요하면 팀 승인 후 문서에 기록한다.
