## 1. 제품 개요

### 1.1 한 줄 정의 [확정]

**혼자 생활하는 시니어가 한국어 음성·텍스트로 AI와 대화하면서, 현재 시간·위치·관심사·이동 부담에 맞는 문화활동 또는 여러 장소를 잇는 나들이 코스를 찾고, 실제 운영·이동·예약 정보를 확인해 선택하도록 돕는 모바일 웹 서비스.**

### 1.2 해결할 사용자 문제 [확정]

1. **선택의 어려움:** 문화행사·전시·공연·체험 정보가 흩어져 있어 무엇을 할지, 오늘/원하는 날짜에 실제 가능한지 판단하기 어렵다.
2. **외출 부담:** 가까워 보여도 실제 걷는 시간, 이동 경로, 운영시간, 예약·참여 조건이 불명확하면 외출 결정을 망설이게 된다.
3. **입력 부담:** 세부 조건을 화면에서 여러 번 설정하거나 앱 내 다른 메뉴를 골라 이동하는 일이 번거로울 수 있다.

> 핵심 가치는 ‘AI가 장소를 많이 추천한다’가 아니라 **사용자의 조건에서 실제로 선택 가능한 후보를 근거와 확인 필요 사항까지 포함해 좁혀 주는 것**이다.

### 1.3 대표 사용자 [확정/미확인 구분]

- **[확정]** 혼자 생활하는 시니어를 대표 사용자로 설정한다. 디지털 숙련도·보행능력이 모두 낮다고 전제하지 않는다.
- **[확정]** 문화 외출 의사는 있지만 어떤 활동을 선택할지 또는 이동 부담을 감당할지 판단하기 어려운 상황에 집중한다.
- **[미확인]** 초기 검증 연령대, 서울 내 대표 지역, 주로 사용할 스마트폰·브라우저, 실제로 확인 가능한 도보/편의 데이터의 범위.

### 1.4 목표 및 제외 범위

| 구분 | 요구 |
|---|---|
| **사용자 목표 [확정]** | 대화로 외출 조건을 설명하고, 개별 문화장소 또는 요청한 문화코스를 추천받아 정보를 확인하고 선택한다. |
| **제품 목표 [확정]** | 하나의 진입 화면에서 조건 수집·음성 대화·추천·수정·재추천까지 연결한다. |
| **포함 [기준 요구]** | 개별 장소 추천, 2~3곳 문화코스, 지도·카드, 운영/가격/예약/이동 근거, 후보 선택 및 저장, 계정·온보딩·내 정보, FAQ/지식 응답, 실패·복구. |

### 1.5 성공 기준(사용자 관점) [제안 — 수치 목표 미합의]

- 사용자가 **말 또는 글로** 출발지·시간·관심/이동 조건을 전달하고, AI의 필요한 보완 질문에 답하여 결과까지 진행할 수 있다.
- 실제 공식 정보 기반 후보를 지도·카드에서 비교하고, 왜 추천했는지 및 무엇을 확인해야 하는지 이해할 수 있다.
- 조건 변경 후 **수정된 조건이 실제 후보/루트에 반영**된다. 기존 확정 저장값은 임의로 바뀌지 않는다.
- 음성을 사용할 수 없는 기기에서도 텍스트/직접 입력으로 동등한 핵심 기능을 이용할 수 있다.
- 정량 성공 지표(첫 추천까지 시간, 시연 소요시간, 사용자 테스트 통과 기준)는 팀 합의 전까지 임의 확정하지 않는다.

## 2. 사용자에게 보이는 서비스 구조 [Q1~Q5 확정]

**핵심 진입 메뉴는 ‘나들이 찾기’ 하나다.** 사용자가 시작 화면에서 ‘즉시 추천’과 ‘코스 만들기’를 먼저 선택할 필요가 없다. 단일 입력 화면에서 AI 대화가 요청 의도를 파악해 두 결과 유형으로 나눈다.

```text
첫 방문 안내/홈
  └─ [나들이 찾기]
       └─ 출발지 · 출발 날짜/시각 · 종료 시각 + [더 원하는 게 있으세요?]
            ├─ 화면에서 조건 직접 입력/수정
            └─ 한국어 AI 음성·텍스트 대화
                 └─ AI가 누락·모호한 필수 조건만 질문 → 조건 확인
                      ├─ 개별 문화장소 요청 → 추천 결과: [위 지도 + 아래 카드]
                      │    ├─ 지도 마커 ↔ 카드 포커스 변경
                      │    ├─ 장소 상세·공식 정보·길찾기
                      │    ├─ 후보 선택 → [내가 고른 장소] 계정 저장
                      │    └─ [조건 바꾸기] → 기존 입력/AI 대화로 복귀 → 재추천
                      └─ 여러 장소 코스 요청 → 코스 결과: [방문 순서 + 지도 + 장소별 카드]
                           ├─ 장소 제외·조건 변경·코스 재생성
                           ├─ [내 나들이 코스] 계정 저장·재접근
                           └─ [조건 바꾸기] → 기존 입력/AI 대화로 복귀

공통: 저장한 결과 재접근/내 정보/Google 로그인/관심사 설정/오류·빈 결과
```

**결과 화면에는 별도 AI 대화창을 추가하지 않는다 [확정 Q5].** 조건을 변경하고 싶다면 `조건 바꾸기`로 원래 입력 화면의 대화 영역에 돌아온다. 이전에 확인한 위치·시간·관심사·대화 맥락은 보존하고 변경한 내용만 새 요청에 반영한다.

### 2.1 대표 사용 시나리오 — 개별 장소 추천

1. 사용자가 홈에서 **나들이 찾기**를 누른다.
2. “오늘 오후에 가까운 전시를 보고 싶은데 많이 걷기는 싫어요”라고 말한다.
3. AI는 출발지·종료시각 등 **아직 필요한 정보만** 확인한다. 사용자가 말한 시각/위치는 같은 화면 입력 필드에 반영된다.
4. AI가 이해한 조건을 보여주고 사용자가 수정·확인한다.
5. 서비스는 실제 문화정보·운영·이동 조건을 조회·판정한 뒤, **상단 지도 + 하단 장소 카드**로 소수 후보를 제시한다.
6. 사용자는 카드를 넘기고 지도와 가격·운영·예약·확인 필요 사항을 확인한 뒤 장소를 선택한다.
7. “더 가까운 곳”이 필요하면 **조건 바꾸기**로 돌아가 AI와 대화를 이어 가고 재추천한다.

### 2.2 대표 사용 시나리오 — 여러 장소 코스 추천

1. 사용자가 같은 **나들이 찾기**에 들어와 “다음 주 화요일에 전시랑 체험 두 군데를 이어서 보고 싶어요”라고 말한다.
2. AI는 **방문 날짜·출발 장소·시작시각·종료 경계** 중 불충분한 항목만 질문한다.
3. 사용자가 확인한 조건을 바탕으로 장소 **2~3곳**을 방문 순서로 연결한 코스 **1개**를 생성한다.
4. 장소별 운영·예약·예상 체류·구간 이동과 확인 필요 항목을 **코스 지도 및 장소/시간 정보**로 보여준다.
5. 사용자는 장소를 제외하거나 조건을 바꿔 재생성할 수 있으며, 마음에 든 코스를 **내 나들이 코스**에 저장한다.

### 2.3 대표적인 음성 상호작용 [예시 문구, 고정 대본 아님]

- 사용자: “청량리역에서 오후 두 시쯤 출발해서 전시를 볼 수 있을까요?”
- AI: “몇 시까지 돌아오셔야 하나요?”
- 사용자: “다섯 시 전까지요. 많이 걷는 건 힘들어요.”
- AI: “걷는 시간을 꼭 제한해야 할까요, 아니면 가까운 곳을 우선 보여드리면 될까요?”
- 사용자: “가까운 곳이면 좋겠어요.”
- 시스템: 출발지·시간·걷기 선호를 화면 필드와 조건 요약에 반영하고 확인 후 결과 생성.

여기서 AI는 사용자의 보행능력·건강 상태를 임의 진단하거나, “가깝다”는 이유만으로 실제 도보 가능성을 보장하지 않는다.

## 3. 기능 요구사항 — 처음 보는 사람도 구현 목표를 알 수 있는 기준

**우선순위:** 아래 ‘핵심’은 이 제품이 목표로 하는 기본 기능. 해커톤 기간 내 단계별 구현 우선순위와 재사용 가능 범위는 팀이 별도로 확인해야 하며, 이 문서가 기존 기능 삭제를 자동 승인하지 않는다.

| F16 | 결과→조건 수정 | 결과 화면의 ‘조건 바꾸기’ | 원래 입력·대화로 복귀하고 확인된 조건·대화·저장 선택 보존 | **확정 Q5** |
| F17 | 반복 추천·비회원 이용 | 추가 추천·재추천·대화·코스 수정 | 추천 횟수 때문에 로그인 강제하지 않음 | **확정 Q1** |
| F18 | 계정·최초 선호·내 정보 | Google 로그인, 관심사 6종, 자유 선호, Skip | 장기 저장/개인화 시 로그인, 선호 관리·초기화와 저장한 선택 분리 | 기준 요구/Q1 변경 |
| F19 | AI 문화정보 Q&A | 장소·이용/서비스 질문 | 근거 있는 범위에서 답변. 불확실하면 확인 필요·공식 경로 제시 | 기준 요구 |
| F20 | 실패·대체 입력 | 음성 실패·지도 미표시·API 오류·추천 0건 | 유형 구분, 재시도·텍스트 전환·조건 복귀·이전 선택 보존 | 기준 요구/음성 추가 |

### 3.1 장소·문화활동 범위 [기준 요구]

- 포함되는 유형: **직접 참여 체험, 공연, 전시, 문화·역사 장소 방문, 축제·행사**.
- 관심사: **전통문화, 역사·궁궐, 문화 체험, 미술·전시, 공연, 축제·이벤트**(복수 선택 또는 미선택).
- 맛집 탐색·일반 쇼핑·스포츠·레저·종합 여행 플래너는 이번 제품의 핵심이 아니다.
- 참여 연령·보호자 동반·예약 사전 신청 등은 실제 이용 가능한지에 직접 영향을 주므로 중요하다.

### 3.2 추천 판정·정보 신뢰 [기준 요구 + Q2 확정]

- **Hard(필수):** 사용자가 분명히 정한 상한·제외조건, 공식 운영 종료, 참여 대상 조건 충돌. 만족하지 못하는 후보를 ‘조건 충족’으로 보여주지 않는다.
- **Soft(선호):** 짧게 걷기 선호, 관심사·예산 선호 등은 가능한 후보를 정렬하는 신호. 선호를 사용자 승인 없이 절대 제한으로 바꾸지 않는다.
- **모호한 이동 제약:** “많이 걷기는 어려워요”처럼 안전·선택에 중요한데 불명확하면 AI가 추가로 확인한다. 필요 이상의 건강정보를 요구하지 않는다.
- **결과 상태:** `조건 충족` / `추가 확인 필요` / `조건 완화 대안`. 내부에서 제외한 후보는 정상 결과에 끼워 넣지 않는다.
- **추천 근거:** 확인 가능한 이유만 장소별 **0~2개**. AI가 운영시간·예약가능·무료·도보시간·무장애 여부를 만들어내지 않는다.
- **미확인 ≠ 무료/예약 불필요/이용 가능 보장.** 방문 계획시간/예상 체류시간과 실제 시설 운영시간을 구분한다.
- 실제 후보가 적으면 숫자를 억지로 맞추지 않는다. Hard 조건에 맞는 곳이 없으면 **0건과 조건 조정 제안**을 명확히 보여준다.

### 3.3 장소 카드 및 코스 결과에 필요한 데이터 [기준 요구]

| 정보 | 표시 원칙 |
|---|---|
| 장소명·유형·주소·좌표 | 실제 출처의 값. 좌표가 없으면 핀을 임의 생성하지 않는다. |
| 사진/아이콘 | 가능한 경우 제공. 사진 부재가 위치/운영 정보 누락을 감추지 않음. |
| 운영일·관람시간·행사기간 | 실제 적용 날짜와 대조. 오래된 정보/확인 불가 표시. |
| 가격·예약·참여대상 | 무료·예약 불필요·성인 참여 가능 등을 추정하지 않음. |
| 거리·이동시간 | 확인 가능한 실제 경로 기반 값만 제공. 직선거리를 도보시간으로 오인하지 않음. |
| AI 추천 이유·상태 | 확인된 근거에서 생성하고 조건 충족/확인 필요/대안 분리. |
| 공식 상세·길찾기 | 확인된 URL만 노출. 자체 예약·내비게이션으로 오인시키지 않음. |
| 코스용 추가 정보 | 방문 순서, 각 장소 체류시간/도착 예상, 구간 이동, 전체 비용의 확인 여부. |

**UI 확정 원칙**

- 개별 추천 결과의 지도는 **위**, 카드 캐러셀은 **아래**다. 지도 마커 선택과 카드 포커스는 양방향 연동.
- 결과 화면에서 조건을 바꾸려면 **입력 화면으로 돌아간다**. 별도의 결과 화면용 채팅 패널은 없다.
- 코스 결과는 단순 개별 장소 카드 모음이 아니라 **방문 순서와 일정/이동 정보**를 보여준다.
- 장기 저장은 선택·확인 후 계정 기능으로 연결한다. OAuth 취소 시 입력·임시 결과를 잃지 않게 한다.
- 시니어 친화: 충분한 글자·터치 영역·명료한 상태 표시·쉬운 한국어·음성 재생 중지·텍스트 대체.

## 5. 음성·AI 대화 명세

### 5.1 확정 동작

1. 사용자가 **한국어 음성 또는 텍스트**로 조건·질문을 전달한다.
2. AI는 사용자 발화의 의도(개별 장소 vs 다중 장소 코스)와 조건(위치·날짜·시간·관심사·이동 선호·예산·제외)을 파악한다.
3. 구조화 필드에 없는 필수 정보만 질문하며 **이미 확인한 값은 반복 질문하지 않는다**.
4. 음성에서 얻은 위치·시간은 **화면의 동일한 필드와 동기화**하고, 수정된 필드의 최신값을 실제 추천 요청에 사용한다.
5. AI 답변은 화면에 **텍스트로 표시하고 음성으로도 안내**한다. 음성을 사용할 수 없더라도 텍스트/직접 입력으로 동일 목적을 달성한다.
6. 코스 요청은 독립 서비스 메뉴가 아니라 **같은 통합 대화 안에서 분기**한다.
7. 결과 화면의 `조건 바꾸기`로 돌아오면 **조건·대화 맥락을 유지**한다.

### 5.2 구현 방식 [제안, 미확정]

- **턴 기반 대화**: 마이크 누르기 → 인식(STT) → 필요 시 전사 텍스트 수정 → AI 응답 → 음성 출력(TTS) → 다음 턴. 상시 마이크 청취·실시간 끼어들기는 확정된 필수가 아니다.
- 음성 상태: 대기 / 듣는 중 / 인식 확인 / 처리 중 / 읽는 중 / 오류. 음성과 텍스트 처리의 중복 전송 방지.
- 실패 시: 권한 거부·브라우저 미지원·인식 실패·무음·TTS 장애·네트워크 장애를 나누어 안내하고 텍스트 입력으로 이어감.
- STT/TTS 선택(API, 브라우저 내장, 비용, 개인정보 처리)은 팀 기술 검증 필요. 사용자 발화 원본을 자동 녹음 저장한다고 가정하지 않는다.

## 6. 데이터·기술 연동 및 운영 경계

### 6.1 데이터·지도 역할 [기준 요구, 실제 새 서비스 접근 여부 미확인]

| 역할 | 확인·검증 대상 | 제품 정책 |
|---|---|---|
| 문화 장소·행사·전시 | TourAPI, 서울문화포털 등 | 기간·위치·공식 링크·운영조건 확인. 실제 응답 품질은 별도 검증 |
| 도보 경로·이동 | Tmap 등 신뢰 가능한 경로 조회 | 구간 이동시간·거리의 근거 표시, 미확인 보행 편의 단정 금지 |
| 지도/외부 길찾기 | Naver Maps SDK·외부 지도 링크 | 지도 핀·경로/길찾기, 좌표·경로 미확인 fallback |
| 환경 보조 | 기상청, AirKorea | 날씨·대기질을 참고하되 공식 행사 취소 여부는 임의 추정 금지 |
| 문화/서비스 질문 | 근거가 있는 문서/FAQ·RAG | 확인된 내용만 답변, 없으면 공식 확인 권고 |
| 계정·장기 선호 | 인증 및 사용자 저장소 | 최소 정보·계정별 분리, 임시 추천과 장기 기록 구분 |

### 6.2 논리적 서비스 계약(기술팀 확정 전 개념 정의)

**입력 조건:** `start_location`, `start_at`(날짜+시각), `end_at`, `interests`, `budget_limit`, `mobility_preference`, `hard_constraints`, `excluded_places`, `existing_plans`, `request_kind`(place/route), `confirmed_fields`, `conversation_context`.  
**대화 응답:** `assistant_text`, `need_clarification`, `missing_fields`, `updated_condition_draft`, `request_kind`, `ready_to_search`.  
**추천 결과:** `candidates[]` 또는 `route(stops[])`, `status`, `reasons`, `facts`, `checks_required`, `official_url`, `source_checked_at`.  
**권한/상태:** 익명 세션 임시 조건/결과, 로그인 계정의 장기 선호 및 `My Pick`/`My Route` 구분.

필드명은 **논리적 계약 예시**이며 기존/신규 API 실제 스키마 확정값이라고 주장하지 않는다. 기술 담당자가 실제 계약을 제시할 때 연동한다.

### 6.3 주요 서비스 운영·보안 원칙

- API 조회 실패·유효한 추천 0건·입력 형식 오류는 **서로 다른 상태**로 처리.
- 개인정보 수집 최소화. 위치·선호·음성 전사 및 원본 음성의 수집/보관/삭제 범위는 구현 전 정의.
- API Secret/개인 정보가 프론트/공개 로그/저장소에 노출되지 않게 한다.
- 후보가 수정 전 결과와 다르면 **최신 확정된 조건의 결과**임을 알 수 있어야 한다. 오래된 비동기 응답이 최신 상태를 덮어쓰지 않아야 한다.
- 현재 선택을 확정한 것과 실제 방문/예약·결제 여부를 구분한다.

## 7. 범위·개발 착수 구분

**중요:** 이 PRD는 **기본 기능 전체를 요구사항에 포함**한다. 다만 이전 프로젝트의 소스가 실제로 사용 가능한지, 해커톤 잔여 기간 안에 모든 기능을 새로 구현할 수 있는지는 **확정된 사실이 아니다**. 제품 기본선의 ‘유지’와 이번 대회 내 구현·검증의 ‘완료’를 혼동하지 않는다.

| 작업 단위 | 사용자 가치 | 현재 상태/처리 |
|---|---|---|
| **핵심 수직 흐름**: 단일 홈→음성/텍스트 조건→AI 확인→실제 개별 추천→지도+카드→조건 수정 | 제품 핵심 가치를 최소 시연으로 검증 | **착수 우선 제안**. 다른 기능을 PRD에서 삭제한다는 의미 아님 |
| **코스 전체 흐름**: 같은 입력에서 코스 요청→조건 확인→2~3곳 코스→수정/저장 | Q3 결정 및 기존 서비스 핵심 기능 유지 | **기준 요구**. 구현 순서·재사용 허용·검증 일정 팀 협의 필요 |
| My Pick/Route 및 Google 계정·선호·내 정보 | 저장/재방문·개인화 | **기준 요구**. 계정 장기 저장에 로그인 적용(Q1) |
| 실데이터 신뢰·이동 조건 | 단순 AI 추천과의 실질적 차별성 | **필수 품질 요구**. 외부 데이터 실제 근거 확보 범위 미확인 |
| STT/TTS 안정성·대체 입력 | 시니어 핵심 이용 방식 | **Q3~Q4 확정 목표**. 세부 기술·지원 기기 미확인 |

**기능 삭제·범위 축소는 팀이 별도 합의해야 한다.** 이 표는 독립적 착수를 돕기 위한 구현 순서의 제안이지 미승인 MVP 축소 결정이 아니다.

# 부록 B. 과거 KONNECT QA의 재검증이 필요한 주요 문제

이 목록은 **과거 특정 조건의 관찰**이며 새 서비스 구현 오류를 입증하지 않는다.

- 시간: 기존 프론트 60분 vs 서버 30분 조건 충돌.
- 추천: 무료 Hard 조건인데 가격 미확인 후보가 나타나는 경우, 운영시간·예약/참여 대상 근거가 잘못 표시된 사례.
- 루트: 대화에서 지정한 날짜/시간과 다른 값으로 생성된 사례, 2~3곳 기준인데 5곳을 구성한 사례, 체류/이동 근거 미검증.
- 계정: 비회원 두 번째 추천 로그인 Gate의 불일치(※ 현재 정책에서는 해당 Gate를 **폐기**), 저장 과정 일부 오류와 로그인 후 상태 복귀 미확인.
- 지도/모바일: 경로 미확인 fallback, 모바일 브라우저별 터치/키보드/화면 크기 QA 보강 필요.
- 상태 보존: 조건 변경, 코스 장소 제외/복구, 사용자 선택의 임시/장기 저장 구분에 대한 회귀 QA 필요.

# 부록 C. 의사결정 요약 및 문서 변경 이력

**Q1 [확정]** 비회원도 반복 추천·음성 대화·코스 이용 가능. 계정 장기 저장/개인화 이력 활용 시 로그인.  
**Q2 [확정]** 걷기 선호(Soft)와 필수 제한(Hard) 구분, 모호하고 중요한 제약은 추가 질문.  
**Q3 [확정]** 사용자에게 보이는 서비스 진입은 ‘나들이 찾기’ 하나. 코스 대화·생성·지도·저장은 유지.  
**Q4 [확정]** 출발지/시각을 말하면 입력 필드에 반영하고 수정·확인 가능.  
**Q5 [확정]** 결과에 별도 대화창 없음. 조건 바꾸기→원래 입력 화면/대화 복귀, 맥락·선택 보존.  
**UI 임시:** 나들이 찾기 / 더 원하는 게 있으세요? / 내가 고른 장소 / 내 나들이 코스 / 내 정보.  
**v0.3 → v0.4 변경:** KONNECT 변경·승계 중심 구조 → **독립된 제품 소개·대표 사용자 시나리오·기능표·화면·서비스 계약·완료기준** 중심으로 재편. 기존 구현/QA의 상세 역사와 경로는 부록으로 이동. *신규 사용자 합의나 기능 삭제는 없음.*
