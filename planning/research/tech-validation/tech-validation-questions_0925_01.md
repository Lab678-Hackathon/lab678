## 1. 가격·예산 구현 후속 — D-09·D-10

9/25 Product 기준은 다음과 같이 확정됐다.

- 복수 좌석가격은 확인된 일반 판매가격 범위로 표시하고 최저가 하나를 대표가격으로 쓰지 않는다.
- 적용 여부가 불명확한 조건부 할인은 일반 최저가격이나 예산 충족 근거로 쓰지 않는다.
- 유료이나 금액을 확정할 수 없으면 `가격 확인 필요`로 처리한다.
- 명시적 예산 상한은 Hard Condition이며, 확인된 일반 이용 가능 가격 중 하나라도 상한 이하여야 통과한다.
- 조정 가능한 예산은 Soft Condition이며 초과 후보는 필요 시 조건 완화 대안으로만 제시한다.
- 공식 가격은 KRW를 기준으로 하고, 선호통화 예산은 기준환율로 KRW 환산해 비교한다.

### Tech 확인
1. 자유기술 가격 문자열에서 **일반 판매가격 / 조건부 할인 / 부분 유료 / 금액 미확인**을 어느 수준까지 안정적으로 분리할 수 있는가?
2. 복수 좌석가격의 원문을 보존하면서 일반가격 범위 또는 가격 목록을 구조화해 예산 판정에 사용할 수 있는가?
3. Hard 예산과 Soft 예산을 위 Product 기준대로 Rule/Data layer에서 분리 판정할 수 있는가?
4. 선호통화 예산 → KRW 비교를 위해 MVP에서 사용할 환율 소스, 갱신 주기, 캐시 방식은 어떤 구성이 적절한가?
5. 환산값을 사용자에게 참고값으로 보여주기 위해 응답에 **기준환율 시점/통화/환산값**을 함께 전달할 수 있는가?

### Product가 원하는 답변
- 구현 가능 / 조건부 가능 / MVP 부담 큼
- 자동 파싱 실패 시 Fallback 방식
- 추가 라이브러리·외부 API 필요 여부
- MVP에서 우선 구현할 최소 범위

**상태:** **미확인** — Tech 세부 구현 회신 대기

## 2. Agent·RAG·Memory PoC — D-14

Product 기준:

- Rule/Data는 운영기간·가격상태·시간충돌·Hard Constraint·숫자 비교처럼 결정론적 판정을 담당한다.
- RAG는 검증된 소스에서 현재 판단에 필요한 근거를 검색·참조한다.
- Agent는 사용자 Context 구조화 → 필요한 정보·도구 선택 → RAG·Rule 결과 확인 → UNKNOWN 판단 → 후보/루트 구성·재판단 → 설명까지 다단계 흐름을 조정한다.
- 단순 추천문 생성만으로는 핵심 Agent 증빙으로 보지 않는다.

### Tech 확인
1. MVP PoC에서 Agent가 **다음 조회나 도구를 동적으로 선택**하는 지점을 어디에 둘 수 있는가?
2. 조회·Rule 결과에 따라 다음 단계가 달라지는 **분기**를 어떤 방식으로 구현할 수 있는가?
3. 1차 후보 또는 루트 구성 실패 시 다른 후보 조회·재조합 또는 명확한 Fallback으로 이어지는 **재판단 흐름**을 구현할 수 있는가?
4. Agent가 실제로 수행한 tool/query 선택, Rule 결과, 분기, 재탐색을 **로그·trace·캡처 등으로 증빙**할 수 있는가?
5. 즉시 추천(A)와 문화루트 B 중 어느 흐름을 1차 Agent PoC로 잡는 것이 공수 대비 증빙이 가장 명확한가?
6. RAG를 별도 기술 요소로 증빙하려면 어떤 검색 대상·retrieval 흐름이 최소 단위로 적절한가?

### Product가 원하는 답변
- 1차 PoC 추천 흐름
- 사용할 framework/workflow 방식 제안
- 실제 tool/RAG/Rule 연결 범위
- 후속 PoC 시점에 보여줄 수 있는 최소 증빙
- 구현 리스크와 보류할 범위

**상태:** **후속검증** — 9/30 멘토링 범위에서는 제외. MVP 구현 진행 이후 PoC 범위·증빙 방식을 확인

## 3. Context/Data 4층 구현 후속 — D-15

Product 기준:

1. Request Context
2. Trip Context
3. User Preference
4. Product Analytics

- Request Context는 현재 요청에 쓰며 자동 장기 보관을 전제로 하지 않는다.
- Trip Context는 같은 여행 안에서 재사용하되 여행 종료·새 여행·Reset 시 자동 적용을 끝낸다.
- User Preference는 사용자가 직접 제공·확인한 안정적 선호만 여행 간 재사용하며 수정·초기화 가능해야 한다.
- 클릭·조회 행동만으로 장기 선호에 자동 승격하지 않는다.
- Product Analytics는 개인화 Memory와 목적을 분리한다.
- Product는 DB·인증·저장소 종류 자체를 고정하지 않는다.

### Tech 확인
1. 4개 층을 MVP에서 물리적으로 모두 분리 저장하지 않더라도 **의미와 재사용 범위가 섞이지 않게 구현**할 수 있는 최소 구조는 무엇인가?
2. Trip Context가 여행 종료·새 여행·Reset에서 자동 적용을 멈추도록 어떤 기준값이나 lifecycle을 두는 것이 적절한가?
3. 사용자가 확인한 User Preference만 여행 간 재사용하고 수정·초기화 가능하게 하는 최소 구현은 무엇인가?
4. 클릭·조회 로그를 Product Analytics에는 남기되 User Preference로 자동 승격하지 않도록 분리할 수 있는가?
5. 이번 4주 MVP에서 실제 구현해야 할 부분과 문서상 설계·후속으로 남길 부분을 어떻게 나누는 것이 적절한가?

**상태:** **미확인** — Tech 회신 대기. LF-09의 현재 선택 상태 저장·복원 세부는 `0926_01`에서 별도로 좁혀 확인한다.

## 5. 기존 `0923_01`에서 계속 추적하는 잔여 확인사항

`tech-validation-questions_0923_01.md`에는 이미 **9/25 Tech 1차 회신**이 반영되어 있고, Product에서도 그 회신을 바탕으로 추가 확인을 진행했다.

특히 가격 영역은 Product가 서울문화포털 문화행사 API **200건을 추가 실측**해 복수 좌석가격, 유료·금액 미확인, Hard/Soft 예산 경계를 확정했다. 따라서 `0923_01`의 질문 전체를 다시 요청하는 것이 아니다.

아래는 **1차 회신과 Product 추가 실측 이후에도 구현·PoC 단계에서 실제 확인이 남아 있는 항목만** 계속 추적한다.

- 예상 이동시간의 구체 산출 방식·공수 → LF-07·LF-08 경로 구현 세부는 `0926_01`로 이관
- 기존 일정 AI 구조화의 실제 품질, 부분 수정·재반영
- 자유기술 필드의 실제 파싱 품질(PRO_TIME·USE_FEE 등)
- 소스 간 중복 매칭은 현재 8/11 소표본 결과가 있으므로, 실제 구현상 필요할 때 추가 검증

현재 확보한 종로구·중구 6,832건의 필드 채움률 자체는 1차 근거로 사용하고, **일반적인 추가 채움률 실측을 이번 9/27 요청의 필수 과제로 두지 않는다.**

9/28 기준 위 잔여 항목은 **이미 완료된 질문을 반복하지 않고 구현·PoC에서 실제 확인이 필요한 범위만 후속 추적**한다.
