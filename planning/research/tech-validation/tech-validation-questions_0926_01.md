## 1. 지도·도보 경로 구현 확인 — LF-07·LF-08 / D-12 후속

### Product 기준
- KONNECT 내부 지도는 **의사결정을 위한 이동 부담 확인**이며 턴바이턴 내비게이션이 아니다.
- 기본 이동 판단은 도보 중심이다.
- 즉시 추천(A)은 현재 위치 → 후보 장소의 이동 부담을 보여준다.
- 특정 날짜 문화루트(B)는 시작점 → 장소 1 → 장소 2 → 장소 3의 순서와 구간별 이동 부담을 보여준다.
- 실제 도보 경로선이 확보되면 경로선을 표시한다.
- 실제 경로선이 없으면 가짜 직선을 실제 도보 경로처럼 표시하지 않는다.
- 대중교통 상세 길찾기는 외부 지도 앱 연결을 우선한다.

### Fallback 기준
1. 실제 경로선 + 신뢰 가능한 거리·시간 확보  
   → 경로선 + 거리 + 예상 도보시간
2. 경로선 없음, 거리·시간은 신뢰 가능  
   → 출발/도착 또는 구간 핀 + 거리·시간 + 외부 지도
3. 거리·시간도 신뢰하기 어려움  
   → 핀 + 외부 지도 확인 안내

### Tech 확인
1. MVP에서 사용할 수 있는 도보 경로선·거리·예상시간 데이터 소스 또는 API 후보는 무엇인가?
2. 즉시 추천(A)의 현재 위치 → 목적지 한 구간과 특정 날짜 문화루트(B)의 다구간 경로를 각각 어느 수준까지 구현할 수 있는가?
3. 특정 날짜 문화루트(B)에서 구간별 거리·예상시간과 전체 순서를 같은 응답 구조로 제공할 수 있는가?
4. 경로 데이터가 없거나 호출 실패 시 위 Fallback 2·3을 안정적으로 분기할 수 있는가?
5. 경로선·거리·시간의 신뢰 여부를 UI가 구분할 수 있도록 상태값 또는 provenance를 전달할 수 있는가?
6. 호출 제한·비용·라이선스 때문에 Product가 원하는 최소 지도 경험을 MVP에서 구현하기 어려운 제약이 있는가?
7. 9/30 멘토링 전에 **실제 동작 또는 PoC로 보여줄 수 있는 최소 범위**는 어디까지인가?

### Product가 원하는 답변
- 구현 가능 / 조건부 가능 / MVP 부담 큼
- 추천 데이터/API 후보
- A와 B 각각의 최소 구현 범위
- 데이터 부족 시 Fallback
- 9/30 전 PoC 가능 범위와 남길 리스크

### 9/28 Tech 회신
- 즉시 추천(A)의 지도·경로 구현을 우선하고 이후 특정 날짜 문화루트(B)를 시도한다.
- 특정 날짜 문화루트(B)는 구현 가능할 것으로 예상하며, 초기 테스트는 현 위치 주변 가까운 관광데이터를 묶어 코스 1개를 제공하는 방식부터 진행한다.
- 이 구현 순서는 Product 요구사항 변경이 아니다. 특정 날짜 문화루트(B)의 최종 Product 기준인 `특정 날짜 + 시작점 + 가용시간 안에서 문화경험 2~3개를 순서 있게 구성한 루트 1개`는 유지하며, 이를 유지하기 어려운 기술 제약이 생길 때만 재협의한다.
- 9/30 멘토링 전 PoC는 어렵고 빠르면 후속 멘토링 시점이 예상된다.

**상태:** **부분확인** — 즉시 추천(A) 우선→특정 날짜 문화루트(B) 후속 순서와 B 초기 테스트 방향은 확인 완료. 실제 경로선·구간별 거리·시간의 구체 구현 수준은 구현 단계 후속.

## 2. 현재 선택 상태 저장·복원 — LF-01·LF-09 / D-15 후속

### Product 기준
- 즉시 추천(A)의 `이 장소로 갈게요`, 특정 날짜 문화루트(B)의 `이 루트로 갈게요` 이후 현재 선택 상태를 저장한다.
- 사용자가 다시 서비스에 들어왔을 때 LF-01에서 현재 선택으로 복귀할 수 있어야 한다.
- 즉시 추천(A)의 장소 선택 상태와 특정 날짜 문화루트(B)의 루트 선택 상태는 같은 Product 개념의 별도 Variant다.
- **선택됨 ≠ 실제 방문**이며 GPS로 방문을 자동 판정하지 않는다.
- Product는 DB·저장소 종류 자체를 고정하지 않는다.

### Tech 확인
1. 로그인 사용자의 선택 장소/루트를 계정 단위로 저장하고 다시 불러오는 최소 구현은 가능한가?
2. 비로그인 사용자는 같은 기기에서 어느 수준까지 임시 보존할 수 있는가?
3. 비로그인 상태에서 선택한 뒤 로그인하면 기존 선택 상태를 계정 상태로 이어받는 것이 MVP 공수상 가능한가?
4. 로그인 사용자의 다른 기기 간 동기화까지 구현할 경우, 동일 기기 저장·복원 대비 추가 공수나 구조적 제약이 큰가?
5. Product에서 `선택 변경`, 새 여행, Reset 등의 상태 종료 기준을 정의해 적용할 때 구현상 큰 제약이 있는가?
6. 9/30 전 시연 가능한 최소 상태 저장 범위는 어디까지인가?

### Product가 원하는 답변
- 로그인 / 비로그인 각각 구현 가능한 최소 범위
- 로그인 전 선택 상태 이어받기 가능 여부
- 기기 간 동기화까지 확장할 때의 추가 공수·제약
- 9/30 전 시연 가능한 범위와 구현상 리스크

### 9/28 Tech 회신
- 비로그인 사용자도 즉시 추천(A)·특정 날짜 문화루트(B) 자체는 공통으로 이용할 수 있다.
- 비로그인 상태에서는 지속적인 데이터 관리·기기 동기화와 저장된 선호 재사용에 제한이 있다고 회신했다.
- 비로그인 상태를 로그인 계정으로 이어받는 것은 기술적으로 가능하지만 Tech는 MVP에서 제외하는 안을 제안했다.
- Product는 비로그인→로그인 상태 이전의 MVP 제외를 아직 확정하지 않는다. 즉시 추천(A)·특정 날짜 문화루트(B) 진입 전 로그인 정책과 함께 후속 결정한다.
- 9/28 추가 확인에서 Product의 해석이 정확하다는 Tech 확인을 받았다. 비로그인 상태에서도 현재 즉시 추천(A)·특정 날짜 문화루트(B)에서 사용자가 선택한 **관심사·예산·이동조건은 해당 요청의 추천에 반영 가능**하며, 로그인은 이러한 Context를 이후 지속적으로 저장·재사용하기 위한 역할로 본다.
- 비로그인→로그인 상태 이전은 기술적으로 가능하지만 Tech는 MVP 제외를 제안했다. Product 최종 결정은 즉시 추천(A)·특정 날짜 문화루트(B) 이용 전 로그인 정책과 함께 9/30 오전 팀 회의에서 한다.

**상태:** **Tech 의미확인 완료 · Product 정책 결정 대기** — 비로그인 현재 요청 조건 반영 가능 여부는 확인 완료. 로그인 진입정책과 상태 이전 MVP 포함 여부만 팀 결정 대기.

## 3. LF-10 방문 후 최소 피드백 — 조건부 MVP 확인

### Product 기준
LF-10은 기본 LF-01~LF-09와 달리 **Product 조건부**다. 9/28 Tech 회신에서 최소 피드백 구현 가능성은 확인 완료했으며, 기술 가능성을 다시 묻지 않는다. 실제 MVP 포함 여부는 남은 일정·우선순위 기준으로 Product에서 후속 결정한다.

최소 피드백 후보:
1. `실제로 다녀오셨나요?` — 예 / 아니오
2. 방문했다면 `안내된 정보가 실제와 대체로 맞았나요?` — 맞음 / 일부 다름 / 많이 다름
3. 방문했다면 `이 추천이 선택에 도움이 됐나요?` — 도움 / 보통 / 도움 안 됨
4. 방문하지 않았다면 이유 — 너무 멂 / 시간 불일치 / 가격·예약 부담 / 다른 선택 / 매력 부족 / 기타

원칙:
- Push, GPS, 자동 방문 탐지는 전제로 하지 않는다.
- 예상 종료시간 이후 사용자가 다음에 서비스를 다시 열었을 때 노출하는 정도의 가벼운 Trigger를 우선 고려한다.
- 선택 수를 실제 방문 수로 해석하지 않는다.

### Tech 확인
1. 위 최소 피드백 UI와 응답 저장을 현재 인증·상태 구조에 붙이는 추가 공수는 어느 정도인가?
2. 예상 종료시간 이후 **다음 재방문 시 노출**하는 Trigger를 별도 Push/GPS 없이 구현할 수 있는가?
3. 즉시 추천(A)의 장소 선택과 특정 날짜 문화루트(B)의 루트 선택 모두에 같은 최소 피드백 구조를 적용할 수 있는가?
4. 피드백 결과를 Product Analytics용으로만 저장하고 User Preference에 자동 승격하지 않도록 분리할 수 있는가?
5. 위 최소안까지 포함할 경우 추가 공수나 구조적 리스크가 어느 정도인지 확인할 수 있는가?

### Product가 원하는 답변
- 추가 공수: 낮음 / 중간 / 큼
- 재방문 시 노출 Trigger 구현 가능 여부
- 응답 저장·Analytics 분리에서 Product 의미를 바꿀 정도의 제약 여부
- 구현 시 막히는 선행조건 또는 리스크

### 9/28 Tech 회신
- LF-10 최소 피드백은 **구현 가능**으로 확인됐다.
- 이 항목의 Tech 가능성 검토는 **완료**로 처리하며 같은 질문을 다시 하지 않는다.
- LF-10 자체는 여전히 **Product 조건부**다. 실제 MVP 포함 여부는 기술 가능성 재확인이 아니라 남은 일정·우선순위 기준으로 Product에서 후속 결정한다.

**상태:** **Tech 검토 완료 · Product 조건부 유지** — 동일 Tech 가능성 재문의 불필요

## 4. 9/28 회신 이후 후속

- **지도·경로:** 즉시 추천(A) 우선→특정 날짜 문화루트(B) 후속 구현 순서는 확인 완료. B 최종 Product 기준은 유지하며 구체 경로선·거리·시간은 구현 단계에서 확인한다. 같은 구현순서 질문은 반복하지 않는다.
- **로그인·비로그인:** 현재 요청의 관심사·예산·이동조건 반영 가능 여부는 Tech 의미확인 완료. 즉시 추천(A)·특정 날짜 문화루트(B) 이용 전 로그인 필수 여부와 비로그인→로그인 상태 이전의 MVP 포함/제외만 9/30 오전 팀 회의에서 결정한다.
- **LF-10:** Tech 구현 가능성 검토 완료. Product 조건부 상태만 유지하며 Tech에 같은 가능성 질문을 반복하지 않는다.
- **PoC:** 9/30 멘토링 범위에서 제외. 이번 멘토링은 기획 구체화 공유와 디자인 메인페이지 초안 중심으로 준비하고 PoC는 후속 시점에 검증한다.
