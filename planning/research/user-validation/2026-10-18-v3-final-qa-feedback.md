**검증 대상:** [KONNECT 배포 서비스](https://codyssey-konnect-frontend.vercel.app/)

## 1. 요약 및 발표 전 확인 우선순위

**결론:** A/B 기본 시연은 제한된 정상 시나리오에서 가능하지만 전체 PASS는 아니다. 특히 A 추천 요청의 반복 실패는 시연 안정성에 직접 영향을 준다.

| 우선 | 관찰·확인 과제 | 상태 | 발표 전 요청 범위 |
|---|---|---|---|
| 1 | **A 추천 요청 실패 5회** | 10/18 직접 확인, 용택님 귀가 후 확인 예정 | 오류 원인·로그 및 정상 복구 확인 **우선** |
| 2 | **B 자연어 출발지와 선택 UI 상태 불일치** | 오전 Work·오후 직접 관찰 | 실제 적용 위치·설정값 일치 여부 확인. 홍대 미지원 안내는 기존 조치로 충분해 추가 요청 제외 |
| 3 | **B 뮤지엄김치간 방문시간이 입장마감·폐관과 충돌** | 오전 Work 사례 | 현재 확보한 운영정보로 최소한의 시간 검증이 가능한지 확인 |
| 4 | **A 즉시 추천 최소 가용시간 30→60분 — Product 정책 변경 제안** | 30분의 실사용성 검토 및 오전·오후 QA 참고 | **기존 최소시간 검증값·안내만 변경 가능한지 협의**; 빠른 선택 1~4시간 유지, 이동시간 포함, 새 시간 알고리즘·체류시간 필터 요청 없음 |

**우선순위는 Product의 제안**이며, 각 항목의 구현 난도·수정 위험·실제 원인은 Tech 확인 후 결정한다. 4번은 확정 반영된 기존 Product 기준이 아닌 **10/18 정책 변경 제안 → 10/19 Tech 반영 수용·Product 기준 60분으로 확정(배포 QA 전)**이다. 60분 최소 입력 정책으로 모든 체류시간 충돌이 자동 해소된다고 주장하지 않으며, 10/19 Tech가 최종 배포에 포함하겠다고 회신했다. 실제 반영 검증은 배포 후 수행한다.

## 2. 발표 전 확인 사항 상세

### 2-1. A 추천 요청 반복 실패 — 가장 우선

**직접 관찰:** 10/18 오후 정상적인 시간·출발지 조건에서 `Find experiences` 요청 시 `Couldn't load experiences`가 **총 5회** 표시되었다. 실패 뒤 조건 재설정·재진입에 시간이 들었다. 이후에는 정상적으로 4개 후보가 생성되었다. B의 시간 수정 중에도 `I couldn't reach the service. Please try again.` 1회가 있었으나 재시도 성공했다(B 건은 A 실패 5회에 합산하지 않음).

**기확인 사항:** 용택님이 귀가 후 확인하기로 했고, 당시 API 토큰은 남아 있다고 회신했다. 따라서 ‘토큰 소진’은 확정 원인이 아니다.

**요청:** 해당 시간대 API·서버·요청 타임아웃 로그 및 오류 이후 복구 동작 확인. 기존 안내의 `Your conditions are kept`와 실제 조건 유지가 일치하는지도 가능하면 확인. 수정 시 우선 일반 A 추천 1회만 최소 재검증.

**시연 영향:** 높음. 서버 실패가 반복되면 추천 기능을 보여줄 수 없다.

### 2-2. B 자연어 출발지 상태 불일치 — 홍대 미지원 대응은 추가 요청 제외

**오전 Work:** 홍대 출발 요청을 받아들인 것처럼 설명했지만 생성된 루트에서 `Current location` 출발이 관찰됨. 실제 좌표 기반 이동시간에 어떤 출발지가 쓰였는지는 별도 확인이 필요함.

**오후 직접 QA:**
- 자연어 `Start at Gwanghwamun Square` 요청 → AI의 루트 요약과 지도·타임라인에는 광화문 출발로 표시.
- 동시에 하단 `Start from` 버튼과 선택창 체크 상태는 `Current location`으로 남음.
- 출발지 선택창에서 **광화문광장을 직접 선택하면 하단 버튼은 정상적으로 광화문으로 변경**됨. 직접 선택 UI 자체의 결함은 아님.
- 대화를 초기화해 홍대(홍익대입구역) 출발로 신규 요청했을 때 `I couldn't find anything open and reachable for that time and place right now.` 안내 후 루트 미생성. 이 사례에서는 종각 등으로 무단 대체 생성하지 않았지만, **‘미지원 지역’인지 ‘이 시간에 후보 없음’인지 구분되지 않았고** 재선택 안내도 구체적이지 않음. 실패 화면의 하단 날짜·시간은 요청값으로 갱신되지 않았으나 실패 시 기존값 유지 정책과 구분 필요.

**요청:** **자연어로 인식한 출발지·실제 추천에 이용한 위치·하단 설정값의 정합성만 확인**. 광화문광장처럼 지원되는 출발지에서도 나타난 표시 불일치를 중심으로 최소 수정 가능 여부를 검토한다.

**홍대 미지원 지역 대응은 기존 조치로 충분하다고 판단하므로 발표 전 추가 수정 요청에서 제외**한다. 미지원 여부를 세밀하게 설명하는 문구 추가나 별도 지역 재선택 UX를 이번에 요구하지 않는다. 기존 10/16 개선안 6번과 테스트 관찰은 기록으로만 유지한다.

**시연 영향:** 높음. 입력과 추천 출발지가 다르면 경로·이동 판단의 신뢰성에 영향.

### 2-3. B 뮤지엄김치간 운영시간 충돌 — 시간 검증 관련

**오전 Work 관찰:** 홍대 출발을 요청한 루트에 **뮤지엄김치간(Museum Kimchikan)**이 포함되어, 방문이 **17:33~18:18**로 계획됨. [시설 공식 사이트](https://www.kimchikan.com/)에는 **최종 입장 17:30 / 운영 종료 18:00**이 안내되어 있어 계획 시간과 충돌한다.

이것은 김치 문화 박물관을 추천한 것 자체의 문제가 아니라, **방문시간을 입장마감 이후부터 배정하고 폐관 후까지 연장한 문제**다. 다만 해당 운영·입장마감 정보가 현재 TourAPI/문화행사 API 또는 서비스 내부 데이터에 존재하는지, 반영 과정에서 누락됐는지는 확인되지 않았다.

**요청:** 현재 확보한 시간 필드만으로 방문 가능 시각을 검증할 수 있는지 확인. 입장마감 데이터가 없다면 실제 확인되지 않은 사항을 확정적으로 표시하지 않는 방식 검토. **신규 외부 API 연동·실시간 크롤링은 발표 전 요청하지 않음.**

**시연 영향:** 실제 현장 방문 실패 가능성. 구현 규모는 데이터 가용성에 따라 판단.

### 2-4. A 최소 가용시간 30분 → 60분 상향 — Product 정책 변경 제안

**오전 Work 관찰:** 명동 / 14:00~14:30(30분) 입력 시 서울시립미술관 추천. 화면에는 **도보 약 18분**과 **`About 60 min`**이 함께 표시됨.

**해석 주의:**
- 사용자가 A 입력에 ‘60분 관람’을 요구한 적은 없음.
- [Product 04](../../product/04-route-time-rules.md)의 ‘박물관·규모 있는 전시 **60~90분**’은 **B 문화루트 구성용 계획 체류시간 범위**로 채택한 것. A의 `About 60 min`이 이 범위에서 나온 값인지, 실제 추천 필터에 쓰였는지는 코드 확인 전 **미확정**.
- 자율형 미술관은 짧은 **부분 관람**도 가능할 수 있으므로 ‘도보 18분+계획값 60분=반드시 78분 필요’ 또는 ‘30분 추천은 무조건 오류’라고 단정하지 않는다.
- 다만 이 수치가 추천 적합성을 판단하는 필수 소요시간이라면 30분 조건과 충돌하고, 단순 권장 관람시간이라면 UI에서 그 성격이 분명해야 한다.

**오후 직접 QA:** 명동 / 16:19~16:49, 후보 4개(모두 `Partially confirmed`) 생성. 도보 약 12~19분 표시. 상세의 개별 계획 체류시간까지 이 사례에서 확인하지 않아 위 충돌의 재현 판정으로 확대하지 않음.

**10/19 정책 결정 업데이트(10/18 당시 제안 내용 보존):** A 즉시 추천에서 이동시간을 포함한 전체 가용시간이 30분이면 실제 문화경험에 사용할 시간이 지나치게 짧아질 가능성이 높으므로, **최소 가용시간을 기존 30분에서 60분으로 상향**한다는 방향을 제안한다.

- A 최소 가용시간: **30분 → 60분**. 직접 종료시각 입력의 최소 간격과 관련 유효성 검사·안내 문구를 같은 기준으로 맞추는 수준에서 적용 가능한지 확인한다.
- 기존 빠른 선택 **`In 1 hr / In 2 hr / In 3 hr / In 4 hr`는 유지**한다.
- `Start`부터 `Done by`까지에는 **출발지에서의 이동시간이 포함**되며, 종료일이 당일 24:00을 넘지 않는 기존 정책을 유지한다.
- A의 **`About 60 min` 등의 예상·권장 관람시간은 필수 체류시간이 아닌 참고값**으로 취급한다는 Product 방향을 제시한다. B 문화루트 구성용 계획값을 A의 필수 방문시간으로 오인하지 않는다. 단, 현재 구현의 수치 출처·계산 방식은 확인된 사실로 단정하지 않는다.
- **B 문화루트의 시간 정책은 변경하지 않는다.**
- 이번 제안은 **새로운 시간 계산 알고리즘, 유형별 체류시간 강제 적용, 이동+관람시간 기반 신규 필터 추가 요청이 아니다.** 최소 입력시간 검증과 관련 안내를 바꾸는 작은 수정이 가능한지만 협의한다.
- **10/19 Tech 회신:** 최소 가용시간 1시간으로 변경하겠다고 안내했다. 해당 범위의 Product 정책은 확정하고, 배포 반영 자체는 아직 재검증하지 않았다.

**참고:** 최소시간을 60분으로 바꾸더라도 각 후보의 실제 방문·관람 완료 가능성이 자동 보장되는 것은 아니다. 이용 가능 여부와 계획값·참고값 구분은 장기적으로 개선할 사항이다.

**시연 영향:** 후보가 이용 가능하다는 사용자 기대와 화면 정보의 의미가 어긋날 수 있음. 원인·수정 난도 확인 후 우선순위 판단.

### 3-3. A/B 직접 검증 및 오전 회귀 확인

## 4. 발표 전 보류 및 발표 자료의 한계 명시

- **개별 전시 최신성:** 대림미술관의 전시 교체·준비기간 등은 시설의 일반 운영시간과 다를 수 있다. 서비스가 활용하는 원천 데이터만으로 개별 전시 관람 가능 여부를 항상 확인할 수 있는지는 미확정. 신규 API·크롤링 추가 대신 **운영정보와 개별 전시 가능성의 차이**를 발표 한계 및 향후 개선 방향으로 명시한다.
- **A 추천 시간 정확성 고도화:** 개별 후보의 공식·예상·계획 체류시간을 반영한 신규 필터 또는 시간 계산 알고리즘 추가는 이번에 요청하지 않는다. **A 최소 가용시간 30→60분 상향은 10/19 Product 정책으로 확정**되었으며 Tech가 최종 배포 포함을 안내했다. 단, 상향만으로 후보별 시간 적합성이 자동 보장되지는 않는다.
- **새 범위 제외:** 복잡한 B 전체 재구성·저장 복구 QA, 신규 언어 지원, 실시간 지도 추적, 지도 아이콘 미세 간격 수정, 현재 범위를 넘어서는 AI/데이터 인프라 재설계.
- **검증 한계:** Cloud Browser 및 모바일 직접 검증 결과가 모든 출발지·날짜·행사·네트워크 조건을 대표하지 않으며, 외부 제공 운영정보의 실시간 정확성을 보증하지 않는다.

## 5. 용택님께 드리는 최종 협의 요청

**전체 수정 요청이 아니라 발표 전 최소 변경 가능성을 판단하기 위한 협의**입니다.

1. **A 실패 5회:** 이미 확인 예정인 로그·원인·복구 안정성 최우선 점검.
2. **B 출발지:** 자연어로 입력한 **광화문 출발**과 실제 출발지·하단 설정값의 정합성만 확인. **홍대 미지원 대응은 기존 조치로 충분하며 추가 수정 요청하지 않음**.
3. **B 입장마감:** 현재 확보된 운영정보로 불가능한 시간 배정을 막을 수 있는지 확인. 추가 연동이 필요하면 보류.
4. **A 최소 가용시간:** **30→60분 Product 변경 제안**을 기존 최소시간 검증값·안내만 수정하는 수준에서 적용 가능한지 확인. 빠른 선택 1~4시간 유지, 이동시간 포함, `About 60 min`은 필수 체류시간이 아닌 참고값으로 정의, B 시간 정책 유지. **새 알고리즘·체류 필터는 요청하지 않으며** 10/19 Tech 수용, 배포 후 최소 확인.

수정 부담이 크거나 기존 정상 흐름을 해칠 위험이 있다면 무리하게 개발하지 않고, **검증된 시연 경로를 사용하며 데이터·운영정보 한계는 발표에서 명확히 설명**한다. 수정 완료를 통보받은 항목만 최소 회귀 확인한다.
