# KONNECT Input & Recommendation Rules

> 역할: 입력, Hard/Soft Constraint, 후보 판정, 불확실성, 예산·무료 필터의 현재 Product 기준  
> 연결 결정: D-07, D-08, D-10

## 1. 입력 UX 원칙 — D-07

- 음성 입력은 MVP 필수 범위에서 제외한다. 기본 텍스트·선택 입력만으로 핵심 Flow를 완성한다.
- 핵심 기능 완료 후 여력이 있으면 음성을 보조 입력수단으로 선택 구현할 수 있다.
- 즉시 추천(A)은 빠른 판단·실행을 위해 **시작 위치·시작 시각·종료 시각**을 구조화된 필수 입력으로 받는다.
- A의 선택조건은 개별 Form을 늘리기보다 **하나의 자연어 선택 입력 영역**에서 보완하는 방향이다.
- 특정 날짜 문화루트(B)는 **안내·입력 예시가 있는 자연어 대화 중심**으로 필수조건을 확보하고 계획·조정을 돕는다. 완전히 빈 자유입력으로 고정하지 않는다.
- 자연어로 받은 조건은 `자연어 → 구조화 → 필요한 사용자 확인·수정 → 추천`으로 처리한다.
- 사용자가 말하지 않은 조건은 임의로 추정하지 않고 미설정으로 둔다.
- AI가 추출한 시간·장소·예산 등 핵심 조건은 추천 전에 확인·수정할 수 있어야 한다.

### 필수 / 선택 입력

#### 즉시 추천(A)
- **출발 기준 위치: 필수**
  - 현재 위치를 빠른 기본값으로 사용
  - 위치 권한 거부 시 장소·지역 직접 입력 가능
  - 사용자가 원하는 출발 위치로 변경 가능
- **시간 경계: 필수**
  - 현재 시각을 빠른 시작 기본값으로 사용
  - 사용자가 시작 시각을 직접 지정할 수도 있음
  - 사용자 지정 종료 시각으로 끝 경계를 확보하며 **자동 기본값은 없다**
  - 가용시간은 **최소 60분(1시간) 이상**, 종료는 **시작일 24:00까지**다. 별도의 4·6·12시간 상한은 두지 않는다.
  - **10/19 Product 기준 변경:** 짧은 이동 후 유의미한 문화경험을 할 수 있도록 A 최소 가용시간을 30분에서 60분으로 상향한다. 출발지부터의 이동시간을 포함하며, 기존 `In 1 hr / 2 hr / 3 hr / 4 hr` 빠른 선택을 유지한다. `About 60 min` 등의 예상·권장 관람시간은 필수 체류시간이 아닌 참고값이고, 이번 변경으로 새 시간 계산·체류시간 필터를 추가하지 않는다. B 시간 정책은 유지한다.
  - 시작 변경 시 종료를 자동 연장하지 않으며, 시작 시각이 종료 시각 이상이면 종료 재선택을 요청한다.
  - 종료 미입력·시작/종료 역전·60분 미만·경계 초과는 추천 전 입력 오류 또는 제한으로 처리한다. 유효한 입력의 후보 없음만 추천 0건·기존 Fallback으로 처리한다. 24:00/익일 00:00 경계와 운영 기준의 의미는 [04 · 시간 기준](./04-route-time-rules.md#3-start-anchor--time-boundary)을 따른다.
- 관심사·예산·이동 선호/허용시간·다음 고정 일정·기존 여행계획·날씨 관련 선호·기타 요구: 하나의 자연어 영역에서 전달하는 선택조건
- 실제 날씨는 기상청 등 시스템/API 환경 Context로 가져온다. 사용자는 실내 선호·비가 와도 괜찮음·야외 선호 등의 **날씨 관련 선호**를 전달하며 기상정보 자체를 입력하지 않는다.

#### 특정 날짜 문화루트(B)
- **LF-04 Conversation-first 화면 위계:** 자연어 요청(입력 자체는 선택) → KONNECT 구조화 → 누락·모호한 필수값만 질문 → 확인된 값의 compact editable summary → 필요 시 해당 값 직접 수정 → `Show culture route`. 처음부터 날짜·위치·시간 Form을 채우게 하지 않는다. `Edit details directly`는 보조 경로이며 날짜·시작점·시작 시각·종료 경계 4값이 모두 확인된 뒤에만 생성한다. B-01/B-02의 필수값·최소 추가 확인·기존 값 유지 로직은 변경하지 않는다.
- **LF-04 Guided Chat 3+1 대표 상태:** 같은 LF-04의 S1 Start(안내·자연어 예시), S2 Clarification(User ↔ KONNECT Turn·누락값 질문), S3 Ready to generate(필수 4값 확인 후 생성 직전), V1 Direct edit / Ambiguity(해당 Hard 값만 수정)로 표현한다. 대화 입력창은 지속하고 Plan summary는 보조 수준, Quick Action은 Starting point가 필요할 때만 제공한다. 새 기능·글로벌 LF 번호가 아니며 실제 화면 분할·전환 Interaction은 UX 재량이다.
- **날짜·출발 위치·시작 시각·종료 경계: 필수**
- 관심사·예산·동행·기존 여행계획: 선택. 이동 선호/허용시간도 기존 선택조건을 유지한다.
- 오늘 현재 위치는 수정 가능한 기본값이다. 미래 날짜에 현재 GPS를 자동 시작점으로 가정하지 않는다.
- 필수조건을 구조화하고 이미 제공한 값을 불필요하게 반복 질문하지 않는다. `문화루트 보기`로 생성한다.
- 누락된 필수조건만 확인하고, 여러 값이 빠지면 간결하게 묶어서 질문한다. `내일 오후` 같은 모호한 핵심값이나 충돌하는 값을 임의 추정하지 않는다.
- 반복적으로 모호한 응답이 이어지면 입력 예시와 해당 조건의 직접 수정 경로를 제공한다. 별도의 전체 입력 화면 전환이나 AI 동적 UI 생성은 필수 요구가 아니다.
- 수정값은 실제 요청 조건에 반영되어야 한다. 구체 입력 UI는 UX/UI, 상태 반영·구현 방식은 Tech가 판단한다.

## 2. 관심사·예산·이동 선호

### 관심사
관심사는 **선택 입력**이며, 입력된 경우 추천 우선순위를 조정하는 Soft Preference로 사용한다.

- 미입력이어도 정상적으로 추천을 진행한다.
- 특별한 선호가 없거나 입력하지 않은 경우 운영 가능성·시간 적합성·이동 부담·정보 신뢰도 등을 중심으로 정렬한다.
- 관심사와 맞는 후보가 부족하면 다른 유형의 후보를 제시할 수 있으나 `선호와 다른 대안`임을 표시한다.
- D-06의 5개 문화경험 유형은 **콘텐츠 범위를 관리하는 내부 상위 분류 체계**이며 사용자 관심사 분류와 1:1 대응하지 않는다.
- 관심사는 즉시 추천(A)과 특정 날짜 문화루트(B)에서 **동일한 6개 값**을 사용하며 **복수 선택 가능**하고 하나의 콘텐츠에도 여러 관심사 태그가 붙을 수 있다.
- 6개 분류의 의미·복수 관심사·미입력 허용 원칙은 유지하되 기존 Chip 선택 UI를 필수 입력방식으로 고정하지 않는다. A는 하나의 자연어 선택조건 영역, B는 안내가 포함된 자연어 대화에서 관심사를 전달하는 방향이다.
- 기존 일정 등 다른 자연어 입력에서 관심사가 추출되는 경우에도 최종적으로 동일한 6개 관심사 값으로 구조화한다.
- 사용자 관심사 6개를 영문 우선으로 사용한다: `Traditional Culture / 전통문화`, `Palaces & Historic Sites / 역사·궁궐`, `Hands-on Experiences / 문화 체험`, `Art & Exhibitions / 미술·전시`, `Live Performances / 공연`, `Festivals & Events / 축제·이벤트`.
- `Traditional Culture`는 전통예술·생활문화·공예·국악·의례 등 살아 있는 전통문화, `Palaces & Historic Sites`는 궁궐·유적·역사건축·역사적 장소 방문에 대한 관심으로 구분한다. 한 콘텐츠에 둘 다 붙을 수 있다.
- `Hands-on Experiences`는 사용자가 직접 만들거나 해보거나 참여하는 **단기 문화 프로그램**이다. 문화체험이 주목적인 김치·전통음식 만들기는 포함할 수 있으나 일반 식사·맛집·시식·식음료 소비는 제외한다. 관람·판매·시연 관람만으로 포함하지 않으며 실제 참여 프로그램 단위의 날짜·회차·대상·예약조건을 적용한다.
- `Festivals & Events`는 축제 및 **기간 한정 특별 문화행사** 중심으로 사용하며 일반 공연·전시라는 이유만으로 모두 Events로 묶지 않는다.
- 자연어 입력의 안내·예시·확인/수정 Interaction은 UX/UI가 설계한다.

### 예산
예산은 선택 입력이며 다음 형태를 지원한다.

- 무료
- 1인 상한
- 미설정

예산이 설정된 경우 **확인된 가격 정보 안에서만** 조건을 적용한다.

- 즉시 추천(A): 선택할 경험 1개의 확인된 필수 비용 기준
- 특정 날짜 문화루트(B): 포함된 경험들의 확인된 필수 비용 합계 기준
- 특정 날짜 문화루트(B)에 필수 비용 미확인 경험이 하나라도 포함되면 확인된 합계만으로 루트 전체를 `예산 충족`으로 판정하지 않는다. 확인된 합계와 함께 `총비용 추가 확인 필요`로 표시한다.
- 교통비·식비·개인 쇼핑비는 문화경험 비용 합계에 포함하지 않는다.

**10/14 Product 결정 — A 예산 초과 Alternative:** 일반적인 금액 상한(예: `Under ₩20,000 each`)은 `Fits your conditions` 및 예산 충족 판정에서 계속 엄격하게 지킨다. 확인된 일반 이용 가능 가격 중 상한을 충족하는 선택지가 있으면 해당 후보를 우선한다. 할인 적용 여부가 확인되지 않거나 가격이 미확인이면 예산 충족으로 판정하지 않는다. **A의 적합 후보가 부족한 경우**, 가격이 확인되고 시간·운영·참여자격 등 다른 필수 실행조건에 충돌하지 않는 후보는 **일반 금액 상한을 초과하더라도 `Alternative`로만 제시할 수 있다**. 초과 금액·차이와 예산 완화 사실을 분명히 표시한다(예: `Under ₩20,000 each` → 확인가격 ₩25,000 → `Alternative · ₩5,000 above your budget`). 이 후보를 `Fits` 또는 `Partially confirmed`로 오분류하거나 사용자 예산이 변경됐다고 간주하지 않는다.

**절대 예산 상한 예외:** `Never exceed ₩20,000`, `절대로 2만원을 넘을 수 없음` 등 초과 불가 의사를 명시했다면 완화 불가능한 Hard Constraint다. 초과 후보는 `Alternative`에서도 제외한다. `Under ₩20,000`처럼 일반적인 금액 상한만으로 절대 초과 불가 의사를 자동 추정하지 않는다. 표현이 실제로 모호하고 판정에 중요하면 필요한 부분만 확인할 수 있다.

A는 조건 충족 후보를 먼저 제공하고 **최대 3~4개를 억지로 채우지 않는다**. 초과 폭이 과도하거나 선택 가치가 낮다면 예산 초과 대안을 생략하며, 적절한 후보가 전혀 없으면 0건 안내·조건 수정을 제공한다. **이번 변경은 A에 한정**하며, **B의 루트 전체 확인 필수비용 총합·예산 판정 및 D-10 무료 필터의 가격 미확인 기준은 기존대로 유지**한다.

### 이동 선호
- **P-09 저장 선호:** 최초 가입에서 문화 관심사 6개와 별도로 걷기 등을 포함한 추가 선호를 자연어로 입력할 수 있다. MVP 기본 흐름은 `자유입력 → LLM 해석 → 사용자 확인·수정 → 저장`이며 장시간 챗봇 상담·반복 추가질문을 기본 흐름으로 요구하지 않는다. 사용자가 확인한 해석값만 장기 User Preference로 저장한다. 이동 관련 저장 선호는 Soft ranking signal이며 숫자형 Hard 상한이나 10분·1km로 변환하지 않는다. 현재 Request의 명시 이동 제한이 항상 우선한다(Request > Trip Context > User Preference). 저장 선호만으로 M01/M02 또는 `Within your walking limit`을 생성하지 않으며 접근성·건강·장애 상태를 추론하지 않는다. My Page에서 확인·변경·해제 가능하고 미설정·Skip 후에도 A/B 제한 없음.
- 미설정이어도 실제 이동 부담은 추천 정렬에 고려한다.
- 즉시 추천(A)에서 이동 허용시간을 입력한 경우에만 이를 추천 판단 조건에 적용한다. 미입력이라면 이동시간·거리를 보여주고 사용자가 판단하며, 이동시간이 길다는 이유만으로 자동 제외하지 않는다. 도심권 약 2km는 내부 참고선이지 Hard 경계가 아니다.
- 사용자가 말하지 않은 `20분`, `30분` 같은 고정 상한을 임의로 만들지 않는다.
- `가까운 곳 위주`, `30분 넘게 이동하고 싶지 않아`, `도보 위주`처럼 입력할 수 있다.
- 기본적으로 Soft Preference로 보되, 사용자가 명확한 금지·상한으로 말하면 Hard Constraint로 처리한다.
- 특정 날짜 문화루트(B)에서 이동시간 상한을 말한 경우 기본적으로 **스팟 간 1회 이동 기준**으로 해석한다.

## 3. 위치·시간 해석

### 위치
- 추천 판단의 기준은 GPS 자체가 아니라 **출발 기준 위치**다.
- `강남 쪽`처럼 넓거나 모호한 표현은 정밀 위치로 간주하지 않는다.
- 추천 정확도에 영향을 줄 정도로 모호하면 더 구체적인 위치 확인 또는 수정 기회를 제공한다.
- 위치 권한이 허용돼도 현재 위치의 정확도가 추천·이동 판단에 충분하지 않으면 출발 기준 위치를 확인·수정할 기회를 제공한다. 구체적인 accuracy 임계값과 판정 방식은 Tech가 정한다.

### Location Quick Select — Starting point 입력 보조

- `Use current location / Search a place / Popular starting points`를 제공하며 기존 현재 위치·직접 검색을 항상 유지한다.
- MVP 대표 시작점 5개: `Gyeongbokgung Palace`, `Anguk · Insadong`, `City Hall · Deoksugung`, `Myeongdong`, `DDP`.
- 선택하면 Starting point가 해당 대표 위치로 채워진다. 해당 지역만 추천하는 별도 모드가 아니며 기존 시간·운영·이동·예산·관심사 판단을 그대로 적용한다.
- N차 방문객도 지명에 익숙하다고 가정하지 않는다. 서울 도심 검증권역·약 2km는 내부 참고선이며 사용자-facing Hard 경계/필터가 아니다.
- B 미래 날짜는 현재 GPS를 자동 시작점으로 가정하지 않고 Search / Quick Select로 실제 시작점을 지정·확인한다.
- LF-04에서는 Starting point가 필요할 때의 보조 경로로 제공한다. 처음부터 큰 지역 선택 UI를 펼쳐 자연어 요청보다 우선하지 않는다.
- 정확한 좌표·지오코딩·대표 anchor는 Tech, Chip/버튼 배치·검색 Interaction은 UX가 결정한다.

### 즉시 추천(A)
- 기본: 현재 위치 + 현재 시각
- 사용자가 더 구체적으로 설정하려는 경우: 지정 출발 위치 + 지정 시작 시각
- **10/13 A 범위:** 다음 고정 일정이 있더라도 이동·도착시간과 복수 일정 충돌을 자동 계산하지 않는다. 사용자가 다음 일정 이동 여유를 고려해 `Available until`을 직접 설정하도록 안내하며, 실제 미적용 Context를 자동 반영된 것으로 표시하지 않는다.

### 특정 날짜 문화루트(B)
- 오늘 또는 미래의 특정 날짜 1일을 사용한다.
- 종일 일정이 아니라 사용자가 지정한 문화경험 가능 시간대만 다룬다.
- 자연어 시간 입력은 내부적으로 시작시각·종료시각으로 구조화한다.

## 4. Hard / Soft Constraint

### Hard Constraint
사용자가 명시했거나 실제 방문 가능성을 직접 깨는 조건.

예:
- 행사 종료·휴무·입장마감 이후
- 참여 자격 미충족
- 사용자가 명확히 넘을 수 없다고 지정한 시간·이동 상한, **절대 초과 불가로 명시한 예산 상한**. A의 일반 금액 상한은 Fits 충족 기준으로 유지하되 §2의 공개된 예산 초과 Alternative 예외를 적용할 수 있다.
- A에서는 사용자가 직접 정한 종료 경계의 시간 충돌(다음 고정 일정까지의 자동 도착 검증은 하지 않음)
- 서비스 범위 밖 또는 식별 불가능한 데이터
- 공식 위험 특보·경보 등으로 안전상 정상 추천이 부적절한 Outdoor 경험

### Soft Preference
추천 우선순위는 바꾸지만 절대 제외 조건은 아닌 항목.

예:
- 관심사
- 가까운 곳 선호
- 일반적인 이동 부담 선호
- 조정 가능한 예산

### 현재 요청의 명시적 제외조건
- 사용자가 현재 요청에서 **원하지 않는 유형·대상**, **과거에 방문했다고 밝힌 장소**, **향후 방문할 계획이라고 밝힌 장소**는 해당 요청에서 제외한다.
- 이 정보는 현재 Request Context이며 장기 User Preference로 자동 저장하지 않는다.
- 후보가 부족하거나 0개가 되더라도 제외조건을 몰래 무시해 후보를 다시 넣지 않는다. 기존 0건 안내·조건 조정 경로를 사용한다.

## 5. 추천 후보와 실패 처리

- 즉시 추천(A)의 현재 팀 방향은 **최대 3~4개 범위의 소수 후보**다. 3개를 고정 보장하지 않는다.
- 완전 일치 후보가 1–2개면 먼저 보여준다.
- 정상 후보가 부족하면 `조건 완화 대안`을 명확히 구분해 제시할 수 있다(A의 일반 예산 상한 초과 후보 포함). **대안으로 추천 수를 강제로 채우지 않는다.**
- 실제 이용 불가 후보를 숫자 맞추기 위해 포함하지 않는다.

### 0건 처리
완전 일치 후보가 없어도 빈 결과로 끝내지 않고, 조정 가능한 조건을 일부 벗어난 근접 대안을 별도로 보여줄 수 있다.

단, 휴무·행사 종료·실제 운영 불가·**완화 불가능한 Hard Constraint 충돌(절대 예산 상한 포함)**은 완화하지 않는다. A의 일반 예산 상한 초과만 §2의 요건을 만족할 때 공개된 `Alternative`로 제시할 수 있다.

## 6. 결과 상태와 내부 판정 순서

사용자-facing 기본 상태는 3개다.

### 조건 충족
현재 확인 가능한 핵심 조건이 맞고 사용자가 설정한 Hard Constraint를 위반하지 않는 후보.

### 추가 확인 필요
알려진 필수 조건(Hard Condition) 충돌이 없고 미확인 사항을 사용자가 공식 경로에서 추가 확인할 수 있으며 후보의 의사결정 가치가 남아 있는 경우. 미확인 때문에 시간 적합성·실행 가능성 또는 자동 루트 구성을 신뢰성 있게 판단할 수 없으면 추천 또는 자동 루트에서 제외한다. 미확인 값을 임의 추정하지 않는다.

상태 의미는 유지하되 중간 상태의 사용자-facing 선호 문구는 `Partially confirmed`다(10/13 Product 방향, 팀 최종 카피 확인 전). 이전 `Check needed`는 사용자에게 확인 책임을 넘기는 듯한 인상을 줄 수 있어 대체 검토하고, 중간 상태를 문화경험 전체의 대표 부정 라벨처럼 보이지 않게 한다. **확인된 적합 요소와 실제 미확인 항목(예: 가격·예약)을 함께 구체적으로 표시**하고, 짧은 영문 문구·배치·시각적 강도는 의미를 보존하는 범위에서 UX/UI가 조정한다. Tech가 데이터 보완 후 중간 상태 발생 비율을 다시 확인하고 여전히 과도하면 상태명 또는 노출 방식을 재검토한다.

### 조건 완화 대안
관심사·Soft Preference 이동조건 등 조정 가능한 조건이 일부 맞지 않거나, **A에서 일반 예산 상한을 넘지만 다른 필수 실행조건에 충돌하지 않는 후보**를 명확히 구분한 상태다. 예산 초과액·완화 이유를 표시하고 사용자 조건을 자동 변경하지 않는다. A의 예산 초과 후보를 `Fits` 또는 `Partially confirmed`로 표시하지 않으며, 절대 예산 상한 등 완화 불가능한 조건을 우회하지 않는다.

`추천 제외`는 사용자-facing 네 번째 상태가 아니라 내부 판정값이다.

### 내부 판정 순서
1. 실제 이용 불가 또는 **완화 불가능한 Hard Constraint 충돌**(시간·참여자격·절대 예산 상한 등) → **추천 제외**
2. 조정 가능한 조건 불일치 또는 **A의 일반 예산 상한 초과**(확인 가격·다른 필수 실행조건에 충돌 없음·초과 차이 표시) → **조건 완화 대안**
3. 명확한 불일치는 없지만 핵심정보 미확인 → **추가 확인 필요**
4. 핵심조건 확인 및 충돌 없음 → **조건 충족**

후보에는 주 상태 1개를 두고 가격·예약·이동 등 추가 확인사항은 별도 태그로 표시할 수 있다.

### 선택 전 결과정보 — D-08

- **우선 제공:** 결과 상태, 추천 이유, 시간 적합성, 가격, 이동 부담, 핵심 예약·참여조건.

- 준비물·사전예약 필수·자격 제한 등 선택을 막을 수 있는 Hard Condition은 일반 상세정보보다 우선 노출한다.
- 미확인 정보는 추정하지 않고 무엇을 추가 확인해야 하는지 구체적으로 표시한다.
- 확보된 공식 상세·공식 예약·공식 확인 경로로 다음 행동을 연결한다.
- Product는 정보 우선순위까지만 정한다. 실제 배치·Interaction·컴포넌트는 UX/UI가 후속 설계한다.

### 추천 이유 — R-01~R-10 Product Freeze

**의미(R-01·R-02):** 추천 이유는 홍보가 아니라 현재 사용자 조건과 후보 사이에 확인된 적합성을 설명한다. 내부 Fit 5종은 Time Fit / Location & Movement Fit / Interest Fit / Budget Fit / Plan Fit. 예약·참여조건은 별도의 실행조건·미확인·주 상태로 제공하며 독립 Fit으로 만들지 않는다.

**공통 생성 원칙(R-03a):** User Context + Candidate Evidence + 명시적 Match Rule이 필요하다. 현재 요청 우선, 유효한 기존 일정·사용자가 확인한 장기 선호만 보조 활용한다. 미확인이나 근거 없는 추정으로 긍정 Fit 또는 AI 설명을 생성하지 않는다. 개별 Fit이 전체 실행·예약·참여 가능성을 보장하지 않는다.

**Fit별 Match Rule(R-03b~f)**
- **Time:** 실제 운영시간·회차·입장마감, 이동·관람시간과 사용자의 가용시간을 비교한다. 실제 확인값, 설명 가능한 예상값 및 허용된 Product 계획값을 구분한다. 자율형 문화시설은 관람 소요시간 미확인 시에도 운영·이동·입장 조건이 확인되면 *방문 가능한 시간대*에 한해 제한적으로 설명하되 관람 완료·실제 입장은 보장하지 않는다. 고정형 회차·필수 실행시간 미확인은 기존 배제/UNKNOWN 기준을 따른다.
- **Location & Movement:** 출발점·후보 위치·신뢰 가능한 이동시간/거리/방식과 명시한 이동 제한 또는 검증된 동선상 이점이 있어야 한다. 단순히 12분 거리라는 사실만으로 이동이 쉽다고 평가하지 않는다.
- **Interest:** 현재 요청의 명시된 관심사 또는 유효한 확인 장기 선호와 근거 있는 콘텐츠 분류 매핑이 일치할 때 생성한다. 미입력은 정상 추천 자체를 막지 않는다.
- **Budget:** 사용자 예산과 실제 적용 가능한 확인 일반가격을 비교한다. 조건부 할인·가격 미확인으로 긍정 Fit을 생성하지 않는다. B에서 일부 필수비용이 미확인이면 전체 루트의 Budget Fit은 생성하지 않되 개별 장소 근거는 분리한다.
- **Plan:** 기존 외부 일정의 전후 시간·장소와 후보의 실제 연결 적합성이 확인될 때 생성한다. B 문화루트 자체를 구성했다는 이유만으로 Plan Fit을 자동 부여하지 않는다.

**우선순위·표현(R-04·R-05):** 후보/루트에서 Primary Reason 1개를 우선하고 별도의 유의미한 근거가 있으면 Secondary 1개까지(최대 2개), 강제 채움 금지. 설명력·후보 간 구별력을 우선하며 고정된 Fit 순서는 정하지 않는다. 과거 2~3개 목표·정상 후보 최소 1개 필수 규칙은 폐기하고, 내부 Fit명을 사용자-facing 그대로 표시하지 않는다. 12 min walk(사실)와 Fits your walking limit(적합성 설명)를 구분한다.

**Reason Copy Dictionary v1.0 (R-05·R-10 UX/Tech 인계, 2026-10-04):** `product/reason-copy-dictionary.md`에 기본 영문 문구 17개(Time 4 / Location & Movement 3 / Interest 6 / Budget 2 / Plan 2), 각 Copy ID의 생성·억제 조건 및 0/1/2개·A/B·LF-09 UX/QA 사례를 Freeze한다. 이는 화면에 17개 노출하거나 개발에 17개 구현을 별도 필수화하는 결정이 아니다. 실제 UI 문구는 의미·근거·미확인 경계를 보존하는 범위에서 UX가 다듬을 수 있다.

**A/B 범위(R-06):** A는 개별 문화경험 Reason, B는 루트 전체(방문순서·이동·누적 시간 등)와 개별 장소 이유를 구분한다. B는 최소 2곳 이상을 고정 상한 없이 구성하되 시간·운영·이동을 우선 검증하고 후보 수·가용시간 강제 채움 금지. Product 계획 체류시간은 실제값으로 단정하지 않는다.

**Reason 0개·미확인·상태(R-07·R-08):** 이유가 0개여도 그 이유만으로 후보를 자동 제외하거나 주 상태를 변경하지 않는다. 해당 Reason은 생략하고 필요한 미확인 설명만 이유 외부에서 제공한다. Fits your conditions / Partially confirmed(팀 최종 영문 문구 확인 전) / Alternative, Hard·Soft 제한·조건완화·UNKNOWN, 예약·참여조건은 기존 규칙을 유지한다. B 재구성 실패 후 이전 루트를 유지하는 경우 과거 Reason을 새 조건 충족의 근거로 재사용하지 않는다.

**AI·Handoff(R-09·R-10):** AI는 근거 있는 Fit을 읽기 쉽게 설명하는 역할만 하고 새 사실·확신·과장·보장을 만들어내지 않는다. Tech는 요청 Context, 후보 Evidence/출처, 확인·예상·계획·미확인 값 유형, Match Rule, 상태/완화, Reason 생성·생략을 검증 가능한 형태로 관리한다. 구현 스키마·Agent/Rule/Data 배분·trace 방식은 Tech가 결정하고, 태그 UI·카드/상세 배치·최종 Copy·Interaction은 UX/UI가 결정한다. QA에는 관심사 미입력·시간/입장마감 충돌·자율형 계획값·가격 미확인·B 비용 누적·루트 재구성 실패/이전 루트 유지를 포함한다.

A 결과는 **Map UI 기반**으로 구성하는 현재 방향이다. 지도만 보여주지 않고 결과 상태·추천 이유·시간 적합성·가격·이동 부담·핵심 예약/참여조건을 가능한 한 추가 화면 없이 함께 제공해 상세 왕복을 줄인다. D-08 정보 우선순위를 유지하며 지도 비율·카드 형태·스크롤 방식은 UX/UI가 설계한다.

## 7. 중복·편중 완화

기존 여행계획이 입력된 경우:
- 이미 포함된 장소의 중복추천을 줄인다.
- 10/13 현재 A에서는 자동 다음 일정 충돌 계산 대신 사용자가 이동 여유를 포함한 종료시각을 설정하도록 안내한다.

같은 장소·운영주체의 매우 유사한 콘텐츠가 소수 후보를 과도하게 점유하는 문제가 실제 데이터에서 확인되면 완화한다.

단, 가까운 위치 자체는 제외 사유가 아니며 같은 장소라도 실제 경험이 충분히 다르면 별도 후보가 될 수 있다.

## 8. 무료 필터와 가격 미확인 — D-10

무료 필터는 **확인된 가격만으로 판정**한다.

| 가격 상태 | 무료 선택 시 처리 |
|---|---|
| 무료 확인 | 조건 충족 |
| 유료 확인 | 정상 무료 결과 제외, 필요 시 조건 완화 대안 |
| 가격 미확인 | 가격 추가 확인 필요 |
| 일부 비용만 확인 | 전체 무료로 보지 않고 가격 추가 확인 필요 |

### 노출 원칙
- 확인된 무료 후보가 충분하면 가격 미확인 후보를 정상 결과에 섞지 않는다.
- 확인된 무료 후보가 부족한 경우에만 `가격 추가 확인 필요` 후보를 별도 노출할 수 있다.
- 가격 미확인은 유료 확정이나 이용 불가가 아니다.

### Tech 후속 확인
가격 상태를 `free / paid / unknown / partial-or-ambiguous` 수준으로 정규화할 수 있는지 확인한다.
