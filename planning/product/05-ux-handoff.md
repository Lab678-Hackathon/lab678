## 1. Handoff 원칙

### Product 선결정
Product에서 결정 가능한 항목은 먼저 닫고 UX/Tech에 불필요한 공동결정을 넘기지 않는다.

Product가 고정하는 범위:
- 필수 / 선택 정보
- 정보 우선순위
- 단계적 정보 공개 원칙
- 결과 상태의 의미
- 정상 / Fallback 흐름
- 가격·시간·미확인 판정 기준
- 즉시 추천(A)·특정 날짜 문화루트(B) 기능 완료기준
- MVP IN / OUT 경계

### UX 참조 (희영님)
Product 기준을 유지하는 범위에서 다음을 구체화한다.
- 화면 수와 단계 구성
- 카드 / 배지 / CTA 배치
- Accordion / Bottom Sheet / 별도 화면 등 Interaction
- 시각적 위계·화면 배치와 입력 UI·그룹화
- 접기/펼치기·상세 진입
- 합의된 입력·결과 상태·다음 행동을 정확히 전달하는 라벨·버튼·최종 UI 문구
- Visual Design

사용자 화면에는 내부 Product/Tech 용어를 그대로 노출하지 않는다. `조정 가능한 예산`, `필수 조건`, `추가 확인 필요`처럼 뜻을 전달하며 구체적인 최종 Copy는 UX/UI가 정한다.

### Tech 참조 (용택님)
아래 Product 동작을 충족하는 구현 방식은 Tech가 결정하고 실제 동작을 검증한다.
- 위치 취득 및 직접입력 Fallback
- 가용시간(Time Boundary) 변환
- 기존 일정 AI 구조화
- 데이터 상태 정규화
- 이동시간 산출
- 루트 조합·재계산
- 오류·재시도 처리

### 공동 확인
UX/UI는 합의된 Product 요구사항을 유지하며 화면·Interaction·문구를 재구성한다. **입력/출력, 상태·대안 흐름·신뢰 기준, MVP 범위·완료기준을 바꿔야 할 때만 Product와 재조율한다.** Tech 구현 제약은 가능한 해결책을 먼저 검토한 뒤 요구사항 유지가 어려울 때 조율한다.

통합회의 결정: 즉시 추천(A)·특정 날짜 문화루트(B)를 모두 진행하며 A 우선 고도화 → B 후속 구현한다. B 난도가 예상보다 높으면 팀에 공유한 뒤 범위를 조정할 수 있다. 아래 Low-fi ID는 기존 요구사항 연결용이며 새 화면 수·분할을 확정하지 않는다. 이번 문서 동기화에서는 Figma를 수정하지 않는다.

## 3. Product User Flow · 공통 사용자 여정

### 즉시 추천(A) Product User Flow
- **대표 상황:** 서울 도심을 자유여행 중이며 지금부터 사용할 수 있는 시간이 있고 문화경험을 원하지만 구체적인 장소·활동은 정하지 않은 상태다. `2~4시간`은 대표 검증 시나리오이며 서비스 이용조건이 아니다.
- **흐름:** 즉시 추천 필요 → 현재 조건 확인 → 판단에 필요한 조건 충족 여부 확인 → 후보 판단 → 조건 충족/추가 확인 필요/조건 완화 대안이면 소수 후보 비교, 적합 후보가 없으면 0건 안내·조건 조정 → 필요한 신뢰·이동 정보 확인 → LF-03 `Select experience`로 장소 선택 → LF-09에서 명시적으로 저장·확정 → 현재 선택 상태 저장.
- **주요 분기:** 위치 권한 거부는 직접 위치 입력, 핵심 조건 모호는 필요한 값만 추가 확인, 후보 부족은 조건 완화 대안 또는 명확한 0건으로 연결한다. 데이터·AI·네트워크 오류는 정상 Product 결과가 아닌 전 구간 공통 시스템 예외로 두고 재시도·안내한다.
- **정상 완료:** A는 LF-03에서 장소를 고른 뒤 LF-09에서 별도의 저장·확정 동작을 완료해 현재 선택 상태가 저장되면 완료한다. 저장 전에는 확정된 현재 선택으로 취급하지 않는다. 외부 지도 실행이나 실제 장소 도착은 완료조건이 아니다.

### 특정 날짜 문화루트(B) Product User Flow
- **대표 상황:** 오늘 또는 가까운 특정 날짜에 시작점과 연속해서 사용할 수 있는 시간이 있고, 그 안에서 고정 상한 없이 실행 가능한 문화경험 최소 2곳을 연결하고 싶은 상태다. 전체 여행일정을 새로 만드는 기능은 아니다.
- **흐름:** 문화루트 필요 → 날짜·시작점·가용시간 확인 → 판단에 필요한 조건 충족 여부 확인 → 신뢰 가능한 개별 후보 판단 → 2개 이상 조합 가능 여부 판단 → 최소 2곳·상한 없는 루트 구성 → 시간·조건·이동부담·전체 동선 확인 → `이 루트로 갈게요` → 현재 선택 상태 저장.
- **주요 분기:** 신뢰 가능한 2개 이상을 조합할 수 없고 실행 가능한 개별 후보가 있으면 개별 추천으로, 개별 후보도 없으면 루트 구성 실패·조건 조정으로 이어간다. 3개를 강제로 채우지 않는다.
- **정상 완료:** 신뢰 가능한 문화경험 최소 2곳(장소 수 고정 상한 없음)이 순서 있는 루트로 구성되고 사용자가 `이 루트로 갈게요`를 확정해 선택 상태가 저장되면 완료한다. 실제 도보 경로선·구간별 거리·예상시간의 구체 구현 수준은 구현 단계 후속 확인이다.

### 즉시 추천(A)·특정 날짜 문화루트(B) 공통 사용자 여정
`상황 발생 → 조건 전달 → 결과 판단 → 신뢰 확인 → 이동·동선 판단 → 선택 확정 → 방문 이후`

7단계 × 8행의 행은 **대표 사용자 질문·가설 / 즉시 추천(A) / 특정 날짜 문화루트(B) / KONNECT 역할 / 신뢰·실패 방지 원칙 / Pain Point·가설 / 감정 흐름·가설 / Low-fi 화면 연결**이다. 정본은 제품 기획 기준서 §11이며, Pain Point·감정 흐름은 검증된 사실이 아닌 Product 가설이다. H3/D-17은 선택 사항이고 진행할 경우 결과를 참고해 보완한다.

- 사용자의 핵심 질문은 `지금 무엇을 할 수 있지? → 무엇을 얼마나 입력해야 하지? → 왜 이걸 추천하지? → 정말 가능한가? → 실제로 이동할 만한가? → 이걸로 정할까?`로 이어진다.
- KONNECT는 필요한 조건만 받고, 선택지를 좁히고, 추천 근거와 확인된 사실·계산/판단·미확인을 구분하고, 이동부담을 판단할 수 있게 하며, 사용자의 현재 선택 상태를 유지한다.
- 선택 수와 실제 방문을 혼동하지 않는다. 방문 후 최소 피드백은 **9/28 Tech 검토에서 구현 가능으로 확인됐지만 Product 조건부 상태를 유지**하는 후속 단계이며 즉시 추천(A)·특정 날짜 문화루트(B) 정상 완료조건에는 포함하지 않는다. 동일 기술 가능성은 다시 묻지 않고 실제 MVP 포함 여부만 일정·우선순위로 후속 결정한다.

### Product / UX 경계
- Product User Flow 단계와 실제 화면은 1:1로 고정하지 않는다.
- **Product:** 사용자 상황, 필요한 정보, 판단 기준, 상태 의미, 정상·대안 분기, 완료조건, MVP 범위를 정의한다.
- **UX/UI:** 상세 확인 → 이동 확인 → 선택 확정의 판단 위계를 유지하며 화면 수·통합/분리·전환 구성, Interaction, 최종 Copy, Visual Design을 구체화한다.
- 내부 지도는 선택을 위한 이동 판단 정보이며 GPS 추적·턴바이턴 내비게이션이 아니다. 상세·실시간 길찾기는 외부 서비스로 연결한다.
- 환경 Context는 일반 주의와 공식 위험 수준을 구분한다. 공식 위험 특보·경보로 Outdoor 정상 추천이 부적절하면 관련 경험을 정상 추천에서 제외하고 실내 대안을 우선하되, 행사 취소 여부는 별도 공식 운영정보로만 판단한다.

## 4. 단계적 정보 공개

- 메인에서는 즉시 추천(A)·특정 날짜 문화루트(B) 두 핵심 목적을 우선 보여준다.
- 기존 여행계획은 **즉시 추천(A)·특정 날짜 문화루트(B) 추천에 선택적으로 반영하는 공통 Context**다.
- 메인에서 위치 권한을 미리 요청하지 않는다. 즉시 추천(A)을 시작해 현재 위치가 필요해지는 시점에 요청하고, 거부 시 직접 입력으로 연결한다.
- 즉시 추천(A)은 **시작 위치·시작 시각·종료 시각**을 구조화된 필수 입력으로 확보한다. 현재 위치·현재 시각은 변경 가능한 기본값이다.
- 관심사·예산·이동 선호·기존 여행계획·날씨 관련 선호 등은 하나의 자연어 선택 입력 영역에서 보완하는 방향이다. 실제 날씨는 시스템/API 환경 Context이며 사용자는 날씨 관련 선호만 전달한다.
- 특정 날짜 문화루트(B)는 날짜·출발 위치·시작 시각·종료 경계를 확보하는 안내·입력 예시가 있는 자연어 대화 중심이다. 관심사·예산·동행·이동 조건·기존 일정은 선택 정보이며 완전히 빈 자유입력으로 고정하지 않는다.
- 10/13 A 일정 범위 조정: 다음 고정 일정 이동·도착시간 및 복수 일정 자동충돌 계산은 현재 MVP 필수에서 제외한다. 사용자에게 `Available until` 입력 시 다음 일정으로 이동할 시간을 고려하도록 안내한다. 실제 반영되지 않은 일정값은 AI가 반영한 것처럼 표시하지 않는다. 전체 일정 자연어는 선택형 Context다.

## 5. Product Low-fi 화면 세트 9+1

> 9/27 Figma 정리에서 B 사용자 흐름 순서에 맞춰 LF-04를 특정 날짜 문화루트(B)·조건 설정, LF-05를 특정 날짜 문화루트(B)·결과로 재번호화했다. 화면 분할·통합·전환 순서는 UX/UI가 결정한다.

### LF-01 — 메인 / 진입

#### Product 기준
- 즉시 추천(A) / 특정 날짜 문화루트(B)를 메인의 두 핵심 행동으로 명확히 제시한다.
- 기존 여행계획은 독립 기능·CTA가 아니라 **즉시 추천(A)·특정 날짜 문화루트(B) 추천에 선택적으로 반영하는 공통 Context**로 다룬다.
- 추가 구현 후보 (Stretch)는 핵심 진입에 올리지 않는다.
- 로그인 / 사용자 식별은 핵심 즉시 추천(A)·특정 날짜 문화루트(B) 행동보다 우선하지 않는다.
- `현재 선택 보기`는 실제 선택 상태가 있을 때만 노출한다. 재검색·조건 변경만으로 선택을 지우지 않고 새 최종 선택 시에만 교체한다.
- 위치 권한은 메인에서 선요청하지 않는다.
- My Page MVP 최소범위는 개인화 관리·현재 여행/최근 선택을 다시 찾는 최소 진입점·계정 정보다. A의 현재 장소 선택은 **My Pick**, B 현재 문화루트는 **My Route**로 구분한다. 이 명칭은 사용자-facing이며 A/B 내부 코드·전체 저장 이력 관리 기능을 새로 요구하지 않는다. 장기 추천에 실제 사용하는 확인된 사용자 선호를 확인·수정·초기화할 수 있어야 하며 이후 추천부터 적용한다. 사용자 확인 전 선호 후보 신호는 장기 선호가 아니며 복잡한 추정 선호 관리 UI는 필수가 아니다. 전체 추천 이력·방문 통계·취향 분석·Stamp/Collection은 MVP 필수가 아니다. 추가 개인화 정보 입력은 Skip 가능하게 하며 상세 화면·Interaction은 UX/UI가 설계한다. 검색창·하단 내비게이션·즐겨찾기 전체를 자동 추가하지 않는다.
- 로그인·상태관리는 MVP IN, Google Social Login 방향이다. 비회원은 첫 추천 결과까지 1회 체험하고 두 번째 추천 또는 재추천 요청 시 로그인 유도한다. 첫 결과 전에 로그인하지 않아도 된다. B의 현재 루트 편집·복구와 새 조합 요청 구분은 [B 로그인 적용 경계](#b-로그인-적용-경계)를 따른다.
- 첫 화면의 신뢰 원칙은 내부 용어 `신뢰 안내`보다 사용자-facing `정보 확인 안내`를 사용한다. 영문 제목은 `About the information`을 기본안으로 둔다.

### P-09 — First-time preference onboarding (독립 Product Low-fi)

- 최초 가입 선호 설정의 관심사 6개는 초기 기본 선택이 없으며, 사용자가 아무것도 선택하지 않고 Skip하는 것도 허용한다.

- MVP 기본 흐름은 **자유입력 → LLM 해석 → 해석된 선호 확인·수정 → 저장**이다. 장시간 챗봇 상담이나 반복 추가질문을 기본 흐름으로 요구하지 않는다. UX는 짧고 자연스러운 입력·확인 Interaction을 설계한다.
- 사용자가 확인한 해석값만 User Preference로 저장한다. 저장 선호는 Soft ranking 보조이며 현재 Request > Trip > Preference·확인 사실/필수 조건 우선. 저장 선호만으로 숫자형 Hard 상한·M01/M02 또는 `Within your walking limit`을 생성하지 않고 접근성·건강·장애 상태를 추론하지 않는다. My Page 조회·수정·초기화 가능.
- Request/Trip 값(현재 예산·동행·일정·가용시간)은 가입 장기 선호로 자동 저장하지 않는다.
- 두 번째 추천/재추천 Gate의 최초 가입은 설정/Skip 후 보존된 흐름 계속; LF-01 자발적 가입도 원래 맥락 유지. 요청조건·결과·현재 선택을 잃지 않는다. 별도 LF/MP 번호 없음. 상세 저장·노출·연속성 기준은 [06 · P-09](./06-ai-tech-boundary.md#p-09--최초-google-가입-선호-온보딩), 기존 P-01~P-08 유지.
- UX는 입력 위젯·최종 Copy·Interaction·Visual Design, Tech는 OAuth·신규회원 판별·저장/복원을 결정한다.

### LF-02 — 즉시 추천(A)·조건 설정

> **10/19 Product 정책 동기화:** 최소 가용시간 60분(출발지에서의 이동 포함). 기존 빠른 선택 `In 1 hr / 2 hr / 3 hr / 4 hr` 유지, 종료 당일 24:00 경계 및 종료 자동 연장 금지 유지. `About 60 min` 등의 관람 예상·권장시간은 필수 체류시간이 아니라 참고값이다. B 시간 정책 및 추천 알고리즘은 변경하지 않는다.

#### Product 기준
- 현재 위치·현재 시각을 빠른 기본값으로 사용한다.
- 출발 위치·시작 시각은 변경할 수 있다.
- 시작 위치·시작 시각·종료 시각은 구조화된 필수 입력이다. LF-02 가용시간은 **최소 60분(1시간) 이상·시작일 24:00까지**이며 별도의 4·6·12시간 상한은 없다. 종료 시각 자동 기본값·시작 변경에 따른 종료 자동 연장은 없고, 시작 시각이 종료 시각 이상이면 종료 재선택을 요청한다.
- 종료 미입력·시작/종료 역전·60분 미만·경계 초과는 추천 전 입력 오류 또는 제한이며, 유효한 입력에서 후보가 없는 경우만 기존 추천 0건·원인별 Fallback을 사용한다. 위치 권한 실패는 추천 실패가 아니라 직접 입력으로 대체한다. 경계 표기와 최소 60분의 운영 목적은 [04 · 시간 기준](./04-route-time-rules.md#3-start-anchor--time-boundary)을 따른다. 오류·제한의 구체 Copy·Interaction은 UX/UI가 설계한다.
- 관심사·예산·이동 허용조건·기존 일정·날씨 관련 선호·기타 요구는 하나의 자연어 선택 입력 영역에서 보완하는 방향이다. 예산과 이동 조건은 서로 다른 의미로 구조화하며 미입력을 허용한다. 실제 기상정보는 시스템/API Context로 구분한다.
- D-06의 5개 문화경험 유형은 내부 콘텐츠 분류이며 사용자 관심사 분류와 동일하지 않다. 관심사는 선택·복수 선택 가능한 Soft Preference다. 최종 관심사 6개는 `Traditional Culture / 전통문화`, `Palaces & Historic Sites / 역사·궁궐`, `Hands-on Experiences / 문화 체험`, `Art & Exhibitions / 미술·전시`, `Live Performances / 공연`, `Festivals & Events / 축제·이벤트`다. 하나의 콘텐츠에 복수 태그가 가능하다. 자연어에서 관심사가 추출되면 같은 6개 값으로 구조화한다. 기존 6개 Chip 선택 UI를 필수 입력방식으로 고정하지 않는다.
- 긴 설문을 완료해야 추천되는 구조로 만들지 않는다.
- A/B Starting point는 현재 위치·직접 검색을 유지하면서 대표 시작점 5개의 Quick Select를 보조로 제공한다. 선택은 출발점 입력이며 지역 전용 추천·2km Hard Filter가 아니다. B 미래 날짜 GPS 자동 가정 금지; 상세 5개·역할 경계는 [02 · Quick Select](./02-input-recommendation-rules.md#location-quick-select--starting-point-입력-보조)를 따른다.

### LF-03 — 즉시 추천(A)·결과+지도 통합

#### Product 기준
- 현재 팀 방향은 **최대 3~4개 범위의 소수 후보**이며 고정 수를 보장하지 않는다. 신뢰 가능한 후보가 1~2개뿐이면 억지로 채우지 않는다. 0건에서는 조건을 몰래 완화하지 않고 명시적 대안·조건 조정을 제공한다.
- 상태를 `조건 충족 / 추가 확인 필요 / 조건 완화 대안`으로 구분한다.
- **10/14 A 예산 Alternative 확정:** `Under ₩20,000 each` 등 일반 금액 상한은 정상 추천의 충족 기준이지만, 적합 후보가 부족하고 다른 필수 실행조건에 충돌하지 않는 **확인 가격의 초과 후보**는 초과액·완화 이유를 표시한 `Alternative`로만 제공할 수 있다. `Never exceed` 등 절대 예산 상한은 제외한다. 가격 미확인을 초과액으로 추정하거나 `Partially confirmed`로 예산 초과를 감추지 않는다. 대안을 강제로 채우지 않으며 B 총예산 기준은 변경하지 않는다. 상세는 [02 §2·§6](./02-input-recommendation-rules.md).
- 추천 이유는 현재 요청/유효 Context + 확인된 후보 근거 + Match Rule이 있을 때만 생성한다. 사용자-facing에는 검증된 Primary 1개를 우선하고 유의미한 Secondary 최대 1개를 추가한다. 근거가 0개여도 그 이유만으로 후보 자동 제외·주 상태 변경을 하지 않으며 강제로 채우지 않는다. 내부 Fit명은 그대로 노출하지 않고 Fact와 Reason을 구분한다.
- **Reason Copy Dictionary v1.0**: `product/reason-copy-dictionary.md`의 **영어 기본 Copy 17개**(T01~T04 / M01~M03 / I01~I06 / B01~B02 / P01~P02)를 디자인 인계 기준으로 사용한다. 해당 파일의 각 출력·미표시 조건은 Product 기준이다. 17개 동시 노출·17개 즉시 필수 구현이 아니라 실제 매칭된 근거에 따라 후보당 0~2개만 표시한다.
- **희영님 확인 시나리오**: Reason 0개(별도 중립 확인 안내 가능·Reason 아님), 1개 단독, 2개, **가장 긴 영문 기본 Copy 51자**, 지도·카드·상세에서의 줄바꿈과 상태/Fact/예약조건 간 정보 위계. A는 후보별, B는 루트 전체와 개별 장소별 근거를 분리한다. Chip/Badge/시각/최종 짧은 Microcopy는 의미를 보존하는 범위에서 UX/UI 재량이다.
- 우선 정보: 결과 상태 / 추천 이유 / 시간 적합성 / 가격 / 이동 부담 / 핵심 예약·참여조건.
- 현재 방향은 **Map UI 기반 결과**다. 지도만 보여주지 않고 위 주요 판단정보를 가능한 한 추가 화면 없이 함께 제공해 상세페이지 왕복을 줄인다. 지도 비율·카드 형태·스크롤 방식은 UX/UI 재량이며 상세 확인→이동 확인→선택은 독립 화면 고정이 아닌 판단 위계다.
- 공식·원천 데이터에서 신뢰 가능한 대표 이미지가 확보된 경우 카드의 보조 의사결정 정보로 제공한다. 이미지 부재만으로 후보를 제외하지 않으며 임의 이미지·AI 생성 이미지로 실제 장소 이미지를 대체하지 않는다.
- Low-fi에서는 `대표 이미지 (있을 경우) / Representative image (if available)` 정도의 Placeholder로 존재 가능성만 표시하고, 이미지 위치·비율·Crop·이미지 없음 상태의 카드 레이아웃은 UX/UI가 결정한다. 영상은 MVP 필수 OUT이다.
- Hard Condition은 일반 상세보다 우선한다.
- 미확인을 무료·예약 불필요·이용 가능으로 해석하지 않는다. 알려진 필수 조건 충돌이 없고 공식 확인이 가능하며 의사결정 가치가 남은 후보만 `추가 확인 필요`로 노출한다. 미확인 때문에 시간 적합성·실행 가능성 또는 자동 루트 구성을 신뢰성 있게 판단할 수 없으면 추천 또는 자동 루트에서 제외하며 추정하지 않는다.
- 중간 상태의 기존 의미는 유지하고 **`Partially confirmed`를 사용자-facing 선호 영문 후보로 검토**한다(팀 최종 문구 확인 전). 과거 `Check needed`는 이용자에게 확인 책임을 떠넘기는 듯한 표현으로 재검토됐으며, **문화경험 전체를 대표하는 부정 라벨처럼 보이지 않도록**, 확인된 적합 요소와 실제 미확인 항목을 함께 구체적으로 보여준다. 짧은 영문 문구·배치·시각적 강도는 UX/UI가 조정한다. 데이터 보완 후에도 발생 비율이 과도하면 상태 표현을 다시 검토한다.
- A의 현재 요청에서 사용자가 명시적으로 원하지 않는 유형·대상, 과거 방문 장소, 향후 방문 예정 장소는 해당 요청의 제외조건이다. 후보 부족이어도 몰래 다시 포함하지 않으며 장기 선호로 자동 저장하지 않는다.
- LF-06 공통 상세는 선택적 확인 경로다. 선택 전 중요한 예약·참여·미확인 조건은 LF-03 카드에 직접 표시하며 일반적 반복 안내는 생략 가능하다. 상세 설명과 공식 확인·예약·외부 지도 등 실제 다음 행동으로 연결한다.
- LF-03의 지도 핀·카드 스와이프는 탐색 포커스 변경일 뿐 선택·저장이 아니다. A는 `Select experience`로 후보를 고른 뒤 LF-09에서 별도의 `Save / Confirm` 성격의 동작으로 최종 확정·저장한다(정확한 영문 문구·배치는 UX 재량). LF-09 도달만으로 저장하지 않으며 미확정 후보를 기존 확정 선택과 구분한다. LF-06은 선택적 상세이며, 선택 확정은 예약·참여·실제 방문 완료가 아니다.
- 조건 수정 / 재추천이 가능해야 한다. 비회원 첫 추천 탐색·최초 확정은 로그인 없이 가능하며 두 번째 새 추천/재추천 시에만 Google 로그인 유도. `Not now`는 기존 결과·탐색을 유지하고, 로그인 후 현재 조건·결과·선택을 잇는다.
- 도보 경로선·거리·시간은 각각 실제 확인된 경우에만 표시한다. 확인 가능한 일부 구간만 별도 표시하고 미확인 구간은 임의 연결하지 않는다. 한 경로의 검증 구간을 식별할 수 없으면 경로선을 숨기고 핀·확인 수치·외부 지도 대안을 사용한다.

#### UX 참조 (희영님)
- 세 상태의 시각적 구분
- 카드 안 정보량과 정보 우선순위 표현
- 미확인 경고 수준
- 조건 완화 대안의 차이 설명
- 상세 / 공식 확인 / 지도 / 조건 수정 CTA 배치
- 현재 위치·목표·실제 도보 경로·시간·거리의 모바일 지도 표현과 `이 장소로 갈게요` 행동. Social Proof는 초기 기본화면 필수가 아니다.

### LF-04 — 특정 날짜 문화루트(B)·조건 설정

#### Product 기준
- 날짜·시작 위치·시작 시각·종료 경계는 기능 성립을 위한 필수 정보다.
- **Conversation-first:** 자연어 요청이 주 경로(입력 자체는 강제하지 않음) → KONNECT 구조화 → 누락·모호한 필수값만 질문 → 확인된 Date / Starting point / Start time / End boundary의 compact editable summary → 필요 시 직접 수정 → `Show culture route`. 날짜·위치·시간 Form을 먼저 채우는 본체로 표현하지 않는다. 이미 받은 값은 유지한다.
- **LF-04 Guided Chat 3+1 대표 상태:** 같은 LF-04의 S1 Start(안내·자연어 예시), S2 Clarification(User ↔ KONNECT Turn·누락값 질문), S3 Ready to generate(필수 4값 확인 후 생성 직전), V1 Direct edit / Ambiguity(해당 Hard 값만 수정)로 표현한다. 대화 입력창은 지속하고 Plan summary는 보조 수준, Quick Action은 Starting point가 필요할 때만 제공한다. 새 기능·글로벌 LF 번호가 아니며 실제 화면 분할·전환 Interaction은 UX 재량이다.
- `Edit details directly`는 보조 경로이며 필수 4값이 모두 확인된 때만 생성 가능하다. 여러 누락값은 한 번에 간결하게 묻고 반복 모호값은 해당 날짜·시작점·시간만 직접 수정한다.
- Starting point가 필요할 때 현재 위치 / Search / Popular starting points 5개를 입력 보조로 제공한다. 큰 지역 선택 UI가 처음부터 주도하지 않으며 지역 추천 모드·2km Hard Filter가 아니다. 선택 Context를 필수 Form 또는 전체 여행 Planner로 승격하지 않는다.
- 관심사·예산·동행·이동 조건·기존 여행계획은 선택 정보다. 관심사는 공통 6개 값으로 구조화하고 복수 관심사·미입력을 허용한다.
- 오늘은 현재 위치를 기본값으로 쓸 수 있으나 미래 날짜의 시작점을 현재 GPS 위치로 자동 가정하지 않는다. 사용자가 시작 위치를 지정·확인할 수 있어야 한다.
- `문화루트 보기`로 이어가며 초기/미입력과 콘텐츠 예시 상태는 필요할 때 구분한다.
- 예산은 루트 전체 문화경험의 확인된 필수 비용 기준이며 가격 미확인은 0원이 아니다. 이동 조건은 주로 경험 간 구간별 이동 부담 기준이다.
- 기존 일정이 없거나 추가 Context를 원하지 않는 사용자는 핵심 루트 흐름을 계속할 수 있어야 한다.
- 누락된 필수조건만 확인하고 여러 필수값이 빠지면 간결하게 묶어서 질문한다. 모호·충돌값은 추정하지 않는다. 반복 모호 응답에는 예시와 해당 조건의 직접 수정 경로를 제공한다. 별도 전체 입력 화면 전환·AI 동적 UI 생성은 필수가 아니며 구체 Interaction은 UX/UI, 수정값의 실제 요청 반영은 Tech가 판단한다.

#### UX 참조 (희영님)
- 즉시 추천(A) 조건 설정과 공통화할 입력 패턴
- 필수/선택 정보의 단계 구성
- 기존 일정 Context 진입·확장 방식
- 입력 순서와 CTA 배치

#### Tech 참조 (용택님)
- 날짜·시작점·가용시간 정규화
- 기존 일정 구조화 결과의 루트 판단 반영
- 모호값 처리 및 루트 생성 조건

### LF-05 — 특정 날짜 문화루트(B)·결과

#### Product 기준
- 특정 날짜·시간 범위 안에서 하루 1코스, 문화경험 **최소 2곳·고정 상한 없는 루트 1개**를 제공한다. 실행 가능한 2개 이상 조합은 정상이며 이용시간을 채우기 위해 후보를 강제로 추가하지 않는다.
- 전체 여행 플래너가 아니다.
- 방문 순서·시간·이동·확인된 비용·핵심 예약/참여조건·미확인 조건을 이해할 수 있어야 한다.
- B 추천 이유는 **루트 전체**와 **개별 문화경험**의 이유를 구분한다. 루트 완성만으로 Plan Fit을 자동 생성하지 않으며 기존 외부 일정과의 검증된 연결이 있을 때만 생성한다. 고정 상한 없이 최소 2곳 이상 구성을 검증하고, 시간값의 실제/계산/계획/미확인 구분을 유지한다. 재구성 실패로 이전 루트를 유지해도 과거 이유를 변경된 조건에 적합한 것처럼 재사용하지 않는다.
- 시간은 공식/확인값, 계산된 예상값, Product 계획값, 미확인값을 구분한다.
- 확인되지 않은 실제값을 임의 생성하지 않는다.
- 신뢰 가능한 2개 이상 조합이 성립하지 않으면 루트를 억지로 만들지 않는다. 가능한 경험을 개별 제안하거나 루트 생성 불가 상태를 안내한다.
- 조건 수정 / 장소 제외 / 재구성이 가능해야 하며 변경하지 않은 유효 입력은 유지한다. 제외 장소는 해당 재구성에 임의 재삽입하지 않고, 영향받는 시간·운영·이동·비용의 실행 가능성을 재검증한다. 재구성 후에도 정상 루트는 최소 2곳·고정 상한 없음·실행 가능성 우선 기준이다. 가격·예약은 경험별로 확인한다.
- 재구성 실패 시 이전 조건·결과를 새 조건과 구분하고 직전 조건·결과로 복귀할 최소 경로를 제공한다. 이전 루트를 새 조건의 정상 결과로 표시하지 않으며, 새 루트 명시적 선택 전 기존 확정 선택을 자동 교체·삭제하지 않는다. 전체 루트 히스토리 UI는 필수가 아니다. 상세 판단 기준은 [04 · 재구성·실패](./04-route-time-rules.md#7-문화루트-수정재구성실패-fallback)를 따른다.
- 경험 상세 및 외부 다음 행동으로 연결한다.
- 순서가 명확한 LF-08 루트 지도로 이동을 이해하고 그곳에서 `이 루트로 갈게요`로 최종 선택을 확정해 현재 루트 선택 상태를 유지한다. 지도·경로의 즉시 추천(A) 우선 구현 → 특정 날짜 문화루트(B) 후속 구현 순서는 Tech와 확인 완료이며 특정 날짜 문화루트(B) Product 요구사항은 유지한다. 실제 도보 경로선·구간별 거리·예상시간의 구체 구현 수준만 구현 단계에서 후속 확인한다. 내부 내비게이션 시작이 아니다.

#### B 로그인 적용 경계

- 첫 루트 생성·검토·선택, 현재 루트 편집·복구(`Remove and rebuild`, `Undo`), 지도 확인·`Go with this route`, 조건 수정 자체에는 로그인을 유도하지 않는다.
- `Rebuild with other places`, `Find another route`, 조건 변경 후 새 루트 생성처럼 **새 후보 조합을 실제 생성하려는 시점 직전**에 로그인을 유도한다. 현재 루트 편집·복구와 새 후보 조합 요청을 구분한다.
- `Not now`에서는 기존 루트·조건·현재 선택을 보존하고 새 루트를 생성하지 않는다. 로그인 성공 후에는 기존 맥락을 유지하여 중단된 새 추천/재추천을 재개한다. 공통 Google 로그인 유도를 사용하며 B 전용 화면을 추가할 필요는 없다.

#### UX 참조 (희영님)
- 순서·시간·이동 관계 표현 방식
- 실제값 / 계획값 / 미확인값의 시각적 구분
- 비용·예약·미확인 정보 위계
- 장소 제외·재구성 Interaction
- 루트와 공통 경험 상세 간 이동
- 지도+목록, 지도/목록 전환, 요약 후 별도 지도 중 모바일 1–2안 제안. 경로 제공 범위는 Tech 확인 결과에 맞추고 임의 직선을 실제 경로처럼 보이지 않게 한다.

#### Tech 참조 (용택님)
- 최소 2곳 이상 조합의 실행 가능성 판단
- 운영시간·고정시각·소요시간 처리
- 이동시간 산출
- 실제 소요시간과 Product 계획시간 분리
- 확인된 비용만 합산하되, 필수비용 미확인 경험이 포함되면 확인된 합계만으로 루트 전체를 `예산 충족`으로 판정하지 않고 `총비용 추가 확인 필요`를 함께 표시
- 고정형 경험 실행시간 미확인 시 자동 루트 제외
- 장소 제외 후 루트 전체 재계산

### LF-06 — 공통 경험 상세 / 공식 확인

#### Product 기준
- 결과 상태→추천 이유→시간 적합성→가격→이동 부담→예약·참여 조건→미확인 정보→공식 상세·예약·확인 경로 순으로 이해할 수 있어야 한다.
- 확인된 사실, KONNECT 계산·판단·예상, 공식 확인 필요를 구분하고 출처·조회시점을 제공한다. `미확인 ≠ 무료 / 예약 불필요 / 이용 가능 보장`을 유지한다.
- 신뢰 가능한 대표 이미지가 있으면 상세에서도 활용할 수 있으며, 이미지가 없으면 빈 Placeholder를 최종 UI에 강제하지 않는다.
- 미확인 항목은 구체적으로 무엇이 미확인인지 표시하며 Trust score는 사용하지 않는다.
- 예약 상태와 확보된 공식 URL에 따라 공식 상세·예약·확인 CTA를 조건부 제공한다. 같은 URL의 CTA는 중복 제공하지 않는다. 예약이 필요 없는 경험에 예약 CTA를 강제하지 않고 특정 날짜 문화루트(B)에서 진입했다면 루트로 돌아갈 수 있다.

#### UX 참조 (희영님)
- LF-06은 A/B 모두 선택적 경험 상세·공식/출처 확인이며 선택 완료의 필수 경유 화면이 아니다. B는 LF-05에서 LF-08로 직접 이동할 수 있다.
- 정보 우선순위와 접기/펼치기
- 카드에서 선택적으로 상세로 이어지는 방식
- 경고·미확인 정보의 시각적 강도
- 상세 확인 → 이동 확인 → 선택의 판단 위계를 유지하는 전환 구성

#### Tech 참조 (용택님)
- 출처·조회시점·확인/미확인 데이터 전달
- 공식 URL 및 예약/확인 경로 제공 가능 범위

### LF-07 — [Legacy] A 도보 지도 분리안 (현재 LF-03 통합)

#### Product 기준
- 별도 LF-07 화면은 활성 A Flow에서 폐기되었으며, 아래 이동 판단·Fallback은 LF-03 통합 지도에 적용하는 기존 참고 기준이다.
- LF-02에서 확정한 시작 위치와 목적지, 확인 가능한 도보시간·거리를 통해 도보 이동부담을 판단한다. 실제 도보 경로선은 확보 가능할 때 제공한다.
- 경로선과 시간·거리가 신뢰 가능하면 모두 제공한다. 경로선만 없으면 출발/도착 핀+신뢰 가능한 시간·거리+외부 지도, 시간·거리도 불확실하면 핀+외부 지도 확인으로 낮춘다. 임의 직선을 실제 경로처럼 표시하지 않는다.
- A의 `이 장소로 갈게요`/`Select experience`는 LF-09 저장·확정 직전의 장소 선택 단계이며, LF-09의 명시적 저장·확정 동작이 최종 확정이다. 보조 행동 `지도 앱에서 길찾기`로 외부 지도를 여는 것은 선택 확정이 아니다. 남은 `공식 확인 필요`는 선택 직전에도 유지한다.
- 내부 지도는 턴바이턴 내비게이션이 아니며 대중교통 상세 길찾기는 외부 지도로 연결한다.
- 이동시간 미확인만으로 후보를 자동 제외하지 않는다. 긴 도보시간만으로도 자동 제외하지 않는다. 사용자가 이동 허용시간을 명시한 경우에만 해당 조건을 판단에 반영한다.

#### UX 참조 (희영님)
- 지도 비율·정보 배치
- 상세 확인 → 이동 확인 → 선택의 판단 위계를 유지하는 화면 구성
- `이 장소로 갈게요`와 외부 상세 길찾기의 시각적 위계

#### Tech 참조 (용택님)
- 실제 도보 경로·거리·시간 산출 범위
- 외부 지도 연결 방식

### LF-08 — 특정 날짜 문화루트(B) 지도·이동 결정

#### Product 기준
- LF-05와 동일한 경험·순서를 유지한다. 시작점은 경험과 별도로 표시하며 시작점→장소 1→장소 2→장소 3(2개면 장소 2까지)의 전체 루트를 보여준다. 경험 2개면 경험 간 이동 구간은 1개다. 구간별 이동수단·시간·거리를 표시하고 지도 번호와 장소명을 대응시킨다.
- 루트 전체 이동 부담과 루트 전체 소요시간을 구분한다. 일부 구간 미확인은 명시적으로 유지하며 부분 미확인 상태의 총 예상값은 근거가 있는 경우에만 산출한다.
- 실제 경로선은 가능할 때 제공한다. 경로선·시간·거리 확보 수준이 낮으면 LF-03과 같은 신뢰 수준의 핀·구간정보·외부 지도 대안으로 낮추고 임의 직선·추정치를 실제 경로처럼 표시하지 않는다. 구체 구현 수준은 구현 단계 후속 확인 대상이다.
- 주 행동 `이 루트로 갈게요`는 참여 가능 보장이 아닌 루트 선택 확정이다. 남은 `공식 확인 필요`는 선택 직전에도 유지한다.

#### UX 참조 (희영님)
- 지도+목록 동시 / 지도·목록 전환 / 요약 후 별도 지도 등 모바일 1–2안 제안
- 장소 순서와 구간 부담의 시각적 이해 방식
- Tech 확인 결과에 따른 대체 표현

#### Tech 참조 (용택님)
- 시작점 + 선택된 방문 장소 전체의 실제 도보 경로선 산출 가능성
- 구간별 거리·시간 제공 가능 범위
- 불가할 경우 가장 가까운 구현 수준

### LF-09 — 현재 선택 상태

#### Product 기준
- 즉시 추천(A)의 장소 선택과 특정 날짜 문화루트(B)의 루트 선택은 같은 LF-09 요구의 내부 Variant다. 실제 사용자-facing 화면에서는 `A · 즉시 추천` / `B · 문화루트` 같은 내부 식별 라벨을 노출하지 않는다.
- LF-01에서 현재 선택으로 돌아갈 수 있고 선택 대상, 날짜+요일을 포함한 가용시간, 기본 이동정보, 핵심 예약·참여조건과 필요한 운영정보를 다시 확인할 수 있어야 한다.
- LF-09의 추천 이유는 LF-03/LF-05에서 **선택 당시** 확인한 Primary 최대 1개와 필요한 Secondary 최대 1개를 유지한다. 근거가 0개인 경우 비워두며 이유를 새로 생성하지 않는다. 주 상태·Fact·미확인 안내를 추천 이유와 구분하고, 실제 라벨/태그·컴포넌트·표시 밀도·최종 영문 Copy는 UX/UI에서 정한다.
- 즉시 추천(A)은 선택 날짜에 적용되는 운영시간을 신뢰 가능한 데이터로 확인할 수 있을 때만 해당 날짜 기준 운영시간을 표시한다. 특별·야간운영도 확인 가능하면 반영하고, 안정적으로 판단할 수 없으면 일반 운영시간을 당일 운영시간처럼 단정하지 않고 `운영시간 확인 필요`와 공식 확인 경로를 제공한다.
- 특정 날짜 문화루트(B)는 현재 선택한 루트를 식별할 수 있는 짧은 이름을 제공한다. 확인 가능한 지역명·주요 장소 정보를 우선 활용하고 근거 없는 테마명·지역명을 만들지 않으며, 안정적으로 만들기 어려우면 `문화루트`로 표시한다.
- B의 장소 순서와 각 장소의 계획 방문시간을 확인할 수 있어야 한다. KONNECT Product 계획시간은 `예정`으로 구분하고, 공식 고정 회차는 확인된 실제 시간과 혼동하지 않게 구분한다.
- A의 `이동 지도`는 LF-03 통합 결과+지도에서 현재 선택 후보를 다시 확인하도록 연결한다. 별도 LF-07 이동은 없다. B의 `루트 지도`는 LF-08로 연결한다. 상세·실시간 길찾기는 외부 지도 연결로 보조할 수 있다.
- `공식 정보`는 A에서는 선택한 문화경험 1건, B에서는 루트에 포함된 각 문화경험별 공식 상세·예약·참여조건 등 필요한 공식 확인 경로에 접근할 수 있게 한다.
- `조건 다시 설정` 또는 `다른 후보 보기`로 재탐색해도 기존 현재 선택을 유지한다. A는 LF-03에서 새 후보를 선택하거나 LF-09에 진입한 것만으로 기존 저장 선택을 교체하지 않으며, LF-09에서 명시적 저장·확정을 완료해야 교체한다. B는 LF-08에서 새 루트 선택을 확정할 때 교체한다.
- **2026-10-08 A 저장 기준:** LF-03 `Select experience`는 후보 선택, LF-09의 별도 저장·확정 동작은 현재 선택 저장이다. 저장 전 A 후보는 임시 선택으로 표시하고 `Your current choice`처럼 이미 저장된 선택으로 오인시키지 않는다. 취소·뒤로가기로 이탈하면 기존 저장 선택을 유지하며 새 후보는 저장하지 않는다. UX는 최종 버튼 명칭·배치와 임시/저장 상태 표시를 정하고, Tech는 저장 시점·복귀 동작을 구현한다. **B의 LF-08 `Go with this route` 확정은 변경하지 않는다.**
- 선택 상태는 실제 방문 완료를 의미하지 않는다. GPS 추적·자동 방문 판정·턴바이턴 내비게이션은 포함하지 않는다.

#### UX 참조 (희영님)
- A 후보 선택 뒤 LF-09에서 명시적으로 저장·확정할 수 있는 버튼/동작을 제공한다. `Save`/`Confirm`의 최종 영문 문구·배치는 UX 재량이며, 저장 전 후보와 저장된 현재 선택을 명확히 구별한다.
- **상단 이동수단 확보:** 고정 하단 내비게이션 바를 추가하지 않고 Home·Profile·Back 등 필요한 접근/복귀를 상단에서 제공한다. 화면별 노출·정확한 위치·아이콘·영문 문구는 UX 재량이며, A/B 간 전환과 이전 단계/홈 복귀가 막히지 않게 한다. 구현 동작은 Tech가 확인한다.
- 홈 안 상태로 둘지 별도 화면/영역으로 둘지
- B의 각 경험별 공식 정보 접근을 팝업·Bottom Sheet·별도 화면·장소별 직접 링크 중 어떤 방식으로 구성할지
- 이동 지도/루트 지도·공식 정보·재탐색 행동의 최종 시각 위계와 Interaction

#### Tech 참조 (용택님)
- 비회원→로그인 시 현재 요청 조건·추천 결과·현재 선택 등 연속성에 필요한 상태를 유지하고 동일 요청 재입력·처음부터 재시작을 방지한다. 임시 상태 전체를 여행 맥락·장기 사용자 선호로 자동 간주하지 않는다. 구체 임시 저장·식별·연결·이전·복원 방식은 Tech가 결정한다.
- 선택 날짜 기준 운영시간과 특별·야간운영을 데이터에서 신뢰성 있게 판정 가능한 범위. 불가하면 `운영시간 확인 필요` Fallback을 유지한다.
- 9/28 Tech 회신 및 추가 의미확인 완료: 비로그인도 즉시 추천(A)·특정 날짜 문화루트(B)를 이용할 수 있고 현재 요청에서 선택한 관심사·예산·이동조건을 해당 요청의 추천에 반영할 수 있다. 지속적 데이터 관리·기기 동기화·저장된 선호 재사용에는 제한이 있다. 당시 비로그인→로그인 상태 이전은 기술적으로 가능하나 Tech는 MVP 제외를 제안했다. 로그인 시점의 확정 정책은 비회원 첫 추천 결과까지 1회 체험·두 번째 추천/재추천 요청 시 로그인 유도이며 Google Social Login 방향이다. 10/1 P-06~P-08에서 추천 흐름 연속성을 Product 요구로 확정했다. 현재 요청 맥락 → 여행 맥락 → 사용자 선호 순으로 보완 적용하며 현재 요청이 기존 장기 선호와 충돌해도 기존 선호 자체를 자동 수정·삭제하지 않는다. 연속성 문제 시 전체 폼 대신 필요한 필수 조건만 최소 재확인한다. 구현 방식은 Tech가 결정하고 세부 맥락·선호 경계는 [06 · AI·Tech 경계](./06-ai-tech-boundary.md)를 따른다.

### LF-10 — 방문 후 최소 피드백 (조건부)

- **상태:** **Tech 구현 가능 확인 완료 · Product 조건부 유지.** 동일 기술 가능성은 재문의하지 않으며 실제 MVP 포함 여부만 일정·우선순위로 후속 결정한다.
- 예상 종료시각 이후 사용자가 KONNECT에 다시 들어왔을 때 방문 여부를 확인하는 Product 기본안이다.
- 방문했다면 `안내된 정보가 실제와 대체로 맞았나요?`, `이 추천이 선택에 도움이 됐나요?`를 최소 선택형으로 받는다.
- 방문하지 않았다면 `왜 가지 않았나요?`를 선택형으로 받는다.
- Push, GPS 자동 방문판정, 사진·장문 후기, 공개 UGC는 현재 범위가 아니다.
- 1화면/단계형 등 구체 Interaction은 UX/UI가 결정한다.

## 6. 정상 / 대안 흐름

### 즉시 추천(A)
**정상**
`즉시 추천(A) 선택 → 최소조건 확보 → 추천 생성 → 소수 후보 → 필요한 신뢰·이동 정보 확인 → LF-03 장소 선택(Select experience) → LF-09 명시적 저장·확정 → 선택 상태 저장`

**Fallback**
- 위치 권한 거부 → 직접 위치 입력
- 위치 권한 허용 후에도 현재 위치의 정확도가 추천·이동 판단에 충분하지 않으면 출발 위치 확인·수정 기회 제공
- 핵심값 모호 → 필요한 항목만 부분 확인
- 비교 가능한 후보가 있으면 추가 확인 필요·조건 완화 대안으로 구분 / 적합 후보가 없으면 비교 없이 0건 안내·조건 조정
- 데이터·AI·네트워크 실패 → 정상 결과와 분리한 전 구간 공통 시스템 예외·재시도 안내

### 특정 날짜 문화루트(B)
**정상**
`특정 날짜 문화루트(B) 선택 → 날짜·시작점·가용시간 확보 → 루트 생성 → 최소 2곳(고정 상한 없음)의 경험 결과 → 필요한 신뢰·전체 동선 확인 → 이 루트로 갈게요 → 선택 상태 저장`

**Fallback**
- 신뢰 가능한 2개 이상 조합 불가 → 개별 추천 또는 루트 구성 실패 안내
- 가용시간 부족으로 조합 불가 → 실패 이유를 구분해 `시간 조건 수정` 또는 `가능한 개별 경험 보기` 제공
- 장소 제외·조건 변경 → 루트 전체 재판단
- 데이터·AI·네트워크 실패 → 재시도 안내

## 7. 즉시 추천(A)·특정 날짜 문화루트(B) 완료기준

### 즉시 추천(A) — 정상 완료
- 시작점(Start Anchor)과 가용시간이 확보되고 입력조건이 추천에 반영된다.
- Hard Constraint 충돌 후보가 정상 추천으로 표시되지 않는다.
- 결과 상태·추천 이유·핵심 실행조건·미확인 정보가 구분된다.
- 사용자가 LF-03 결과+지도에서 신뢰정보와 이동 부담을 확인하고 `Select experience`로 장소를 선택한 뒤, LF-09에서 별도의 저장·확정 동작을 완료하여 현재 선택을 유지하면 A 정상 완료다. LF-09 저장 전에는 완료로 처리하지 않으며, 저장 후 완료 피드백을 제공한다. LF-06 상세·외부 지도 실행·실제 장소 도착은 완료조건이 아니다. 상세 확인 → 이동 확인 → 선택·저장의 판단 위계를 유지하며 구체 상호작용은 UX/UI가 정한다.

### 즉시 추천(A) — Fallback 완료
- 불가능한 후보로 추천 수를 채우지 않는다.
- 0건 / 추가 확인 필요 / 조건 완화 대안을 실제 상태에 맞게 구분한다.
- 위치 거부·핵심값 모호·처리 실패 시 직접 입력·부분 수정·재시도로 복귀할 수 있다.

### 특정 날짜 문화루트(B) — 정상 완료
- 현행 Flow: LF-04 입력 → LF-05 결과 → LF-08 루트 이동 확인·선택 확정. 필요 시 LF-06 선택적 상세/공식 확인으로 왕복하며, `이 루트로 갈게요 / Go with this route`에서 현재 루트를 확정한다. LF-09 B는 이후 현재 선택으로 재접근하는 상태이며 완료 필수 단계가 아니다.
- 재구성한 새 루트는 명시적 선택 전 기존 확정 선택과 구분한다. 일부 이동 미확인·중간 상태의 미확인 정보는 선택 후에도 유지하며 선택 완료를 이동정보·예약·참여 가능 확인 완료로 표시하지 않는다.
- 날짜·시작점·가용시간 안에서 신뢰 가능한 문화경험 최소 2곳(고정 상한 없음)이 순서 있는 루트로 구성된다.
- 시간·이동·확인된 비용·핵심 조건·미확인 정보를 구분해 이해할 수 있다.
- 조건 수정·장소 제외 후 전체 루트를 다시 판단한다.
- 사용자가 필요한 신뢰 정보와 전체 동선을 확인한 뒤 `이 루트로 갈게요`를 확정하고 현재 선택 상태가 저장되면 정상 완료한다. 상세 확인 → 이동 확인 → 선택의 판단 위계를 유지하며 화면 구성은 UX/UI가 정하고 실제 도보 경로선·구간별 거리·예상시간의 구체 구현 수준은 구현 단계 후속 확인 대상이다.

### 특정 날짜 문화루트(B) — Fallback 완료
- 2개 이상 신뢰 가능한 경험 조합이 성립하지 않으면 완성된 루트처럼 표시하지 않는다.
- 개별 추천 또는 루트 구성 실패로 전환하고 사유·다음 행동을 제공한다.
