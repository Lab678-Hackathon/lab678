# KONNECT AI·Tech Boundary Handoff

> 기준일: 2026-10-01  
> 상태: **Product 기준 확정 / Tech 구현·PoC 확인 대기**  
> 연결: H2 · D-14 · D-15 · D-16 · P-01~P-09  
> 목적: KONNECT의 핵심 AI가 단순 추천문 생성이 아니라 실제 다단계 조회·판단·도구 사용으로 동작하도록 Product 동작 요구와 Tech 검증·구현 경계를 정리한다.

## 1. Product가 정의하는 동작과 신뢰 기준

Product는 필요한 사용자 가치·동작·상태를 정의한다. 아래 요구를 어떤 Rule/Data·Agent·RAG·Memory 조합과 책임배분으로 구현할지는 Tech가 결정한다.

| 필요한 동작 | Product 요구 | 유지할 신뢰 기준 |
|---|---|---|
| 사실·제약 판정 | 운영기간·휴무·가격·시간충돌·필수 조건·숫자 비교·데이터 상태를 확인된 근거로 판단 | 명백한 사실 판정을 LLM 추정으로 대체하지 않음 |
| 근거 확인 | TourAPI와 검증된 정보원에서 현재 추천에 필요한 정보를 검색·참조 | 가격·예약·운영 가능 여부를 임의로 생성하지 않음 |
| 환경 Context 판단 | 기상청·AirKorea의 확인 가능한 환경 상태를 후보 판단에 반영하고 공식 위험 수준에서는 관련 Outdoor 정상 추천을 제한 | 환경정보만으로 행사 취소·휴관을 추정하지 않음 |
| 다단계 판단 | 사용자 조건 구조화 → 필요한 정보·도구 선택 → 확인 결과에 따른 재판단 → 후보/루트 구성 → 이유·불확실성 설명 | 결과에 따른 분기·재탐색과 다음 행동을 실제로 확인 |
| Context 재사용 | 허용된 현재 요청·여행 맥락과 확인된 사용자 선호를 §2의 우선순위·유효범위에서 재사용 | 단일 행동·반복 횟수만으로 장기 선호 자동 확정 금지; 사실·필수 조건 우선 |

### 핵심 원칙

- 확인된 사실·제약을 근거로 판단한다. 특정 기술 계층의 이름이나 고정 호출 순서는 Product 요구가 아니다.
- 미확인은 무료·예약 불필요·이용 가능 등으로 추정해 메우지 않는다. 알려진 필수 조건 충돌이 없고 공식 경로에서 추가 확인 가능하며 후보 가치가 남으면 `추가 확인 필요`로 노출한다. 미확인 때문에 시간 적합성·실행 가능성·자동 루트 구성을 신뢰성 있게 판단할 수 없으면 추천 또는 자동 루트에서 제외한다.
- AI가 추천·구성·설명에 관여함을 고지하고, 공식 확인 사실 / KONNECT 계산·계획·AI 판단 / 미확인을 구분한다. AI 결과가 실제 이용 가능성을 보장한다고 표현하지 않는다.
- Agent 필요성은 단순 설명 생성이 아니라 실제 다단계 동작·도구 사용으로 검증한다. 과제·팀 합의의 기술요소 요구가 있어도 구체 구현 구조는 Tech가 결정한다.
- R-09 추천 이유 기술 경계: 사용자 Context + 후보 Evidence + Product Match Rule로 확인된 Fit만 설명한다. AI는 미확인 데이터로 신규 사실·긍정 적합성·예약/참여 보장을 만들지 않으며 0개 이유도 강제하지 않는다. 값 상태(확인/예상/계획/미확인), Rule 판정, 주 상태·조건 완화와 생성한 Reason 근거는 검증 가능해야 한다. 구체 Rule/Data/Agent/RAG 분담·스키마·trace 방식은 Tech 판단이다.
- R-05/R-10 Reason Copy Dictionary v1.0: `product/reason-copy-dictionary.md`의 17개 **기본 영문 문구 후보**에 대해 출력·억제 규칙·Copy ID·A/B 루트/장소 구분·0개 예외·실제/계산/계획값을 구현 검증 사례로 참고한다. 기존 MVP 요구를 넘어 전부를 동시에 구현·표시해야 한다는 의미가 아니며 구체 템플릿·LLM/Rule 구현은 Tech 판단이다.
- A 현재 요청의 명시적 제외조건(원하지 않는 유형·대상, 과거 방문 장소, 향후 방문 예정 장소)은 Request Context에서 실제 후보 구성에 반영한다. 장기 선호로 자동 승격하지 않고 후보 부족 시에도 임의로 해제하지 않는다. 구체 파싱·필터 구현은 Tech가 결정하되 사용자 의도 결과는 검증 가능해야 한다.
- **10/14 A 예산 초과 Alternative:** 일반 금액 상한(`Under ₩20,000` 등) 초과 후보라도 가격이 확인되고 다른 필수 실행조건에 충돌하지 않으면, 정상 후보 부족 시 **초과액·완화한 조건을 명시한 Alternative로만** 보여줄 수 있다. 예산 충족/Fits/Partially confirmed 판정으로 우회하지 않으며, `Never exceed` 등 명시적 절대 상한·휴무·자격 미충족 같은 불가능 조건은 완화하지 않는다. 최대 3~4개 강제 채움 금지, B 총예산 판정 불변. 구체 판정은 [02](./02-input-recommendation-rules.md).

## 2. 기존 여행계획·로그인·Memory 영향 매트릭스

개인화 맥락은 **현재 요청 맥락 (Request Context) / 여행 맥락 (Trip Context) / 사용자 선호 (User Preference)**로 구분하고, **제품 분석 데이터 (Product Analytics)**는 개인화 Memory와 별도 목적으로 관리한다. 구분 기준은 필드명이 아니라 **정보의 출처와 유효기간**이다. 현재 추천은 **현재 요청 맥락 → 여행 맥락 → 사용자 선호** 순으로 보완 적용하고 충돌 시 현재 요청을 우선한다. 운영시간·회차·가격·예약·환경 등 확인 가능한 사실과 **필수 조건**은 별도로 판단하며 개인화가 덮어쓰지 않는다.

현재 요청 맥락은 해당 추천 흐름을 기본 유효범위로 한다. 같은 여행에 계속 적용할 의도가 확인된 정보만 여행 맥락으로 재사용하며, 현재 여행 범위에서만 적용한다. 새 여행 시작·사용자 초기화 등 여행 범위 종료를 확인할 수 있는 시점부터 자동 적용을 중단한다.

장기 사용자 선호는 사용자가 장기 성향으로 명시했거나 서비스가 추정한 선호를 사용자가 확인한 경우 저장·재사용한다. **단일 요청·클릭·선택·방문·대화를 자동 승격하지 않는다.** 반복 행동은 **선호 후보 신호**이며 반복 횟수만으로 확정하지 않는다. MVP에서는 2회·3회 같은 고정 임계값을 Product 규칙으로 두지 않는다. 확인된 사용자 선호는 사용자가 확인·수정·초기화할 수 있어야 한다.

여행 맥락·사용자 선호의 수정·초기화는 **이후 추천부터 적용**하고 이미 생성된 과거 결과를 소급 변경하지 않는다. 개인화 정보가 없거나 충돌 해소가 어렵다면 임의 추정보다 현재 요청과 확인 가능한 사실을 기준으로 판단한다.

**개인화 데이터 구조는 용택님·민규님이 공동 논의하며 구체화한다.** 민규님은 데이터 의미·경계·재사용 기준 논의를 지원하고 용택님은 저장·조회·대화기록 구현 가능성과 기술 구조를 검토한다. 사용자별 대화기록은 Tech에서 구현 가능하다고 확인했으며 구현 완료나 세부 설계 확정을 뜻하지 않는다.

| 항목 | Product 기준 | UX 영향 | Tech 영향 / 확인사항 |
|---|---|---|---|
| 기존 여행계획 | 즉시 추천(A)·특정 날짜 문화루트(B)의 **선택형 Context** | 제3의 핵심 기능이나 종합 플래너처럼 보이지 않게 | 입력 내용 구조화·저장·재사용 방식 |
| 계획 없는 사용자 | 추가 입력 없이 즉시 추천(A)·특정 날짜 문화루트(B) 사용 가능 | 일정 없음도 정상 경로 | 일정 데이터가 없어도 추천 로직 동작 |
| 다음 고정 일정 | **시간 + 장소** 최소 입력을 기본 경로로 사용 | 처음부터 긴 일정 입력폼을 요구하지 않음 | 시간·장소를 Hard Context로 구조화 |
| 전체 일정 | 필요한 사용자만 확장 입력 | 단계적 정보 공개 | 날짜·시간·장소 우선 추출 |
| AI 구조화 확인 | 추천에 영향을 주는 **모호한 Hard 값만 확인** | 모든 추출값을 재확인시키지 않음 | 모호한 필수 조건과 미확인 데이터 표현 방식 |
| 로그인/사용자 식별 | MVP IN·Google Social Login 방향 / 첫 결과까지 비회원 1회, 두 번째 추천·재추천 요청 시 로그인 유도 / 현재 추천 흐름 연속성 유지 | 첫 진입 로그인 강제 없음; 재입력·재시작 방지 | 계정/세션/Memory 연결·이전·복원 방식은 Tech 판단 |
| 사용자 상태·My Page | MVP IN / 개인화 관리·현재 여행/최근 선택 최소 진입·계정 정보 | 확인된 선호 확인·수정·초기화; 추가 입력 Skip 가능 | 범위 내 저장·조회·관리 구현은 Tech 판단 |
| Context 재사용 | 현재 요청 맥락 → 여행 맥락 → 사용자 선호 순으로 보완 적용 | 수정·초기화는 이후 추천부터 적용 | Memory 구성·저장·조회와 기술요소 증빙 방식 |

### My Page MVP 최소범위 — P-04·P-05 완료

My Page는 **MVP IN**이며 최소범위는 **개인화 관리 / 현재 여행·최근 선택을 다시 찾는 최소 진입점 / 계정 정보**다. 사용자-facing 진입명은 **My Pick**(A 현재 선택) / **My Route**(B 현재 루트)로 구분하고 A/B 내부코드 노출·전체 선택 이력 신규 요구는 하지 않는다. 전체 추천 이력·방문 통계·취향 분석·Stamp/Collection은 MVP 필수범위가 아니며 기록·통계 중심 서비스로 확장하지 않는다.

장기 추천에 실제 사용하는 **확인된 사용자 선호**를 확인·수정·초기화할 수 있어야 하며 이후 추천부터 적용한다. 선호 후보 신호는 사용자 확인 전 장기 선호가 아니고, 별도의 복잡한 추정 선호 관리 UI는 MVP 필수가 아니다. 추가 개인화 입력은 과도한 가입 Form을 강제하지 않고 Skip 가능하게 한다. 선택과 실제 방문은 구분하며 GPS 자동 방문판정은 추가하지 않는다.

로그인·상태관리는 **MVP IN**, 방식은 **Google Social Login 방향**이다. 첫 진입에서 로그인을 강제하지 않으며 **비회원은 첫 추천 결과까지 1회 이용하고, 두 번째 추천 또는 재추천 요청 시 로그인 유도**한다. 비회원 첫 추천 후 로그인해도 **현재 요청 조건·생성된 추천 결과·현재 선택 등 경험 연속성에 필요한 상태를 유지**해 동일 요청 재입력이나 추천 흐름 재시작을 요구하지 않는다. 임시 상태 전체를 여행 맥락·장기 사용자 선호로 자동 간주하지 않는다. 현재 요청의 의미와 진행 상태를 가능한 범위에서 이어간다.

B 첫 생성·검토·선택과 현재 루트 편집·복구·조건 수정 자체는 비회원 이용 범위다. 로그인 유도는 새 후보 조합을 실제 생성하기 직전에 적용하며, 행동별 경계와 취소·재개 기준은 [05 · B 로그인 적용 경계](./05-ux-handoff.md#b-로그인-적용-경계)를 따른다.

로그인 직전 요청과 기존 장기 선호가 충돌해도 기존 선호 자체를 자동 수정·삭제하지 않는다. 연속성 문제가 발생하면 **전체 폼 대신 필요한 필수 조건만 최소 재확인**한다. 임시 저장 대상·위치·유지 방식, session/DB, 로그인 전후 식별·연결, 데이터 이전·복원·병합·충돌·복구 및 저장·조회 방식은 **Tech가 결정**한다. 현재 요청의 관심사·예산·이동조건 반영은 Tech 의미확인 완료다. 정책 안의 화면 구성은 UX/UI가 설계하며 저장·인증·익명화·물리삭제·백업·보관기간 구현은 Tech가 검토한다.

### P-09 — 최초 Google 가입 선호 온보딩

- 최초 가입 선호 설정의 관심사 6개는 초기 기본 선택이 없으며, 사용자가 아무것도 선택하지 않고 Skip하는 것도 허용한다.
- Google Social Login으로 KONNECT 계정이 **최초 생성될 때 1회**, 기본 1화면 수준의 간단한 선호 설정을 제공한다. 기존 회원에게 반복 노출하지 않는다.
- 입력은 문화 관심사 6개(`Traditional Culture / Palaces & Historic Sites / Hands-on Experiences / Art & Exhibitions / Live Performances / Festivals & Events`, 복수 선택 가능)와 **추가 선호 자유입력**이다. 추가 선호에는 걷기 등 장기적으로 활용하고 싶은 개인 선호를 자연어로 적을 수 있다. 모두 미입력·Skip 가능하며 Skip해도 A/B 이용을 제한하지 않는다.
- MVP는 `자유입력 → LLM 해석 → 사용자 확인·수정 → 저장`의 간결한 구조로 한다. 장시간 챗봇 상담·반복 추가질문은 기본 Product 요구가 아니다. 자연어 해석·저장 구조는 Tech, 입력·확인 Interaction·Visual Design은 UX가 설계한다.
- 사용자가 확인한 해석값만 장기 User Preference로 저장한다. 이동 관련 저장 선호는 **Soft ranking signal**이며 숫자형 Hard Constraint가 아니다. 현재 Request의 명시 이동 제한 우선, Request > Trip Context > User Preference 유지. 저장 선호만으로 M01/M02 또는 `Within your walking limit` Reason 생성 금지. 접근성·건강·장애 상태 추론 금지. My Page 확인·변경·해제 가능.
- 현재 요청 예산·동행·이번 여행 일정·현재 가용시간 등 Request/Trip Context 값은 가입 장기 선호로 자동 저장하지 않는다.
- 사용자가 이 화면에서 직접 선택한 값은 확인된 User Preference로 저장 가능하다. **현재 Request > 유효한 Trip Context > User Preference**를 유지하며 가입 선호가 현재 요청의 명시 조건·확인 사실·필수 조건을 덮어쓰지 않는다. 이후 My Page에서 조회·수정·초기화 가능하다.
- 비회원 첫 추천 결과 1회 → 두 번째 추천/재추천 Login Gate는 유지한다. Gate에서 최초 가입하면 선호 설정 또는 Skip 후 중단했던 추천 흐름을 이어가며 기존 요청조건·결과·현재 선택을 잃지 않는다. LF-01 자발적 최초 가입도 원래 진입 맥락을 불필요하게 끊지 않는다. P-01~P-08은 유지한다.
- 최종 Interaction·Visual Design은 UX, OAuth·신규회원 판별·1회 노출 관리·저장/복원 HOW는 Tech 판단이다. 별도 전역 LF/MP 번호는 만들지 않는다.

## 3. PoC에서 확인할 사용자 동작 예시

다음은 검증할 동작의 예시이며 특정 workflow나 모듈 호출 순서를 지정하지 않는다.

### 즉시 추천(A)

시작 위치·시작 시각·종료 시각은 구조화된 필수 입력으로 확보하고 선택조건은 하나의 자연어 영역에서 보완하는 방향이다. 실제 기상정보는 API 환경 Context, 실내/비/야외 관련 선호는 사용자 입력으로 구분한다.

사용자 조건/기존 일정 해석  
→ 필요한 문화경험 데이터 조회  
→ 운영·가격·시간 등 사실·제약 판정 결과 확인  
→ 미확인·추가 확인 필요 분리  
→ 현재 조건에 맞는 후보 구성  
→ 추천 이유·확인된 조건·불확실성 설명  
→ 공식 확인 경로·외부 지도 등 다음 행동 제시

### 특정 날짜 문화루트(B)

B-01~B-02는 안내·입력 예시가 있는 자연어 대화 중심으로 날짜·출발 위치·시작 시각·종료 경계를 확보하는 Product 기준으로 확정했다. 이미 제공한 값은 반복 질문하지 않고 누락·모호한 필수값만 확인하며 직접 수정한 조건을 실제 요청에 반영해야 한다. LF-04의 Product 화면 위계는 Conversation-first: 자연어 요청(강제 없음) → 구조화 → 부족·모호한 필수값만 질문 → compact editable summary → 필요한 값 직접 수정 → 필수 4값 확인 후 `Show culture route`다. 직접 수정·Starting point Quick Select는 보조 경로이며 Form-first·지역 추천 모드·2km Hard Filter로 만들지 않는다. 별도 전체 입력 화면 전환·AI 동적 UI 생성은 필수가 아니며 구체 Interaction·Visual Design은 UX, 구조화·workflow·저장 HOW는 Tech가 결정한다. 완전히 빈 자유입력이나 새 Agent 영문 명칭을 공식 기준으로 고정하지 않는다. 별도 FAQ·여행정보 Bot을 핵심기능으로 분리하기보다 현재 자연어 대화 흐름에서 FAQ·여행정보·자연어 추천을 함께 처리하는 방향이며 과제 기술요소 요구와 실제 증빙 기준은 유지한다.

날짜·시작점(Start Anchor)·가용시간(Time Boundary) 구조화  
→ 후보 데이터 조회  
→ 운영·시간·이동 상태 확인  
→ 최소 2곳 이상 조합 시도(장소 수 고정 상한 없음)  
→ 충돌/불가 시 다른 후보·조합 재판단  
→ 신뢰 가능한 조합이 성립하면 루트 생성  
→ 성립하지 않으면 개별 추천 또는 루트 구성 실패 안내

## 4. PoC에서 확인할 내용

아래 항목은 **② PoC에서 검증할 내용**이다. Product는 확인할 동작·품질·검증 목적을 정하고 실제 증빙 방식은 Tech가 선택한다.

| 확인할 내용 | 실제로 확인되어야 할 것 |
|---|---|
| 다단계 Agent | 다음 조회·도구 사용을 선택하고 여러 단계를 연결하는 동작 |
| 데이터 조회 | 현재 조건에 필요한 정보를 조회하는 동작 |
| 판정 결과 반영 | 확인된 사실·제약 결과에 따라 다음 행동이 달라짐 |
| 미확인 처리 | 정보 부족을 추정으로 메우지 않고 상태를 구분 |
| 후보/루트 재판단 | 조건 불충족 시 다른 후보·조합을 검토하거나 대안 흐름으로 전환 |
| Context 재사용 | 허용된 범위의 확인된 Context를 다시 불러옴 |
| 근거 기반 설명 | 추천 이유·불확실성이 확인한 정보와 연결됨 |
| 실행 증빙 | 위 동작이 문서상 가능성이 아니라 실제 실행으로 확인됨 |

핵심 AI를 Agent로 설명하려면 ① 다음 조회·도구 사용 선택 ② 조회·판정 결과에 따른 분기 ③ 최종 추천 또는 루트/대안 흐름까지의 다단계 연결을 확인한다. 어떤 log·trace·metadata·캡처로 이를 보일지는 Tech가 결정한다.

현재 Product 결정을 막는 기술적 사실·제약이 발견되면 **① 지금 Product 결정을 위해 필요한 확인**으로 구분해 질문한다. workflow·schema·cache·framework·orchestration·prompt·저장·trace 구성은 **③ 실제 개발 중 Tech가 결정할 구현 세부**이며 초기 Product 기획에서 확정을 요구하지 않는다.

## 5. 역할 경계

### Product 확정

- 사용자 입력·필수/선택과 기존 여행계획·로그인의 제품 역할
- 필요한 다단계 AI 동작과 사용자 가치
- 미확인·대안 흐름·신뢰 및 Context 재사용 원칙
- 즉시 추천(A)·특정 날짜 문화루트(B) 완료기준과 PoC에서 실제 확인할 동작·검증 목적

### UX/UI 후속

- 첫 추천 결과까지 비회원 1회 체험·두 번째 추천/재추천 요청 시 로그인 유도와 추천 흐름 연속성 정책 안의 Interaction; 연속성 문제 시 필요한 필수 조건만 최소 재확인
- 전체 일정 확장 입력 방식
- 구조화 결과의 확인·수정 Interaction
- 추가 확인 필요 상태의 화면 표현

### Tech 판단·실행

- 아키텍처·데이터 구조·API 호출·알고리즘
- Agent/RAG/Memory 구성과 책임배분·workflow·도구 호출 구조
- 저장·조회·인증과 반복 탐색·루트 재계산 구현
- framework·orchestration·prompt와 성능 최적화
- log·trace·metadata·캡처 등 실제 증빙 방식 및 구현 공수·순서

사용자 입력/출력, 상태·대안 흐름·신뢰 기준, MVP 범위·완료기준을 바꿔야 할 때 Product와 재조율한다. Tech는 가능한 해결책을 먼저 검토한다. 요구를 유지하는 구현 방식은 Tech가 판단한다. 팀은 A 우선 고도화 → B 후속 구현으로 모두 진행하기로 확정했고, B 실제 난도가 예상보다 높으면 팀에 공유한 뒤 범위를 유연하게 조정할 수 있다. B 제외나 완료기준 축소를 자동 승인한 것은 아니다.

### 이번 Product Delta의 확인 결과·후속
- **10/13 최신 Product 결정:** B는 2~3개 고정 상한을 폐지하고 최소 2곳·루트 1개·실행 가능성 우선·강제 채움 금지로 변경했다. 시간 처리 순서는 공식 확인값 → 자율형 사용자 계획값 → **Product 채택 유형별 계획 체류시간 범위** → 미확인이며, 장소별 40분 일괄은 임시 구현이다. 유형별 범위는 10/13 회의 후 Product 채택 완료([04 §5](./04-route-time-rules.md#5-고정형--자율형)); 실측·대표 사례 근거, 범위 내 세부 산정 및 Tech 실제 적용 여부는 후속 확인한다. A는 다음 일정 이동시간·복수 일정 충돌을 자동 산정하지 않고 사용자가 종료시각에 이동 여유를 반영하도록 안내한다. 사용자-facing 명칭은 My Pick / My Route다. 중간 상태 문구 `Partially confirmed`는 선호안이며 UX·팀 최종 카피 확인이 남아 있다.


- A 필수 3조건 구조화·선택조건 자연어 보완은 기존 기준을 유지한다. B는 B-01~B-04의 입력·추가 확인·루트 구성·재구성 기준이 확정됐으며 [02](./02-input-recommendation-rules.md)·[04](./04-route-time-rules.md)를 따른다. LF-04의 Conversation-first 위계와 P-09 걷기 단일 선택·Soft 경계는 Product Figma EN/KR에 반영했다. 구체 Agent 구성·workflow·저장·지도 기술 스택은 Tech, 최종 입력 Interaction·Visual Design은 UX 판단이다.
- B 미검증 구현은 [10/4 Tech 확인 요청](../research/tech-validation/tech-validation-questions_1004_01.md)의 B-T01~B-T06으로 관리한다. 기본 시간 처리·실패 Fallback 구현 가능성 및 A 우선→B 후속 구현 방향은 확인 완료다. 계획 체류시간 근거·산정, 실제 데이터 시간충돌·다구간 이동, 조건 수정·재구성 복구·상한 없이 최소 2곳 이상 구성한 루트의 실행 가능성 검증은 후속이며 구체 알고리즘·저장·증빙 방식은 Tech가 판단한다.

- 지도·경로의 즉시 추천(A) 우선 구현 → 특정 날짜 문화루트(B) 후속 구현 순서는 Tech와 확인 완료다. 특정 날짜 문화루트(B) Product 요구사항은 유지하며, 실제 도보 경로선·구간별 거리·예상시간의 구체 구현 수준만 구현 단계에서 후속 확인한다. 어렵다면 경로선 / 번호 핀+순서 / 신뢰 가능한 시간·거리 / 외부 지도 연결 중 가능한 범위를 구분한다.
- LF-10 최소 피드백은 Tech 구현 가능 확인 완료다. 동일한 기술 가능성·부담 여부를 다시 확인하지 않으며 Product 최종 MVP 포함 여부만 일정·우선순위 기준으로 대기한다. Product는 필요한 동작을 정하고 라이브러리·API·저장 방식은 Tech가 판단한다.
- 기상청·AirKorea 환경 Context를 실제 후보 판단에 연결하고, 공식 위험 특보·경보 수준에서는 관련 Outdoor 정상 추천 제외·실내 대안 우선 분기가 동작하도록 구현한다. 공식 위험 단계의 구체 매핑과 API 처리 방식은 Tech가 정하되 환경정보만으로 행사 취소를 판정하지 않는다.
