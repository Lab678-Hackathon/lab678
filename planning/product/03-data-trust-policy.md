# KONNECT Data & Trust Policy

> 역할: 데이터 소스, 가격·예약·참여조건, 환경 Context, 공식 확인 경로와 데이터 품질 리스크의 Product 기준  
> 연결 결정: D-09, D-11, D-10  
> 조사 근거: [W2 추가 데이터 Product 직접검토·Tech 확인 요청](../research/KONNECT_W2_추가데이터_Product직접검토_Tech확인요청_2026-09-23.md)

## 1. 가격·예약·참여조건 — D-09

### 가격
- 확인된 가격·무료 여부만 예산 판단에 사용한다.
- 빈값, `Varies`, 모호한 자유기술 값은 `가격 추가 확인 필요`로 처리한다.
- 일부 비용만 확인된 경우 전체 비용이 예산 내라고 단정하지 않는다.
- B 문화루트에 필수 비용 미확인 경험이 포함되면 확인된 비용 합계만으로 루트 전체를 `예산 충족`으로 판정하지 않고 `총비용 추가 확인 필요`를 함께 표시한다.
- 복수 좌석가격은 확인된 일반 판매가격 범위로 표시하고 원본 가격 문자열을 보존한다. 가장 낮은 숫자 하나를 행사 대표가격으로 쓰지 않으며 잔여좌석·현재 구매 가능성도 보장하지 않는다.
- 학생·지역주민·예술인·재관람·얼리버드·기간 한정 등 적용 여부가 확인되지 않은 할인가는 일반 최소가격이나 예산 충족 근거로 쓰지 않는다.
- 유료임이 확인됐지만 금액을 알 수 없으면 `유료 · 금액 미확인`과 `가격 확인 필요`로 표시한다. 무료·예산 충족·예산 초과·이용 불가로 추정하거나 자동 제외하지 않고 공식 확인 경로를 제공한다. `일부 체험 유료` 등은 `부분 유료 · 세부 금액 확인 필요`로 구분한다.
- 공식 가격은 KRW가 기준이다. 선호통화 예산 입력은 기준환율로 KRW 환산해 확인된 일반가격과 비교한다. 결과는 공식 KRW 가격을 우선 표시하고 환산값은 참고값으로 병기하되 실제 결제금액을 보장하지 않는다. 금액 미확인 시 환산가격을 임의 생성하지 않는다.

### 예약·참여
확인된 아래 상태만 사실로 표시한다.
- 사전예약 필요
- 예약 불필요
- 현장 참여 가능

API에 정보가 없다는 이유로 `예약 불필요` 또는 `현장 참여 가능`으로 처리하지 않는다.

### 이용 가능성 상태 분리
아래는 서로 다른 상태다.
- 사전예약 필요
- 지금 예약 가능
- 잔여좌석 있음
- 실제 입장·참여 가능

KONNECT는 실시간 잔여좌석이나 실제 입장·참여 가능성을 보장하지 않는다.

### 공식 확인 경로
- 확보한 공식 상세·예약 경로가 있으면 제공한다.
- 확보하지 못한 경우 그 사실을 숨기지 않는다.
- 정보 부족을 곧바로 `이용 불가`로 단정하지 않는다. `추가 확인 필요` 노출 또는 추천·자동 루트 제외는 [02의 미확인 노출·제외 기준](./02-input-recommendation-rules.md)을 따른다.

## 2. MVP 데이터 소스 전략 — D-11

### 기본 구조
1. **TourAPI** — 기본 데이터 소스
2. **서울문화포털 문화행사 API** — 행사·문화정보 보완
3. **KOPIS** — 공연 시간·가격·러닝타임·예매경로 등 보완
4. **기상청** — 날씨 Context
5. **AirKorea** — 대기질 Context

### 9/23 Tech 확인 상태
- 서울문화포털 문화행사 API: 접근·사용 가능성 확인
- KOPIS: 접근·사용 가능성 확인
- 기상청: 접근·사용 가능성 확인
- AirKorea: 접근·사용 가능성 확인

**접근 가능 ≠ 추천 판단에 필요한 모든 필드가 안정적으로 확보됨**을 의미한다.

실제 필드 채움률·중복 매칭·세부 파싱 품질은 구현 과정에서 계속 확인한다.

## 3. 지역기관 웹·팝업 처리

### 자동수집 제약
- 종로문화플랫폼: Tech 확인상 크롤링 차단
- 종로구청: Tech 확인상 크롤링 차단
- 종로문화재단: 렌더링 구조상 자동수집 난이도 높음
- 중구문화재단: 렌더링 구조상 자동수집 난이도 높음
- 중구청 문화정보: Product 직접검토상 공식 페이지가 분산되어 MVP ingestion 우선순위가 낮음

따라서 지역기관 웹은 4주 MVP의 **자동 수집·데이터 보완 소스에서 제외**한다. Product 조사 과정에서 참고할 수는 있으나, 서비스의 별도 수집 파이프라인이나 누락정보 보완 소스로 사용하지 않는다.

다만 TourAPI·서울문화포털 문화행사 API·KOPIS 등 **핵심 소스에서 공식 URL이 확보된 경우**, 해당 공식 페이지를 사용자의 최종 확인 경로로 연결할 수 있다. 이는 지역기관 웹을 별도 데이터 소스로 수집한다는 의미가 아니다.

### 팝업
현재 안정적인 공개 API나 수집 경로를 확보하지 못했으므로 **4주 MVP 추천 후보에서 제외**한다. 구조화된 데이터 확보가 가능해질 때 후속 재검토한다.

## 4. 데이터 품질 리스크

현재 MVP에서는 다음 리스크를 전제로 한다.

- 공식 소스 간 가격·시간·상세정보 충돌 가능성
- 동일·유사 콘텐츠의 중복
- 부모 행사 페이지와 개별 프로그램 정보 차이
- 자유기술 필드의 파싱 난이도
- 원본 갱신시점과 API 조회시점의 차이
- 언어별 정보량·필드 차이
- API 접근 가능 여부와 실제 필드 채움률의 차이

### 처리 원칙
- 서로 다른 소스가 충돌하면 임의로 합성해 사실로 확정하지 않는다.
- 사용자 선택에 중요한 정보가 불명확하면 [02의 미확인 노출·제외 기준](./02-input-recommendation-rules.md)에 따라 처리한다. 시간 적합성·실행 가능성 또는 자동 루트 구성을 신뢰성 있게 판단할 수 없으면 추천 또는 자동 루트에서 제외한다.
- 공식 상세 경로가 있으면 최종 확인 수단으로 연결한다.
- 공식·원천 데이터에서 신뢰 가능한 대표 이미지가 확보된 경우 추천 카드·상세의 보조 의사결정 정보로 사용할 수 있다. 이미지가 없다는 이유만으로 후보를 제외하지 않는다.
- 대표 이미지가 없을 때 다른 장소 이미지나 AI 생성 이미지를 실제 장소·행사 이미지처럼 임의 대체하지 않는다. 영상은 4주 MVP 필수 정보로 두지 않는다.
- 실제 중복 매칭·충돌 해소 로직은 Tech 구현 검증을 거쳐 구체화한다.

## 5. 날씨·대기질 Context

기상청과 AirKorea는 별도 날씨 기능이 아니라 **추천 Context**다.

### 기상청
- 강수·눈
- 기온 등 날씨 조건

### AirKorea
- PM 등 대기질

### 적용 원칙
- 일반적인 환경 상태에서는 실내 경험에 불필요한 불이익을 주지 않고, 야외 경험도 정상 후보로 판단할 수 있다.
- 비·더위·추위·대기질 등으로 야외 활동 부담이 커지면 주의정보를 표시하고 Outdoor 우선순위를 낮추며 적절한 실내 대안을 우선할 수 있다.
- 기상청·AirKorea 등 공식 위험 특보·경보가 적용되어 안전상 정상 추천이 부적절한 경우 관련 Outdoor 경험은 정상 추천에서 제외하고 실내 대안을 우선한다.
- 환경 위험에 따른 추천 제외와 행사 자체의 취소·휴관 판정은 분리한다. 날씨·대기질만으로 행사 취소·휴관·참여 불가를 추정하지 않으며, 공식 취소·운영변경은 공식 소스 확인이 있을 때만 반영한다.
- 미래 예보를 확보할 수 없는 경우 임의 추정하지 않고 미확인으로 둔다.
- Product는 임의의 강수량·기온·PM 수치를 Hard 임계값으로 고정하지 않으며, 공식 위험 단계의 구체 매핑은 Tech 구현에서 확인한다.

## 6. 기본 서비스 성립 원칙

추가 검색·크롤링이 실패해도:

> `TourAPI + 구조화된 공식 API`

만으로 기본 추천이 성립해야 한다.

부족한 실행조건은 [02의 미확인 노출·제외 기준](./02-input-recommendation-rules.md)을 따른다. 추가 확인 후보로 노출할 수 있는 경우 공식 확인 경로를 제공하며, 시간 적합성·실행 가능성 또는 자동 루트 구성을 신뢰성 있게 판단할 수 없으면 추천 또는 자동 루트에서 제외한다.

## 7. 무료 필터 연결 — D-10

가격 미확인 정보를 무료로 간주하지 않는다.

무료 선택 시:
- 무료 확인 → 정상 결과
- 유료 확인 → 필요 시 조건 완화 대안
- 가격 미확인·일부 비용만 확인 → 가격 추가 확인 필요

세부 판정 규칙은 [02-input-recommendation-rules.md](./02-input-recommendation-rules.md)에서 관리한다.

## 8. 추천 설명·경험 데이터·유료 노출

- 추천 이유는 확인된 원천 정보, 명시적 입력, 설명 가능한 계산 결과에 근거한다. 구체 축·표시 개수는 [02](./02-input-recommendation-rules.md)에서 관리한다.
- Social Proof는 **향후 보조 근거**이며 현재 MVP의 핵심 추천 근거가 아니다. `이 장소로 갈게요` 선택 수와 실제 방문 확인 수를 분리하고, 기간·행동을 정확히 표시한다. 데이터가 부족하면 숨기며 최소 표본 임계값은 아직 정하지 않았다.
- 발표·Figma의 가상 수치는 필요 시 `데이터 축적 후 예시`로 표시하고 실제 운영 데이터처럼 표현하지 않는다.
- BM Hypothesis v0의 제휴·광고는 기본 추천 판정·순위를 바꾸지 않는다. 실행조건에 맞지 않는 장소를 광고비 때문에 추천하지 않으며 유료 노출은 일반 추천과 분리해 `Sponsored / 제휴` 등으로 식별한다. 홈 배너는 향후 확장이다.
