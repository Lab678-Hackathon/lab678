# KONNECT 협업·업무 운영 가이드 — 2026-10-05 이후

## 1. 목적

KONNECT가 기획 중심 단계에서 UX/UI 구체화와 구현 단계로 이동함에 따라, 팀원 간 확인 대기와 중복 작업을 줄이고 각 역할이 병렬적으로 작업할 수 있도록 협업 방식을 정리합니다.

이 문서는 특정 역할의 업무를 줄이기 위한 규칙이 아니라, **Product · UX/UI · Tech/Data 각 영역의 책임과 인계 기준을 명확히 하여 팀 전체의 작업 속도와 정합성을 높이는 것**을 목적으로 합니다.

현재는 **즉시 추천(A), 특정 날짜 문화루트(B), 로그인·개인화(P), 추천 이유(R)까지 주요 Product 기준이 대부분 확정된 상태**입니다. 앞으로는 이미 확정된 기준을 반복해서 다시 검토하기보다, 각 담당자가 자신의 영역에서 1차 완성도와 검증까지 책임하고 역할 간 판단이 필요한 지점만 빠르게 공유합니다.

---

## 2. 핵심 운영 원칙

1. **병렬 작업 확대** — 다른 담당자의 전체 검토를 기다리지 않고, 확정된 기준 안에서는 각 역할이 자율적으로 진행합니다.
2. **역할별 1차 자체 점검** — 각 담당자는 자신의 산출물에 대해 1차 자체 점검까지 수행한 뒤 공유합니다.
3. **변경사항 중심 검토** — 전체 산출물을 반복해서 다시 검토하지 않고, 변경된 부분과 그 변경으로 직접 영향받는 부분을 중심으로 확인합니다.
4. **확정 기준 재논의 최소화** — 이미 합의된 Product 기준은 새 근거, 기술 제약, 멘토 피드백, 사용자검증 결과가 있을 때만 다시 엽니다.
5. **역할 간 의사결정에 집중** — 팀 논의는 Product 의미, UX 영향, 기술 제약이 교차하는 쟁점에 집중합니다.
6. **1회 검증 원칙** — 변경 반영 후 필요한 범위를 한 번 검증하고, 특별한 문제가 없으면 해당 작업을 닫습니다.

## 3. 역할별 책임

| 역할 | 주 책임 | 기본 완료 기준 |
|---|---|---|
| **기획** | 사용자 의미, 조건, 상태, 정책, 결과 기준, 완료 기준, 우선순위와 MVP 범위 | 새 결정 또는 기존 기준 변경이 필요한 쟁점 판단 |
| **UX/UI** | 화면 표현, 정보 위계, 상호작용, 시각적 구성, 권한 범위 내 문구 조정 | 확정 기획 기준에 대한 1차 자체 점검 후 시안 완성 |
| **개발·데이터** | 인증·저장·데이터·지도·API·구조·구현 방식, 기술적 제약 | 구현 가능성·제약·대안까지 검토하고 기획 영향 여부 정리 |
| **팀장** | 팀 일정·의존성·블로커·우선순위 조율, 필요한 논의 연결, 진행상태 확인 | 담당자가 불명확한 일이나 작업 간 충돌이 방치되지 않고 다음 행동이 명확한 상태 |

각 담당자는 먼저 자기 영역을 점검하고, 자신의 전문 영역 안에서 가능한 범위까지 스스로 결정하고 완성합니다.

**팀장 역할은 각 전문 영역의 결정을 대신하는 역할이 아닙니다.** 기획 판단은 기획, UX/UI 판단은 UX/UI, 구현 방식은 개발·데이터 담당자가 맡습니다. 팀장은 여러 역할 사이의 의존성·일정·블로커를 조율하고, 필요한 의사결정이 적절한 담당자에게 연결되도록 합니다.

현재처럼 한 사람이 팀장과 개발·데이터 역할을 함께 수행할 수 있지만, 두 역할의 책임 범위는 구분합니다.

## 4. 변경 분류와 기본 작업 흐름

변경이 발생하면 먼저 아래 네 종류 중 하나로 분류합니다.

| 변경 종류 | 구분 기준 |
|---|---|
| **기획 기준 변경** | 사용자에게 보이는 조건·상태·결과·정책·완료 기준이 바뀌는 경우 |
| **UX/UI 표현 변경** | 기획 의미는 그대로이고 화면 구성·문구 표현·상호작용만 바뀌는 경우 |
| **개발 구현 변경** | 사용자에게 보이는 기획 의미를 바꾸지 않는 구현 방식·구조·기술 선택 |
| **검증 근거 변경** | 사용자검증·개발 가능성 확인·데이터 검증 등의 결과가 추가되거나 상태가 변경되는 경우 |

모든 변경은 다음 순서로 처리합니다.

① 변경 종류 확인 → ② 해당 영역의 기준본 먼저 수정 → ③ 직접 영향받는 자료만 확인 → ④ 해당 담당자가 자기 영역 1차 점검 → ⑤ 기획 의미가 바뀌거나 충돌할 때만 기획 담당 확인 → ⑥ 필요한 변경사항만 반영 → ⑦ 1회 검증 후 종료

어느 담당 영역인지 판단할 수 없는 경우도 §5에 따라 기획 담당에게 확인합니다. 변경 하나 때문에 모든 Docs / Sheet / GitHub / Figma를 자동으로 수정하지 않습니다.

### UX/UI 예시

UX/UI 기준본 수정 → 직접 영향받는 화면·자료 확인 및 자체 점검 → §5에 해당하는 쟁점만 기획 담당 확인 → 필요한 변경사항 반영 → 1회 검증

### 개발·데이터 예시

구현·데이터 기준본 수정 및 가능 / 조건부 가능 / 부담 큼 / 보류와 근거 정리 → 직접 영향 범위 자체 점검 → §5에 해당하는 쟁점만 기획 담당 확인 → 필요한 변경사항 반영 → 1회 검증

## 5. 기획 확인이 필요한 경우

기획 담당에게 다시 확인해야 하는 경우는 다음으로 제한합니다.

- 기존 확정 기획과 충돌하는 경우
- 사용자 결과나 행동이 달라지는 경우
- MVP 범위 또는 완료 기준이 달라지는 경우
- 어느 담당 영역인지 판단할 수 없는 경우

단순 표현 변경이나 구현 방식 차이는 기획 담당의 재승인을 기본 요구사항으로 두지 않습니다. 기존 기획 의미를 보존하는 아래 사항은 각 담당자의 재량으로 진행합니다.

- 화면 배치와 시각 디자인
- 일반적인 상호작용 세부
- 구현 방식
- 기획 고정 문구를 제외한, 의미를 유지하는 범위의 UX 문구 조정
- 코드·데이터 구조 선택

## 6. UX/UI 공유 방식

UX/UI 산출물은 가능하면 아래 정보를 함께 공유합니다.

- **작업 범위**: 이번에 수정/추가한 화면 또는 상태
- **1차 자체 점검**: Product 기준 확인 여부
- **Product 확인 필요**: 판단이 필요한 쟁점 1~N개
- **UX/UI 재량**: 나머지 배치·상호작용·시각 디자인은 UX/UI 기준으로 진행

현재 디자인 검토는 최신 페이지를 기준으로 진행하며, 이전 버전은 별도 검토 대상에서 제외합니다.

---

## 7. Tech/Data 공유 방식

Tech/Data 검토는 가능한 한 아래 구조로 정리합니다.

- **항목**: 검토 대상
- **판정**: 가능 / 조건부 가능 / 부담 큼 / 보류
- **근거**: 데이터, API, 구현 구조, 일정 등의 이유
- **대안**: 필요 시 가능한 대체안
- **Product 영향**: 사용자 경험 또는 MVP 범위가 바뀌는지 여부

**구현 방식은 Tech/Data가 결정하고, 그 결과로 사용자에게 제공되는 경험·기능 범위·Product 목적이 달라지는 경우에만 Product 판단으로 연결합니다.**

## 8. 문서·Figma 운영

| 자료 | 역할 |
|---|---|
| Google Docs `KONNECT 제품 기획 기준서` | 기획 정책 기준 |
| Google Sheet `KONNECT 제품 기획 실행·의사결정 기록` | 진행 상태·결정 추적 |
| GitHub `planning` | 팀 인계·버전 관리·개발/UX 참고 |
| 기획 Figma | 화면 의미·상태·대체 처리·기획 와이어프레임 |
| UX/UI Figma | 실제 UX/UI 설계 기준 |

각 영역의 기준본을 먼저 수정하고, 직접 영향받는 자료에 필요한 변경사항만 반영합니다.

- 의미 있는 기획 변경사항의 관련 자료 반영은 묶어서 진행할 수 있으나, 해당 영역 기준본의 수정을 미루는 뜻은 아닙니다.
- 단순 시각 디자인·상호작용 변경은 기획 문서까지 복제하지 않습니다.
- 변경 영향이 없는 문서까지 억지로 수정하지 않습니다.
- 변경 후에는 변경 범위와 직접 영향 범위만 1회 검증합니다.

### 작업 종료 시 최소 기록

모든 변경 작업을 마칠 때 다음 세 가지만 남깁니다. §6·§7의 공유 형식은 담당 영역에 필요한 설명에 사용합니다.

1. 수정한 대상
2. 확인했지만 영향 없어 수정하지 않은 대상
3. 1회 검증 결과

### 현재 자료와 과거 자료 구분

필요에 따라 자료가 다음 세 상태로 구분되도록 합니다.

| 상태 | 사용 의미 |
|---|---|
| **현재 기준** | 실제 작업·구현·인계에 사용 |
| **참고** | 현재 기준은 아니지만 판단 근거로 사용 가능 |
| **변경 이력** | 당시 결정·작업 기록 보존용 |

과거 자료를 현재 기준에 맞춰 계속 다시 작성하지 않습니다. 과거 자료가 현재 기준처럼 오해될 가능성이 있을 때만 참고·구버전·변경 이력 등을 명확히 표시합니다.

### 전체 정합성 점검 사용 조건

전체 자료를 대상으로 하는 전수 점검은 상시 업무로 하지 않습니다. 다음 단계 전환 시점에만 제한적으로 실시합니다.

- 주요 기획 확정 직후
- UX/UI → 개발 본격 인계 전
- 구현 완료 후 사용자검증 전
- 최종 발표·제출 전

일반적인 수정에서는 영향받는 영역만 확인합니다.

## 9. AI/LLM 활용 원칙

각자 사용하는 AI/LLM에도 동일한 운영 기준을 적용합니다.

- 이미 확정된 Product 기준은 다시 기획하지 않습니다.
- 작업 전 필요한 기준만 최소 범위로 읽습니다.
- 각 역할의 산출물을 먼저 해당 역할 관점에서 1차 자체 점검합니다.
- 다른 역할의 판단이 필요한 쟁점만 별도로 분리합니다.
- 전체 정합성 점검은 §8의 단계 전환 시점에만 제한적으로 실시하며, 일반 수정은 영향받는 영역만 확인합니다.
- 변경된 범위와 직접 영향 범위만 검증합니다.
- 새 근거가 없는 한 기존 확정 기준을 유지합니다.

### AI/LLM용 초압축 요약

1. KONNECT는 현재 A 즉시 추천, B 특정 날짜 문화루트, P 로그인·개인화, R 추천 이유까지 주요 Product 기준이 대부분 확정된 상태입니다.
2. 각 담당자는 자기 영역의 1차 완성도와 자체 점검까지 책임합니다.
3. UX/UI는 자기 영역을 먼저 점검하고, §5의 기획 확인 조건에 해당하는 경우만 기획 담당에게 확인합니다.
4. 개발·데이터는 구현 가능성·제약·대안을 먼저 정리하고, §5의 기획 확인 조건에 해당하는 경우만 기획 담당에게 확인합니다.
5. Product는 새 결정 또는 기존 기준 변경이 필요한 경우에 집중합니다.
6. 팀장은 일정·의존성·블로커를 조율하고 필요한 판단을 적절한 담당자에게 연결합니다.
7. 이미 확정된 기준은 새 근거 없이 다시 열지 않습니다.
8. 전체 재검토보다 변경사항과 직접 영향 범위만 확인합니다.
9. 변경 반영 후 1회 검증하고 작업을 닫습니다.

## 10. 현재 단계의 팀 공통 방향

지금부터는 새로운 Product 범위를 계속 확장하기보다, **확정된 기준을 UX/UI와 Tech 구현으로 옮기고 실제 동작을 검증하는 단계**에 집중합니다.

- UX/UI: 최신 A/B/공통 화면 구체화 및 1차 자체 점검
- Tech/Data: 구현·PoC·기술 검증 본격 진행
- Product: 역할 간 충돌·범위 변경·새 의사결정이 필요한 부분 중심으로 판단
- 팀장: 일정·의존성·블로커를 확인하고 역할 간 필요한 협의를 연결
- 팀 공통: 실제 빌드 이후 통합 QA와 사용자검증으로 연결

## 11. 한 문장 원칙

> **각 담당자가 자기 영역을 완성하고 1차 검증한 뒤, 역할 간 판단이 필요한 부분만 함께 결정한다.**
