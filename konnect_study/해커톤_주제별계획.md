## 방향 A. 멀티컨텍스트 공공 AI 추천 (최우선 권장)

### 핵심 메시지
> "지금 이 순간의 날씨·교통·혼잡도·대기질·사용자 조건, 다섯 가지 공공 데이터를 AI가 동시에 읽어 실제로 지금 갈 수 있는 문화경험만 골라드립니다."

### KONNECT와의 연결
현재 KONNECT는 이미 날씨(KMA) + 대기질(AirKorea) + 위치 + 시간 + 사용자 조건을 멀티컨텍스트로 처리하고 있습니다. 여기에 **서울시 실시간 공공 API 2~3개를 추가**하면 주제 완성도가 크게 올라갑니다.

### 추가할 공공 데이터

| 데이터 | API | 활용 방식 |
|---|---|---|
| 지하철 혼잡도 | 서울 열린데이터광장 | 혼잡 노선 → 도보 경로 우선 추천 |
| 따릉이 잔여 대수 | 공공자전거 실시간 API | 자전거 이용 가능 시 이동 옵션 추가 |
| 무장애 관광지 여부 | 한국관광공사 무장애 API | 동반자 조건에 따른 필터 |
| 공공 와이파이 | 과기부 공공 와이파이 API | 외국인 로밍 부담 구간 안내 |

### 구현 계획 (3인, 2박 3일)

```
Day 1 — 설계 (8h)
  AI/Backend A   서울 열린데이터광장 가입 + API 키 발급
                 sources/subway_congestion.py 구조 설계
                 domain/environment.py 확장 포인트 파악

  Backend B      models/recommend.py에 context_badges 필드 추가
                 DB 스키마 변경 없음 (기존 Supabase 그대로)
                 api/recommend.py 스텁 확장

  Frontend/PM    컨텍스트 배지 UI 설계 (날씨·교통·혼잡도 아이콘)
                 데모 시나리오 3개 초안 작성
                 새 브랜치: git checkout -b hackathon/multi-context

Day 2 — 구현 (12h)
  AI/Backend A   sources/subway_congestion.py 구현 (httpx + tenacity)
                 sources/bike_station.py 구현
                 domain/environment.py — 혼잡도 컨텍스트 판정 추가
                 agent/environment.py — 병렬 조회에 신규 소스 추가
                 pytest 추가

  Backend B      agent/orchestrator.py — 신규 컨텍스트 주입
                 models/environment.py — 컨텍스트 필드 확장
                 api/ 라우터 최종 연결
                 Render 배포 갱신

  Frontend/PM    컨텍스트 배지 컴포넌트 구현 (CSS 토큰 재사용)
                 결과 카드 상단 "현재 조건" 요약 섹션 추가
                 실 브라우저 QA

Day 3 — 통합·데모 (6h)
  전원           end-to-end 테스트 (실 공공 API 응답 확인)
                 데모 시나리오 리허설 3회
                 발표 자료 5분 구성
```

### 데모 시나리오
1. **일반 상황**: 맑음·지하철 보통·따릉이 있음 → 이동 옵션 포함 문화 루트
2. **복합 악조건**: 비·지하철 혼잡·대기질 나쁨 → AI가 실내 + 도보 최소 코스로 자동 전환
3. **접근성 필요**: 동반자 거동 불편 → 무장애 인증 장소만 필터

### 핵심 차별점
- 공공 API만 사용 (신뢰성·공공성 확보)
- 컨텍스트 배지로 "왜 이 추천인지" 한눈에 설명 (AI 설명 가능성)
- 기존 신뢰 불변식 유지 (미확인 정보 추정 금지)

## 방향 B. 무장애 접근성 여행 지원

### 핵심 메시지
> "장애인·고령자·유모차 동반 여행자가 서울의 공공 문화시설을 불안 없이 방문할 수 있도록, 접근성 공공 데이터와 AI가 함께 경로를 설계합니다."

### KONNECT와의 연결
기존 사용자 선호 시스템(`domain/preferences_merge.py`)에 접근성 프로파일을 추가하고, 한국관광공사 무장애 관광 API를 `sources/`에 추가합니다.

### 추가할 공공 데이터

| 데이터 | API | 활용 방식 |
|---|---|---|
| 무장애 관광지 정보 | 한국관광공사 무장애 API | 휠체어·유모차·고령자 필터 |
| 엘리베이터 운행 현황 | 서울교통공사 API | 지하철역 엘리베이터 실시간 상태 |
| 배리어프리 화장실 | 서울시 공공화장실 API | 경로 내 접근 가능 편의시설 |

### 구현 계획 (3인, 2박 3일)

```
Day 1 — 설계 (8h)
  AI/Backend A   무장애 API 스펙 분석 + sources/accessible.py 설계
                 domain/accessibility.py 판정 로직 설계
                 (휠체어 가능/부분/불가 3단계)

  Backend B      models/preferences.py — accessibility_profile 필드 추가
                 DB 마이그레이션: user_preferences에 컬럼 추가
                 api/ 스텁 준비

  Frontend/PM    입력 화면에 접근성 프로파일 선택 UI 설계
                 (휠체어 이용 / 유모차 / 고령자 동반)
                 결과 카드 접근성 배지 디자인

Day 2 — 구현 (12h)
  AI/Backend A   sources/accessible.py 구현
                 domain/accessibility.py 구현 + pytest
                 agent/orchestrator.py — 접근성 Hard 필터 추가
                 (접근성 미확인 → fits 아님, check로 분류)

  Backend B      api/recommend.py — 접근성 프로파일 반영
                 Pydantic 모델 최종 확정
                 배포 갱신

  Frontend/PM    접근성 프로파일 선택 컴포넌트
                 결과 카드 배리어프리 배지
                 QA (접근성 ON/OFF 비교)

Day 3 — 통합·데모 (6h)
  전원           실 API 응답 확인 + 통합 테스트
                 데모 시나리오 리허설
                 발표 준비
```

### 데모 시나리오
1. **휠체어 이용자**: 접근 불가 장소 자동 제외, 무장애 인증 장소만 추천
2. **유모차 동반**: 계단 없는 경로 + 수유실 인근 장소 우선
3. **고령자 동반**: 도보 거리 최소화 + 실내 위주 루트

### 핵심 차별점
- 사회적 약자를 위한 공공 데이터 활용 (공공성 최고점)
- "접근 불가" 추정 없이 확인된 정보만 필터 (신뢰성)

## 공통 기술 강점 (발표 시 강조 포인트)

어떤 방향을 선택하든 아래를 발표에서 강조하면 심사위원에게 효과적입니다.

1. **공공 데이터만 사용** — TourAPI(한국관광공사), KMA(기상청), AirKorea(환경부) 등 정부 공식 API
2. **AI가 사실을 만들지 않는다** — 판정은 코드, 설명만 LLM (AI 신뢰성·윤리)
3. **멀티컨텍스트 동시 처리** — 날씨·교통·시간·위치·사용자 조건을 한 번에
4. **미확인 정보는 미확인으로 표시** — 추정으로 채우지 않는 투명성
5. **배포 완료 서비스** — 라이브 URL에서 바로 데모 가능

## 실행 판단 보완 — 계획을 실제 해커톤에서 쓰는 방법

### 1. 먼저 고정할 전제

이 문서의 “공공 데이터 + AI + 멀티컨텍스트”는 주제에 맞춘 확장 방향이다. 현재 KONNECT의 검증된 베이스는 **서울 문화경험 추천**이며, 해커톤 시작 전에 새 기능을 전부 완성해야 하는 것은 아니다.

따라서 다음 원칙으로 범위를 제한한다.

- 기존 A 추천 흐름을 망가뜨리지 않는다.
- 새 API는 최대 1~2개만 핵심 경로에 추가한다.
- 외부 API가 실패해도 기존 추천 결과가 보이게 한다.
- 미확인 데이터는 `check_needed` 또는 “확인 필요”로 표시한다.
- 발표에서 구현되지 않은 도시·접근성·실시간성을 완료 기능처럼 말하지 않는다.

### 2. 주제 확인 후 선택 규칙

| 해커톤 주제 | 선택 | 이유 |
|---|---|---|
| 공공 데이터·AI 융합·스마트 관광 | **A** | 현재 기능과 가장 많이 겹치고 2박 3일 내 성공 확률이 높음 |
| 사회적 약자·포용·접근성 | **B** | 공공성과 사회적 가치가 가장 강함. 단, 데이터 품질 확인을 먼저 해야 함 |
| 생성형 AI·콘텐츠·다국어 | **C** | 구현은 빠르지만 기존 KONNECT 플랫폼 차별점이 약해질 수 있음 |
| 협업·개인화·그룹 의사결정 | **D** | 발표 임팩트는 있으나 DB·동시 입력·충돌 처리 공수가 커서 후순위 |

**주제 발표 전 기본 선택은 A**로 한다. 주제가 접근성을 명시적으로 요구할 때만 B로 전환한다. C와 D는 A/B의 핵심 흐름이 안정화된 뒤 남는 시간에만 선택한다.

### 3. 권장 최종안

#### 기본안: A를 얇게 구현한 “상황 인식 문화경험 추천”

기존 날씨·대기질·시간·위치·사용자 조건에 **실시간 이동 상황 1개**만 추가한다.

- 1순위: 서울 지하철 혼잡도
- 2순위: API 발급·응답이 불안하면 따릉이 또는 혼잡도 중 검증된 하나
- 새 데이터는 Hard 제외가 아니라 Context 배지·Soft 랭킹에만 사용
- 실시간 값이 없으면 기존 추천으로 graceful fallback

발표 문장:

> “KONNECT는 후보를 많이 생성하는 AI가 아니라, 공공 데이터와 현재 상황을 함께 확인해 지금 갈 수 있는 선택지를 줄이는 AI입니다.”

#### 접근성안: B를 별도 제품으로 만들지 말고 A의 프로파일로 추가

접근성 API가 실제로 확인될 때만 다음 범위로 제한한다.

- 입력: 휠체어·유모차·고령자 동반 중 하나 선택
- 확인된 접근성 필드만 badge로 표시
- `accessible=true`라고 단정하지 않고 `confirmed / partial / unknown`으로 표시
- 접근성 정보가 없으면 자동 통과시키지 않고 확인 필요로 분리
- 엘리베이터 실시간 연계·완전한 무장애 경로 계산은 이번 해커톤 범위에서 제외

### 4. 2박 3일 실행 계획과 게이트

#### 시작 전 준비 — 2시간 이내

| 작업 | 완료 기준 |
|---|---|
| API 후보 조사 | 실제 endpoint, 인증 방식, 샘플 응답, 이용 조건 확보 |
| 키 검증 | 개발 PC에서 `curl.exe` 또는 Python으로 200 응답 확인 |
| 베이스 검증 | `/health`, A 추천, B 루트, FAQ 각 1회 성공 |
| 브랜치·환경 분리 | `hackathon/<topic>` 브랜치와 `.env` 준비 |
| 데모 입력 고정 | 출발지·시간·자연어 요청·기대 결과 문서화 |

**API 키 또는 샘플 응답을 확보하지 못하면 해당 기능은 구현하지 않고, 기존 데이터로 시연 가능한 범위로 즉시 축소한다.**

#### Day 1 — 검증과 계약 우선

| 역할 | 작업 | 종료 조건 |
|---|---|---|
| AI/Backend A | 새 API의 응답을 raw fixture로 저장하고 adapter 계약 정의 | 네트워크 없이 fixture 테스트 가능 |
| Backend B | Pydantic 모델·Envelope·환경변수·fallback 설계 | 새 필드가 없어도 기존 API 응답이 유지됨 |
| Frontend/PM | 배지·상태·미확인 문구와 발표 흐름 설계 | `confirmed / check needed / unavailable` 3상태 확정 |
| 전원 | 30분 통합 회의 | Hard 조건과 Soft 신호의 경계 합의 |

Day 1 종료 시점에 **실 API 연동보다 먼저 fixture 기반 계약 테스트**가 통과해야 한다. 계약이 불명확한 API를 Day 2까지 붙잡지 않는다.

#### Day 2 — 최소 구현

| 역할 | 작업 | 종료 조건 |
|---|---|---|
| AI/Backend A | `sources/<provider>.py`, timeout·retry·정규화 구현 | API 실패 시 `None`/unknown으로 반환 |
| Backend B | environment/context 모델과 orchestrator 연결 | 기존 A 추천 테스트가 모두 통과 |
| Frontend/PM | 배지·요약·fallback UI 구현 | 미확인·API unavailable이 긍정 상태로 보이지 않음 |
| 전원 | 로컬 E2E와 실제 API 3회 테스트 | 성공 3회 또는 원인 기록 후 fallback 확정 |

새 데이터로 후보를 Hard 제외하지 않는다. 운영 가능성·가격·예약 같은 사실 판정은 기존 공식 데이터와 결정론 로직만 담당한다.

#### Day 3 — 안정화와 발표

| 시간 | 작업 |
|---|---|
| 오전 | 전체 테스트, lint, 실제 API smoke test, 모바일 브라우저 확인 |
| 점심 전 | Render/Vercel 배포 및 `/health` 확인 |
| 오후 초반 | 대표 시나리오 3회 리허설, 실패 시 fallback 리허설 |
| 오후 후반 | 3분 문제·해결·신뢰성·확장성 발표 구성 |

Day 3에 새 기능을 추가하지 않는다. 실패한 기능은 숨기지 말고 feature flag를 끄거나 fallback 상태로 고정한다.

### 5. Definition of Done

다음 항목을 모두 만족해야 “해커톤 기능 완료”로 표시한다.

- [ ] 기존 A 추천·B 루트·FAQ가 신규 변경 전후로 동작한다.
- [ ] 신규 API 성공·빈 응답·401/403·timeout·잘못된 JSON을 각각 테스트했다.
- [ ] 신규 데이터에 provenance와 상태가 있다.
- [ ] 미확인 값을 무료·이용 가능·접근 가능으로 바꾸지 않는다.
- [ ] 외부 API 실패 시 5xx 대신 기존 결과 또는 명시적 unavailable 상태를 반환한다.
- [ ] API 키가 프론트 번들·로그·Git에 노출되지 않는다.
- [ ] 모바일 폭에서 배지와 오류 문구가 읽힌다.
- [ ] 대표 데모를 새 터미널/새 브라우저에서 3회 반복 성공했다.
- [ ] 배포 URL에서 `/health`와 핵심 API smoke test가 통과한다.
- [ ] 발표 자료에 실제 구현 범위와 미구현 범위를 구분해 적었다.

### 6. 장애 시 fallback 순서

```text
신규 실시간 API 성공
  → context badge + soft ranking
신규 API 빈 응답/부분 실패
  → "현재 데이터 확인 필요" 표시 + 기존 추천 유지
기존 TourAPI 일부 실패
  → 성공한 소스만 병합
핵심 공식 API 실패
  → 정상 추천인 것처럼 채우지 않고 재시도/오류 화면
```

준비된 결과를 실제 응답인 것처럼 보여주는 방식은 사용하지 않는다. 데모 중 장애가 나면 “실시간 소스가 unavailable이어서 검증된 기본 추천으로 전환했다”고 설명한다.

### 7. 발표 구성안

#### 3분 버전

1. **문제 30초:** 여행자는 장소 목록이 아니라 지금 갈 수 있는 장소가 필요하다.
2. **입력 30초:** 위치·시간·관심사·현재 상황을 자연어로 입력한다.
3. **판정 60초:** 공식 데이터 조회, 코드 판정, AI 설명 분리를 보여준다.
4. **결과 30초:** fits/check needed/alternative와 근거·미확인 표시를 보여준다.
5. **플랫폼 30초:** 서울 커넥터 위에 검증된 코어가 있고, 다른 데이터 커넥터로 확장한다.

#### 반드시 보여줄 화면

- 입력 조건과 AI가 이해한 조건
- 결과 상태와 Reason/Fact/Unconfirmed 구분
- 새 공공 컨텍스트 배지
- API 일부 실패 시 fallback 상태
- 지도·경로 또는 “경로 확인 필요” 상태

#### 심사위원 질문에 대한 답

| 질문 | 답변 |
|---|---|
| 다른 도시도 가능한가? | 코어는 재사용 가능하지만 도시별 공식 데이터·지도·이동 커넥터를 추가해야 한다 |
| AI가 틀리면 어떻게 하는가? | 가격·시간·좌표·예약 판정은 코드와 공식 데이터가 소유하고, 미확인은 확인 필요로 남긴다 |
| API가 끊기면? | 선택 소스는 fallback하고, 핵심 사실 소스가 실패하면 결과를 만들어내지 않는다 |
| 플랫폼인가? | 현재는 개발자 확장형 플랫폼 코어이며, 멀티테넌트 SaaS는 후속 단계다 |
| 공공 데이터만 쓰는가? | 공식 공공 데이터가 사실의 기준이고, OpenAI·지도·이동 API는 보조 인프라로 구분해 사용한다 |

### 8. 기존 문서와의 정합성 메모

- “공공 데이터만 사용”이라는 표현은 현재 구조와 정확히 일치하지 않는다. OpenAI, Supabase, Tmap, Naver Maps, 선택적 Google Places도 사용하므로 **“공공 데이터를 사실 기준으로 사용하고 AI·지도·이동 API를 보조로 사용”**으로 표현한다.
- “베이스가 전부 완비”라는 표현은 RAG 적재, API 키, Render CORS, Naver 도메인 등록 여부에 따라 달라진다. 발표 전 smoke test로 확인한다.
- A 추천 간헐 실패 이력은 해결 전까지 계획서에서 삭제하지 않는다. 해결되면 재현 날짜·커밋·테스트 결과를 추가한다.
- 방향 A의 “5종 공공 데이터”는 새 API가 실제 연결된 뒤에만 사용한다. 현재는 날씨·대기질·위치·시간·사용자 조건과 새 데이터 1종을 구분해 설명한다.

## 최종 실행 결론

1. 주제가 확정되지 않았다면 **A의 얇은 MVP**로 시작한다.
2. API 키·샘플 응답을 Day 1에 검증하지 못하면 즉시 기존 KONNECT 데모로 축소한다.
3. 접근성 주제라면 B를 A의 프로파일 확장으로 구현하고, 확인되지 않은 접근성을 보장하지 않는다.
4. C와 D는 핵심 추천 안정화 이후의 선택 사항이다.
5. 해커톤에서의 목표는 “기능을 많이 추가”하는 것이 아니라 **공공 데이터 기반 신뢰 판정 플랫폼이라는 주장을 실제 화면과 실패 처리로 증명하는 것**이다.
