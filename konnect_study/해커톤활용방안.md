# KONNECT 코드 자산 활용방안 및 재활용 계획

> 작성일: 2026-10-28  
> 대상: KONNECT 리포지토리를 규모·주제·평가 방식이 다른 대회와 프로젝트에 재활용하는 팀

---

## 1. 결론 요약

**재활용 가능하다. 대회의 규모·주제·평가 방식과 관계없이 기존 구조와 코드를 활용하고, 대회 주제에 맞는 콘텐츠만 교체하면 된다.**

KONNECT는 AI Agent, RAG, 인증, 지도, 외부 API 연동, 결정론적 판정, 테스트·배포 구조를 이미 갖춘 서울 문화경험 서비스다.
대회가 더 작거나 주제가 달라도 기존 구조를 제한 없이 활용할 수 있다. 서비스명, 안내 문구, 질문·답변 콘텐츠, 추천 대상, RAG 문서, 화면 카피와 같은 콘텐츠를 주제에 맞게 바꾸면 동일한 Agent·API·판정·화면 구조를 새로운 결과물에 적용할 수 있다.

### 문의 결과를 반영한 전제

- 이번 대회가 KONNECT와 같은 급인지 여부와 관계없이 활용할 수 있다.
- “플랫폼으로 출품 가능한가”가 아니라 “기존 코드 위에 주제 콘텐츠를 어떻게 적용할 것인가”를 기준으로 판단한다.
- 기존 서비스의 구조와 기능은 유지하고, 주제에 맞는 콘텐츠·데이터·문구를 교체한다.
- 새 대회에서는 기존 기능을 제한 없이 활용하고, 필요하면 콘텐츠 범위만 줄이거나 늘린다.

## 2. 재활용 가치 분석

### 2.1 강점 — 이미 갖춰진 것

| 영역 | 내용 |
|---|---|
| AI Agent 파이프라인 | LangChain tool-calling, 멀티턴 대화, 오케스트레이터 (`agent/`) |
| RAG | Supabase pgvector + OpenAI Embeddings — 지식베이스 적재·검색 전 과정 |
| 인증 | Supabase Auth (Google OAuth + 익명 Sign-in + identity linking) |
| 데이터베이스 패턴 | Supabase Postgres + RLS, 마이그레이션 스크립트 |
| 배포 패턴 | Render(백엔드) + Vercel(프론트) 구조 — 새 대회 환경에 맞춰 재설정 필요 |
| 외부 API 클라이언트 | TourAPI, TMap, Google Places, KMA, AirKorea — httpx + tenacity 패턴 |
| 프론트엔드 | 10개 페이지, 10개 이상 컴포넌트, 지도, 바텀시트, 상태관리 |
| 번역 모듈 | `agent/translate.py` + `components/translate-toggle.js` 기존 구현 존재 |
| 평가 프레임워크 | `eval/` — golden set + metrics, pytest 기반 검증 |
| 데이터 신뢰 패턴 | normalize → judge → rank → explain 파이프라인 |

### 2.2 약점 / 위험 요소

| 리스크 | 설명 |
|---|---|
| 도메인 결합도 높음 | `domain/` 로직이 서울 문화경험에 특화 — 새 도메인은 신규 작성 필요 |
| 학습 곡선 | 백엔드 모듈 90개 이상 — 온보딩에 반나절 최소 필요 |
| Seoul 특화 API | TourAPI EngService2는 한국 문화관광 전용 |
| 신뢰 불변식 | CLAUDE.md §6 원칙 — 도메인이 달라도 검증 가능한 공통 기준 |

### 2.3 콘텐츠 교체 대상

다음은 새 주제에 맞춰 내용만 교체하면 된다.

- TourAPI EngService2와 서울문화포털 호출 및 한국 관광 분류값
- 서울 중심 기본 위치·문화시설 분류·의료관광 제외 규칙
- Naver Maps·Tmap 기반 좌표·경로 처리
- 서울 여행 FAQ와 RAG 지식 문서
- 서울 문화경험에 맞춘 Reason 문구와 화면 카피
- 현재 배포 URL, CORS 값, API 키, Supabase 프로젝트 설정은 각 대회 환경에 맞는 값으로 입력한다.

이 부분은 **콘텐츠·데이터·환경설정 교체 대상**이다. 기존 Agent, API, 화면, 판정, 테스트 구조는 그대로 활용하고 주제에 맞는 값과 문구만 바꿔 적용한다. 교체 범위에는 제한을 두지 않는다.

## 3. 재활용 방식 선택

### Option A: 기존 서비스 위에 기능 확장

기존 도메인(서울 문화경험) 위에 새 기능 레이어를 추가.

- 인프라·인증·배포 즉시 사용
- 온보딩 빠름 (기존 코드 건드리지 않고 새 모듈만 추가)
- 2박 3일 내 데모 가능한 완성도 달성 현실적
- 주제와 사용자 흐름이 서울 문화·관광과 가까울 때 권장
- 대회 기간이 짧고 라이브 데모가 중요한 경우 적합

### Option B: 콘텐츠 교체형 재활용 (권장)

FastAPI + Supabase + LangChain + Vanilla JS 패턴을 추출해 완전히 다른 서비스 구축.

- 자유도 높지만 기존 코드 제거·개조에 시간 소요
- 대회 주제가 달라도 기존 Agent·RAG·판정·API·UI 구조를 그대로 사용할 때 적합
- 서비스명, 질문·답변, 추천 콘텐츠, 안내 문구, RAG 문서만 새 주제에 맞게 교체한다
- 기존 기능을 제한하지 않고 필요한 기능을 모두 활용할 수 있다

### Option C: 기존 KONNECT를 기준 서비스로 활용

대회 규모가 작거나 주제 콘텐츠만 바꾸면 될 때는 코드를 크게 바꾸지 않는다.

- 기존 서비스의 배포 URL·시연 영상·테스트·아키텍처 문서를 참고 자료로 사용
- 새 대회 요구에 맞는 콘텐츠와 데이터만 교체
- `normalize → judge → rank → explain` 구조와 신뢰 불변식을 설계 근거로 재사용
- 기존 저장소를 새 대회 결과물로 오인시키지 않고, 재사용한 모듈과 새로 만든 부분을 명시

**권장 방식:** 기존 KONNECT 구조를 유지하고 주제 콘텐츠를 교체한다. 필요한 경우 새 API나 화면도 기존 구조에 맞춰 추가한다.

### 3.1 재사용 수준 결정표

| 상황 | 가져갈 것 | 가져가지 않을 것 |
|---|---|---|
| 같은 관광·문화 계열 | Agent, domain 판정, 지도 UI, 세션 | 서울 API·서울 카피 |
| 다른 공공서비스 추천 | API 계약, 정규화·판정·근거 표시, 테스트 패턴 | 관광 분류·지도·Tmap |
| FAQ·문서 질의 | RAG chunk/retrieve/refuse, citations, Envelope | 서울 여행 knowledge |
| 이미지·번역 중심 대회 | FastAPI 계약, 인증 선택, 오류 처리, UI 상태 | 추천 orchestrator 전체 |
| 단기간 프로토타입 | 입력·결과 컴포넌트, 도메인 순수 함수, fixture | Supabase Auth·멀티턴·장기기억 |
| 장기 프로젝트 | 코어 모듈, 어댑터 계약, eval, trace | 현재 배포 설정과 하드코딩 URL |

## 4. 재활용 트랙

### Track 1: 유사 도메인 확장 — 맛집 + 문화 패키지 루트 `난이도 중`

문화경험 추천 후 주변 식당을 자연스럽게 연계한 통합 루트 제공.

**확장 포인트:**
- `sources/` — 네이버 로컬 검색 API 또는 Kakao Local API 클라이언트 신규 추가
- `domain/food_filter.py` — 가격대·식이제한(채식/할랄/글루텐프리) 판정 로직
- `models/recommend.py` — `food_option` 필드 추가
- `agent/orchestrator.py` — 문화 후보 확정 후 식당 후보 병렬 조회 연결
- 프론트 — 결과 카드에 식당 섹션 추가

**데모 시나리오:** "박물관 관람 후 근처 한식 맛집(채식 가능)"을 한 번에 추천

---

### Track 2: 공통 판정 코어 재활용 — 그룹 여행 플래너 `난이도 중`

여러 명의 관심사·예산·이동 선호를 병합해 공통 루트 추천.

**확장 포인트:**
- `models/group.py` — GroupSession, MemberPreference 스키마
- `db/migrations/0003_group_sessions.sql` — 그룹·멤버 테이블
- `domain/preferences_merge.py` — 다수 선호 교집합/가중합 로직 확장
- `api/group.py` — 그룹 생성·참가·선호 제출 엔드포인트
- 프론트 — 멤버 초대 링크 생성 + 선호 입력 시트 신규 추가

**데모 시나리오:** 4명이 각자 선호 입력 → AI가 모두가 만족할 문화 루트 생성

---

### Track 3: 기능 모듈 재활용 — 번역 + 현장 가이드 강화 `난이도 낮음`

이미 존재하는 `translate.py` + `translate-toggle.js`를 확장해 현장 AI 가이드로 발전.

**확장 포인트:**
- `api/interpret.py` — `POST /api/interpret` 신규 (이미지/음성 → 번역 + 맥락 설명)
- OpenAI Whisper — 음성 입력 → 텍스트 변환
- GPT-4o Vision — 안내판 사진 → 번역 + 문화 설명
- 프론트 — 카메라/마이크 입력 컴포넌트, 결과 오버레이

**데모 시나리오:** 한국어 안내판 사진 찍기 → 즉시 영어 번역 + 문화적 배경 설명

---

### Track 4: 컨텍스트 파이프라인 재활용 — 날씨 연동 동선 실시간 재구성 `난이도 중`

이미 있는 `domain/environment.py` + `sources/kma.py`를 심화해 날씨 변화 시 루트 자동 재구성.

**확장 포인트:**
- `sources/kma.py` — 실황(현재) → 단기예보(3~6시간 후) 추가 연동
- `domain/route.py` — 예보 악화 감지 시 실내 경험 우선 재정렬 로직
- `agent/route_orchestrator.py` — 날씨 변화 알림 + 대안 루트 제안
- 프론트 — 날씨 변화 배너 + "실내 전환" CTA

**데모 시나리오:** 오후에 비 예보 → 야외 일정을 실내 대체로 자동 재구성

## 5. 2박 3일 개발 일정

### Day 1 — 이해 + 설계 (8~10시간)

```
오전 (3h)  코드베이스 온보딩
           - CLAUDE.md §2(스택), §4(아키텍처), §6(신뢰 불변식) 필독
           - backend 실행: cd backend && uvicorn app.main:app --reload
           - frontend 실행: cd frontend && python -m http.server 5500
           - 기존 pytest 전체 통과 확인: python -m pytest

오후 (3h)  Track 선정 + 설계
           - 팀 논의로 Track 1~4 중 선택
           - 새 엔드포인트 API 계약 설계 (Pydantic 모델 초안)
           - 신규 외부 API 키 발급 (필요 시)
           - 새 브랜치 생성: git checkout -b hackathon/track-N

저녁 (3h)  기반 작업
           - DB 스키마 추가 (Supabase SQL 에디터)
           - models/ 에 새 Pydantic 모델 파일 생성
           - 더미 pytest 1개 작성 후 Green 확인
```

### Day 2 — 핵심 구현 (12시간)

```
오전 (4h)  백엔드 핵심 로직
           - sources/ 에 새 API 클라이언트 추가 (httpx + tenacity 패턴 복사)
           - domain/ 에 판정 로직 추가 + 단위 테스트
           - pytest Green 유지하며 진행

오후 (4h)  Agent 연결 + API 엔드포인트
           - agent/tools/schemas.py 에 새 Tool 추가
           - chat_agent.py 또는 orchestrator.py 확장
           - api/ 에 새 라우터 추가 → main.py include_router
           - 로컬 curl/브라우저로 동작 확인

저녁 (4h)  프론트엔드
           - pages/ 에 새 페이지 또는 기존 페이지 확장
           - components/ 에 새 UI 컴포넌트
           - js/api.js 에 새 엔드포인트 래퍼 추가
           - 모바일 브라우저 확인 (390px 기준)
```

### Day 3 — 통합 + 데모 (6~8시간)

```
오전 (3h)  통합 테스트 + 버그 수정
           - 전체 pytest 통과 확인
           - 실 브라우저 end-to-end 데모 시나리오 3회 통과
           - 엣지케이스 처리 (0건, API 실패 등)

오후 (2h)  배포 + 데모 준비
           - Render 백엔드 재배포 (git push → 자동)
           - Vercel 프론트 재배포
           - 데모 시나리오 3개 정리 + 발표 자료 준비

발표       5분 라이브 데모 + Q&A
```

## 6. 팀 역할 분담 (3인 확정)

> 팀원 3명 기준. 백엔드 2인 / 프론트+PM 1인 구성이 KONNECT 확장에 가장 효율적입니다.  
> 예상 주제: 공공성 + AI + 멀티컨텍스트

| 역할 | 주요 담당 영역 | Day 1 | Day 2 | Day 3 |
|---|---|---|---|---|
| **AI / Backend A** | agent/, domain/, sources/ | 새 공공 API 조사 + 클라이언트 작성 | LangChain 파이프라인 연결, 멀티컨텍스트 심화 | 통합 디버깅, trace 시각화 |
| **Backend B** | api/, db/, models/, 배포 | DB 스키마 + Pydantic 모델 확정 | API 엔드포인트 + Render 배포 갱신 | 버그 수정, 배포 안정화 |
| **Frontend + PM** | pages/, components/, 발표 | 화면 흐름 설계 + Track 최종 선정 | UI 구현 + 공공 데이터 출처 배지 | 데모 시나리오 3개 + 발표 준비 |

### 3인 분업 시 주의사항
- **API 계약(Pydantic 모델)을 Day 1 저녁까지 확정**해야 A와 B가 Day 2에 충돌 없이 병렬 작업 가능합니다.
- Backend B가 `api/` 라우터를 먼저 스텁으로 올려두면 Frontend가 Day 2 오전부터 바로 연결 가능합니다.
- Frontend + PM이 QA 역할도 겸하므로 Day 2 저녁에 통합 테스트 시간을 반드시 확보하세요.

## 10. 대회 규모별 콘텐츠 교체 계획

### 유형 A — 짧은 소규모 대회·아이디어 검증

**목표:** 1~2일 안에 주제 콘텐츠를 교체해 문제와 결과 화면을 보여준다.

- 기존 프론트의 입력·결과 카드 스타일과 기능을 그대로 사용
- 외부 API는 1개 이하, 가능하면 fixture 또는 공개 샘플 데이터 사용
- 로그인·RAG·장기기억·지도는 제외
- 결정론적 판정 함수 1개와 테스트 3~5개를 먼저 작성
- 발표에서는 “KONNECT의 신뢰 판정 패턴을 적용했다”고 설명

이 유형에서도 전체 구조를 사용할 수 있으며, 실제 발표에 필요한 콘텐츠만 준비한다.

### 유형 B — 2박 3일 기능 구현 대회

**목표:** 기존 AI·API·화면 흐름에 새 주제 콘텐츠를 연결한 하나의 완주 시나리오를 만든다.

- 기존 기능과 콘텐츠를 제한 없이 활용
- 필요한 경우 신규 외부 API를 추가
- Day 1에 새 콘텐츠·API·키를 확인하고 기존 흐름에 연결
- Day 2 종료 시 기존 핵심 기능과 신규 기능을 각각 독립 실행
- Day 3은 새 기능보다 배포·fallback·발표 검증에 사용

### 유형 C — 장기 프로젝트·제품화

**목표:** 기존 구조를 유지하면서 주제 콘텐츠를 계속 교체해 여러 대회와 프로젝트에 활용한다.

1. 새 대회의 서비스명·소개·질문·답변 콘텐츠를 교체한다.
2. RAG 문서를 새 주제에 맞게 교체한다.
3. 추천 대상과 결과 문구를 새 콘텐츠에 맞게 교체한다.
4. 필요한 경우 API 키와 외부 데이터만 새 환경에 맞게 입력한다.
5. 기존 테스트·오류 처리·신뢰 원칙은 그대로 유지한다.

이 유형은 KONNECT를 다음 대회와 제품의 기본 구조로 계속 활용하는 계획이다.

## 11. 재활용 절차

### Phase 0 — 콘텐츠 교체

새 대회의 주제에 맞춰 다음 내용을 자유롭게 교체한다.

- 서비스명·소개·사용자 안내
- 질문·답변·RAG 문서
- 추천 대상·데이터·카테고리
- Reason copy·배지·화면 문구
- 이미지·아이콘·브랜드 콘텐츠
- 외부 API endpoint·키·환경변수

기존 Agent, API, 화면, 판정, 테스트 구조는 그대로 활용한다. 콘텐츠 교체 범위에는 제한을 두지 않는다.

### Phase 1 — 최소 슬라이스 구현

다음 순서로 한 번에 끝까지 연결한다.

```text
입력 모델
  → fixture 또는 단일 API 조회
  → 공통 Fact 정규화
  → 결정론 판정
  → 결과 Envelope
  → 결과 화면
  → 성공·빈 응답·실패 테스트
```

필요하면 로그인, 멀티턴, 여러 외부 API, 디자인 확장도 기존 구조에서 함께 활용한다.

### Phase 2 — 재사용 검증

- 원래 KONNECT 테스트가 새 프로젝트 변경으로 깨지지 않는지 확인
- 새 도메인에서 빈값·모호값이 긍정으로 바뀌지 않는지 확인
- API 실패와 timeout이 정상 결과로 위장되지 않는지 확인
- 출처·provenance·미확인 상태가 화면까지 전달되는지 확인
- 기존 저장소와 새 결과물의 담당 범위를 문서화

## 12. 코드 재활용 시 지켜야 할 기준

### 반드시 유지할 것

1. **미확인 ≠ 가능**: 빈값을 무료·예약 불필요·접근 가능으로 바꾸지 않는다.
2. **사실과 설명 분리**: LLM은 사실을 만들지 않고, 근거를 설명하거나 구조화한다.
3. **부분 실패 투명성**: 일부 소스가 실패하면 상태를 표시하고 성공한 범위만 반환한다.
4. **공통 응답 계약**: 성공·빈 결과·검증 실패·시스템 오류를 구분한다.
5. **테스트 가능한 판정**: 외부 API 호출과 순수 판정 로직을 분리한다.

### 새 프로젝트에서 바꿀 수 있는 것

- 서울 전용 Hard 제외 규칙과 새 주제의 판정 규칙
- 가격·예약·운영시간 등 사실의 정의
- 기본 시간·거리·반경 값
- 사용자 동의·로그인·개인정보 저장 범위
- 새 외부 API endpoint·키·호출 설정
- RAG 문서의 내용과 출처

## 13. 발표·제출 시 표현

### 권장 표현

> KONNECT에서 검증한 AI Agent, 근거 기반 RAG, 결정론적 판정, 부분 실패 처리 패턴을 이번 주제에 맞게 재사용했다. 서울 관광 전용 데이터와 UI는 그대로 가져온 것이 아니라 요구사항에 맞게 교체·축소했다.

### 안내할 표현

- “기존 구조와 코드는 유지하고 대회 주제에 맞는 콘텐츠를 제한 없이 교체해 활용한다.”
- “Agent, API, 화면, 판정, 테스트 구조를 재사용하고 필요한 콘텐츠와 데이터만 바꾼다.”
- “환경에 따라 API 키와 배포 설정은 새 값으로 입력한다.”

## 14. 재활용 완료 기준

- [ ] 대회 주제에 맞는 콘텐츠와 데이터로 교체했다.
- [ ] 기존 Agent·API·화면·판정·테스트 구조가 정상 동작한다.
- [ ] 새 외부 API와 환경변수를 입력했다.
- [ ] 새 RAG 문서와 화면 문구를 반영했다.
- [ ] 성공·빈 응답·timeout·인증 실패를 테스트했다.
- [ ] 미확인 데이터가 긍정 상태로 표시되지 않는다.
- [ ] 발표 자료에 “기존 구조 재사용 + 콘텐츠 교체” 내용을 명시했다.

## 최종 의견

KONNECT는 대회의 규모·주제·평가 방식과 관계없이 재활용할 수 있다. **기존 구조와 코드를 유지하고 콘텐츠·데이터·환경설정만 교체하면 새로운 대회와 프로젝트에 제한 없이 적용할 수 있다.**

```text
그대로 활용: API 계약 · Agent/RAG · 화면 · 판정 · 테스트 · 오류 처리
교체: 서비스 콘텐츠 · 질문/답변 · 추천 데이터 · 문구 · 이미지 · 외부 API 설정
```

따라서 최종 전략은 **“KONNECT의 기존 구조와 코드를 그대로 활용하고, 대회 주제에 맞는 콘텐츠만 교체해 제한 없이 재사용하는 것”**이다.
