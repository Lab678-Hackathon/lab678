# KONNECT 해커톤 플랫폼 사용 검토 의견

> 검토일: 2026-10-28  
> 검토 대상: [konnect_report.md](./konnect_report.md) 및 기존 플랫폼 평가·특이점 문서  
> 목적: KONNECT를 해커톤에서 “플랫폼”으로 소개하고 사용할 수 있는지 판단

## 1. 결론

**해커톤에서 플랫폼으로 소개하고 시연하는 것은 가능하다.** 다만 현재 구현은 범용 플랫폼이라기보다 다음 구조에 가깝다.

> **서울 문화경험 도메인에 실제 적용된 신뢰형 추천 플랫폼 코어 + 서울 전용 데이터 커넥터**

따라서 발표에서는 “어떤 도시·어떤 도메인이든 즉시 연결되는 완성형 플랫폼”이라고 말하기보다, **다른 도시와 도메인으로 확장할 수 있는 공통 코어를 서울에서 검증한 플랫폼**이라고 표현하는 것이 정확하다.

### 최종 판단

| 사용 목적 | 판단 | 의견 |
|---|---|---|
| 해커톤 데모 | **GO** | 이미 화면·API·배포·핵심 시나리오가 있어 충분히 시연 가능 |
| 서울 관광/문화 서비스 파일럿 | **조건부 GO** | 미결 장애와 외부 API 의존성을 데모 전에 정리해야 함 |
| 여러 도시로 확장하는 플랫폼 | **조건부 GO** | 소스 어댑터와 지역 설정 계층을 먼저 분리해야 함 |
| 여러 도메인을 지원하는 공개 SaaS | **현재 NO** | 테넌트·권한·쿼터·관측성·데이터 계약이 아직 제품화되지 않음 |

## 2. 플랫폼으로 볼 수 있는 근거

### 2.1 재사용 가능한 코어가 실제로 존재함

다음 부분은 서울 데이터가 바뀌어도 재사용할 수 있는 플랫폼 자산이다.

- FastAPI 기반 API 계약과 공통 `Envelope` 응답
- Pydantic 입력·출력 모델
- 외부 데이터 조회 → 정규화 → 결정론 판정 → 랭킹 → 설명의 파이프라인
- 가격·운영시간·예약·좌표를 LLM이 임의 생성하지 못하게 한 신뢰 경계
- `fits / check_needed / alternative` 3상태 결과 모델
- 외부 API 실패를 부분 성공으로 처리하는 graceful fallback
- Supabase Auth·세션·선호·RLS 구조
- RAG의 근거 검색 및 근거 없을 때 refuse하는 흐름
- 테스트 가능한 `domain/` 순수 판정 로직
- 추적 ID와 단계별 trace 구조

이 구조는 단순한 서울 추천 화면보다 재사용 가치가 높다. 특히 “AI가 추천했으니 믿어야 한다”가 아니라 **확인된 사실과 미확인 정보를 분리하는 추천 엔진**이라는 포지셔닝은 해커톤에서 차별점이 될 수 있다.

### 2.2 실제 사용자 흐름이 끝까지 연결되어 있음

리포트 기준으로 다음이 하나의 제품 흐름으로 연결되어 있다.

1. 자연어·위치·시간 입력
2. 후보 조회와 공식 데이터 보강
3. 운영 가능성·예산·예약·이동 판정
4. 결과 카드와 지도 표시
5. 선택 저장
6. 로그인·선호 반영
7. 챗봇·루트·FAQ로 확장

플랫폼 주장을 뒷받침하려면 단순 아키텍처 그림보다 이 연결된 흐름을 보여주는 편이 효과적이다.

## 3. 플랫폼이라고 부르기 전에 해결할 위험

### P0 — 데모 안정성

기존 문서에는 정상 조건에서 A 추천이 반복 실패한 이력이 남아 있다. 리포트의 “Phase 4 완료”와 충돌하므로, 완료 선언만으로 해결됐다고 간주하면 안 된다.

- 최근 배포에서 경복궁역 기준 추천을 최소 3회 반복 실행
- 실패 시 `trace_id`, HTTP 상태, 외부 소스별 성공/실패를 확인
- 프론트의 1회 재시도만으로 숨기지 말고 최초 원인을 기록
- 실패해도 TourAPI 일부 결과로 화면이 열리는지 확인

**판단:** 이 항목이 재현되면 플랫폼 발표보다 먼저 안정화해야 한다.

### P0 — 설정·문서의 정합성

다음 설정은 신규 배포를 깨뜨릴 수 있다.

- [render.yaml](../render.yaml)의 CORS 값이 `REPLACE-WITH-VERCEL-URL` placeholder
- [frontend/js/config.js](../frontend/js/config.js)에 실제 URL과 placeholder가 함께 존재
- `config.py`의 `AGENT_LOOP` 기본값과 `.env.example` 값이 다름
- RAG 문서의 청크 수가 5개/6개로 서로 다르게 기록됨

플랫폼은 다른 사람이 환경을 복제할 수 있어야 하므로, “현재 내 배포는 된다”보다 **새 환경에서 재현되는가**가 중요하다.

### P1 — 외부 API가 너무 많음

현재 핵심 흐름은 TourAPI, 서울문화포털, Tmap, Naver Maps, OpenAI, Supabase, 기상청, AirKorea, 선택적 Google Places에 의존한다.

이 구조는 기능적으로 풍부하지만 해커톤 운영에서는 다음 장애가 발생할 수 있다.

- 키 만료·권한 미승인
- API별 rate limit·할당량 초과
- 특정 API 응답 지연
- 외부 장애가 긴 요청시간으로 누적
- 서비스별 개인정보·상업적 사용 조건 확인 필요

**권장:** 발표 핵심 시나리오는 TourAPI + OpenAI + Supabase + 지도 정도의 최소 경로로 제한하고, 날씨·대기질·Places·서울문화포털은 실패해도 핵심 흐름이 유지되는 선택 기능으로 운영한다.

### P1 — 범용 멀티테넌트 기능이 아직 없음

현재 구조는 사용자 계정과 선호를 지원하지만, 플랫폼 고객 또는 도시별 테넌트를 지원하는 구조와는 다르다.

부족한 플랫폼 기능:

- 테넌트/조직/프로젝트 구분
- 테넌트별 데이터 소스와 API 키
- 테넌트별 프롬프트·정책·브랜드 설정
- 사용량·비용·쿼터 관리
- 관리자 화면과 감사 로그
- 데이터 소스 버전과 갱신 상태 관리
- 테넌트 간 데이터 격리 정책

그러므로 현재는 “개발자가 커넥터를 추가해 확장하는 플랫폼 코어”이지, 고객이 직접 가입해 도시를 추가하는 셀프서비스 플랫폼은 아니다.

### P1 — 데이터 커넥터 추상화가 부족함

도시 확장 시 [sources/](../backend/app/sources/)의 TourAPI·서울문화포털·Tmap 호출부를 교체해야 하고, 도메인 모델도 한국 관광 데이터의 필드에 영향을 받는다.

플랫폼화하려면 다음 계약을 먼저 고정하는 것이 좋다.

```text
ProviderAdapter
  search_candidates(query, location, time_window) -> RawCandidate[]
  get_details(candidate_ids) -> RawDetail[]
  get_operational_facts(candidate_ids, date) -> OperationalFact[]
  get_movement(origin, destination) -> MovementInfo
```

그 위에 `Candidate`, `OperatingFact`, `PriceFact`, `ReservationFact`, `MovementInfo` 같은 공통 모델을 두면 도시별 소스 교체 범위를 줄일 수 있다.

### P2 — 평가 데이터가 플랫폼 품질을 증명하기에 작음

리포트에는 약 151개 이상 또는 과거 268개 테스트가 기록되어 있지만, eval golden set은 3개 쿼리로 작다. 단위 테스트가 판정 로직을 보호하는 것과 실제 추천 품질을 검증하는 것은 다르다.

해커톤 발표 전 최소한 다음 평가 세트를 추가하는 것을 권장한다.

- 정상 추천 10개
- 0건이 되어야 하는 Hard 조건 5개
- 가격 미확인·예약 미확인 5개
- 외부 API 부분 실패 5개
- 자연어 시간·위치 파싱 5개
- 실내/실외 충돌·배제 번복 5개
- 루트 시간 충돌 5개

평가 결과는 정확도 하나보다 다음 지표로 제시해야 한다.

- Hard 제외 누락률
- 미확인 정보의 긍정 오판율
- 외부 API 부분 실패 시 응답 성공률
- p50/p95 응답시간
- 0건·check-needed 결과의 설명 가능성

## 4. 해커톤에서의 추천 포지셔닝

### 피해야 할 표현

- “모든 도시와 모든 여행 도메인을 즉시 지원한다”
- “AI가 여행 가능 여부를 보장한다”
- “외부 API가 끊겨도 항상 정상 동작한다”
- “완전 자동으로 예약·방문까지 처리한다”

### 권장 표현

> KONNECT는 공식 데이터와 신뢰 판정을 조합해, 현재 조건에서 실제 가능한 문화경험을 좁혀주는 확장형 AI 추천 플랫폼이다. 서울 문화경험을 첫 번째 도메인으로 검증했으며, 데이터 커넥터와 정책 설정을 교체해 다른 도시로 확장할 수 있다.

핵심 데모 메시지는 “AI가 많이 말한다”가 아니라 다음이어야 한다.

1. 사용자의 자연어 조건을 구조화한다.
2. 공식 데이터를 직접 조회한다.
3. 운영시간·가격·예약·이동을 코드로 판정한다.
4. 확인되지 않은 것은 확인 필요로 남긴다.
5. 데이터 소스 일부가 실패해도 가능한 범위만 투명하게 보여준다.

## 5. 권장 해커톤 데모 범위

### 메인 시나리오 — 5~7분

1. 경복궁역 또는 광화문을 출발지로 선택
2. 오늘 14:00~17:00, 전통문화 선호, 박물관 제외 입력
3. A 추천 결과에서 `fits / check needed / alternative` 상태를 비교
4. 근거·미확인 flag·거리·지도 핀을 보여줌
5. 후보 하나를 선택해 현재 선택 상태를 저장

### 확장 시나리오 — 3~5분

1. 챗봇에서 문화루트 요청
2. 실내 선호로 후속 수정
3. 이동 경로와 시간표 표시
4. FAQ 질문에서 RAG 근거와 refuse 동작을 보여줌

### 데모 운영 원칙

- 시작 5분 전에 `/health` 호출
- 동일한 출발지·시간·입력으로 사전 리허설
- 외부 API가 불안하면 준비된 결과를 가짜로 보여주지 말고, 실제 장애·fallback을 설명할 수 있게 준비
- 발표 중에는 신규 도시/도메인 생성 약속을 구현 완료처럼 시연하지 않음

## 6. 플랫폼 전환 우선순위

### 해커톤 직전 — 반드시

1. A 추천 간헐 실패 원인 재현·수정 또는 데모 차단 조건 명시
2. CORS·API URL·AGENT_LOOP placeholder와 기본값 통일
3. RAG ingest 및 필수 환경변수 점검 스크립트 제공
4. 핵심 외부 API의 키·할당량·권한 점검
5. 배포 후 A/B/FAQ 각각 3회 이상 실호출
6. 응답시간과 외부 API별 실패 로그를 trace_id로 확인

### 해커톤 직후 — 플랫폼 코어화

1. `sources/`를 `ProviderAdapter` 계약으로 분리
2. 서울 고정값을 `TenantConfig` 또는 `DestinationConfig`로 이동
3. 도메인별 후보·운영·가격·예약 fact 모델을 명시
4. API 키를 테넌트/환경별 secret으로 분리
5. eval golden set을 30개 이상으로 확대
6. API rate limit, 비용 상한, 요청 취소, circuit breaker 추가

### 제품화 단계 — 공개 플랫폼

1. 멀티테넌트 DB/RLS와 관리자 화면
2. 데이터 소스 연결·상태·갱신 이력 UI
3. 사용량·비용·쿼터·감사 로그
4. 개인정보·외부 API 약관·데이터 보존 정책
5. 모델·프롬프트·정책 버전 관리
6. SLO/알람/장애 대응 runbook

## 8. 최종 의견

KONNECT는 해커톤에서 플랫폼으로 사용해도 된다. 다만 발표에서의 플랫폼은 **완성된 범용 SaaS**가 아니라 **검증된 추천·신뢰 판정 코어와 교체 가능한 데이터 소스 구조**를 의미해야 한다.

현재 가장 설득력 있는 전략은 다음이다.

1. 서울 문화경험을 대표 구현으로 시연한다.
2. 공식 데이터·판정·신뢰 경계를 플랫폼의 핵심 기술로 설명한다.
3. 도시별 데이터 커넥터와 정책 설정을 다음 확장 포인트로 제시한다.
4. 미결 장애와 외부 API 의존성을 숨기지 않고 안정화 계획까지 보여준다.

**따라서 해커톤 제출·발표는 GO, 범용 플랫폼 출시 선언은 보류**가 최종 의견이다.
