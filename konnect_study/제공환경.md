## 1. 주최 측 제공 항목

참가자 가이드에는 “Naito API 토큰 추가 제공, GPU V100 서버 지원”으로 적혀 있지만, 실제 전달받은 서버 코드와 사양은 다음과 같다. 아래 구성 정보를 현재 계획의 기준으로 삼되, 접속 정보와 운영 정책은 별도로 확인한다.

| 항목 | 제공 내용 | 확인된 범위 |
|---|---|---|
| Naito API | 팀장 계정에 API 토큰 추가 제공 | 토큰 제공 사실만 명시. endpoint·인증 헤더·모델명·요청 형식은 별도 안내 확인 필요 |
| `gp1l4-g3` | NVIDIA L4 24GB 1장, vCPU 4개, RAM 48GB | LLM·비전 모델 추론과 모델 서빙용 |
| `s2-g3` | vCPU 2개, RAM 8GB Standard 서버 | 웹·FastAPI·일반 작업·선택적 DB용 |
| 저장공간 | 약 100GB로 전달됨 | 모델 가중치와 데이터 저장에 사용. 실제 마운트 경로·용량 확인 필요 |

### 서버 코드 해석

현재 정보상 문서의 “V100”은 실제 장비 사양과 다르며, `gp1l4-g3`는 **L4 GPU 서버**로 보는 것이 맞다. 이 구성은 모델을 바닥부터 대규모 학습하는 환경보다, 7~8B급 오픈모델 또는 양자화 모델을 올려 안정적으로 추론·서빙하는 환경에 적합하다.

- L4 서버: Ollama·vLLM·Transformers 등 모델 런타임과 Naito 연동 실험
- s2 서버: FastAPI, 정적 파일 프록시, health check, 선택적 Redis/PostgreSQL
- 저장공간: 모델 1~2개와 최소 데이터만 보관

70B급 모델, 다중 GPU 학습, 대규모 파인튜닝은 이번 구성의 기본 범위로 잡지 않는다. 해커톤에서는 모델 크기보다 cold start·메모리·동시 요청·시연 안정성을 먼저 검증한다.

## 2. 가이드에 명시되지 않은 항목

참가자 가이드에는 다음 항목의 제공 여부가 적혀 있지 않다.

- 웹 프론트엔드 호스팅
- FastAPI 등 백엔드 상시 실행 서버
- PostgreSQL 또는 Supabase DB
- 사용자 인증 서비스
- 파일·오브젝트 저장소
- 도메인·TLS 인증서
- GPU 서버와 일반 서버의 외부 공개 URL 또는 포트
- Naito API의 정확한 base URL, 모델 목록, rate limit, 사용량 제한
- 두 서버 사이의 사설망 통신 가능 여부와 방화벽 규칙
- 100GB 저장공간의 실제 위치와 영속성

따라서 **GPU 서버가 곧 공개 웹 서버 또는 DB 서버라고 가정하면 안 된다.** 현재는 `gp1l4-g3`와 `s2-g3`를 역할 분리해 쓰는 구성이 합리적이지만, 실제 배포 가능 여부는 서버 접속 정보와 네트워크 정책을 확인해야 한다.

## 3. 해커톤 최소 웹앱 구성

이번 대회는 10월 30일 주제 공개 후 11월 1일 13:00까지 제출해야 하므로, 처음부터 DB와 계정을 모두 넣기보다 실제 시연 경로를 먼저 완성한다.

```text
정적 프론트엔드
  ↓ HTTPS
s2-g3 일반 서버
  ├─ FastAPI /api
  ├─ /health
  ├─ /api/plan/chat
  ├─ /api/recommend 또는 주제별 핵심 API
  ├─ DB (주제상 필요할 때만)
  └─ gp1l4-g3 내부 주소 호출
                  ↓
          L4 GPU 서버
            ├─ 오픈모델 서빙
            ├─ Naito API 연동 보조
            └─ 모델 추론
```

GPU 모델을 직접 서빙하지 않는 주제라면 s2-g3에서 FastAPI가 Naito API를 직접 호출하고, `gp1l4-g3`는 사용하지 않는 선택도 가능하다. 사용하지 않은 GPU를 억지로 기능에 넣지 않는다.

### 필수 기능

- 주제에 맞는 입력 화면
- 핵심 AI 기능 1개
- 결과 화면
- 로딩·오류·재시도 상태
- Naito API 연결 adapter
- API 키를 브라우저에 노출하지 않는 백엔드 프록시
- `/health` 확인용 엔드포인트
- README 실행 방법과 `.env.example`
- 2분 시연 영상에서 입력부터 결과까지 재현되는 고정 시나리오

### 초기에는 생략 가능한 기능

- 회원가입·로그인
- 사용자별 장기 저장
- 채팅 이력
- 관리자 화면
- RAG용 pgvector
- 실시간 스트리밍
- 복잡한 멀티테넌트 설정

DB가 없더라도 일회성 추천, Naito 채팅, 결과 표시, 시연 영상 제작은 가능하다. 발표 시 저장 기능을 구현하지 않았다면 “이번 MVP 범위에서 제외”라고 명시한다.

## 5. 현재 KONNECT에 적용할 실행 순서

### 1단계: 제공 서버 확인

운영진 또는 멘토에게 다음을 확인한다.

1. V100 서버가 웹 요청을 받을 수 있는가?
2. 외부에서 접근 가능한 IP 또는 URL과 포트가 있는가?
3. SSH 접속 방식과 계정은 무엇인가?
4. Docker·Python·CUDA·인터넷 접근이 가능한가?
5. 서버에 프로세스를 대회 종료까지 유지할 수 있는가?
6. 팀별 자원과 GPU 사용량 제한이 있는가?
7. Naito endpoint·모델·인증 헤더·rate limit은 무엇인가?

### 2단계: 가장 얇은 백엔드 실행

- s2-g3에 FastAPI 서버를 배포하고 `/health` 먼저 검증
- 외부 공개가 불가능하면 기존 Render를 공개 API 예비 경로로 유지
- GPU 모델이 필요한 주제만 gp1l4-g3에 모델 서버를 띄운다.
- `GET /health` 먼저 검증
- Naito 토큰은 서버 환경변수로만 입력
- `POST /api/plan/chat`을 Naito adapter와 연결
- 주제 공개 후 핵심 API를 하나 추가

### 3단계: 필요한 경우에만 저장 기능 추가

- 발표 시연이 안정화된 뒤 Supabase를 연결한다.
- 로그인·저장·RAG가 주제의 핵심이 아니면 추가하지 않는다.
- DB 연결 실패가 핵심 AI 시연을 막지 않도록 선택 기능으로 격리한다.

- 소스코드는 최종 커밋 기준으로 심사되므로 11월 1일 13:00 전 최종 커밋을 확정한다.
- GitHub 저장소는 Public으로 유지한다.
- API 키와 인증정보는 커밋하지 않는다.
- README에 설치·환경설정·실행 방법을 적는다.
- 발표자료에는 Naito API, GPU 서버, 사전 보유 KONNECT 코드 등 사용한 자원을 빠짐없이 적는다.

## 7. 현재 결론

- **Naito API 토큰:** 반드시 adapter를 미리 준비한다.
- **`gp1l4-g3` L4 서버:** 7~8B급 모델 서빙·추론용으로 활용하되, 70B급·다중 GPU 학습은 범위에서 제외한다.
- **`s2-g3` 일반 서버:** FastAPI·웹·선택적 DB를 맡기는 것을 우선 검토한다.
- **웹 백엔드:** s2-g3 공개가 가능하면 그곳에 배포하고, 확인 전까지 기존 FastAPI/Render를 예비 경로로 유지한다.
- **DB:** 초기 MVP에는 넣지 않는다. 로그인·저장·RAG가 주제상 필요할 때만 추가한다.
- **프론트:** React를 도입하지 않고 Vanilla JS를 유지한다.
- **최소 성공 기준:** 입력 → Naito 또는 핵심 AI 처리 → 결과 표시를 실제 화면에서 안정적으로 재현하는 것.
